## 세션 시작 루틴

> 사용자 요청을 처리하기 전, 매 세션 시작 시 자동으로 실행한다.

### 1. 현재 상태 파악

1. `workspace/project_rules.md` 확인 (존재하는 경우) — 프로젝트 고유 라우팅 힌트·행동 규칙 로드
2. `workspace/tasks/active/` 폴더 확인 — **이 폴더가 진행 중 작업 항목의 primary source다**
3. `workspace/tasks/INDEX.md` 확인 (존재하는 경우) — 요약·타입 참조용 cache. **참조하기 전에 아래 INDEX 유지보수를 먼저 수행한다.**

> **INDEX.md 유지보수 원칙:** INDEX는 현재 처리할 작업 항목을 찾기 위한 캐시이고, `tasks/done/`은 완료 이력 원본이다. INDEX를 참조하거나 작성할 때마다 다음 순서로 한 번 저장한다.
>
> 1. active/hold 폴더에 맞는 행만 남기고, 완료된 작업 항목의 done 행은 제거한다. done 폴더와 plan.md는 제거하지 않는다.
> 2. 작업 항목 행은 `active` → `hold` 순으로 정렬한다. 각 그룹은 생성일 내림차순, 같은 날짜는 항목명 오름차순이다. `[Layer 2 완료]` 마커는 표 밖의 하단 상태 기록으로 보존한다.
>
> 전체 정합성 점검은 현재 소스·Runtime 규칙·최신 문서를 기준으로 한다. `tasks/done/`은 과거 결정의 근거가 현재 기준만으로 불명확할 때만 선택적으로 참조하며, INDEX에 자동 재등록하지 않는다.

**메모리 시스템 우선순위:**

두 개의 메모리 시스템이 병존한다:

| 시스템 | 위치 | 역할 |
|--------|------|------|
| **프로젝트 메모리** (primary) | `workspace/memory/` | 프로젝트 설계 결정, 아키텍처, 계약, 도메인 규칙 |
| **세션 메모리** (보조) | `~/.claude/projects/.../memory/` | 사용자 선호, 협업 방식, 개인 컨텍스트 |

**충돌 시 원칙:**
- `workspace/memory/`가 항상 우선한다 — 프로젝트 사실(코드·설계·결정)에 관한 한 정답은 workspace다.
- 세션 메모리의 "기억"이 workspace 내용과 다르면 → workspace를 신뢰하고 세션 메모리를 오래된 것으로 간주한다.
- 세션 메모리는 workspace에 없는 **사용자 행동 방식·선호·협업 스타일**에만 권위를 가진다.

**단계 모델 — major (기본, 7단계):**
```
설계 중 → 설계 완료 ⛔계획승인 → 구현 중 → 검증 중 → 테스트 중 → 검토 완료 ⛔완료승인확인 → 완료 승인 → done
```
- **계획 승인** (`설계 완료 → 구현 중`): 사용자 명시적 승인 필요. 이후에는 요구사항 명세 또는 위험 신호 변경만 사용자 승인과 체크섬 갱신이 필요하며, 명세 밖 실행 기록 보완은 기록·누적 보고한다.
- **완료 승인 확인** (`검토 완료 → 완료 승인`): 사용자 명시적 완료 요청 필요. `완료 승인` 없이 done 이동 차단.
- **소스 수정**: 원칙적으로 `구현 중` 상태에서 진행한다. hook 경고가 있으면 agent는 누락된 작업 항목·계획·승인 여부를 사용자에게 알리고 바로잡는 경로를 제안한다. 기본 hook은 작업을 차단하지 않는다.
- **되돌아가기**: 어느 단계에서든 이전 단계로 자유롭게 복귀 가능 (게이트 없음).

**단계 모델 — minor (경량, 3단계):**
```
작성 중 [자동 승인] → 구현 중 → 완료 승인 ⛔완료승인확인 → done
```
- **계획 승인 생략**: 에이전트가 최소 plan.md 작성 직후 즉시 `approve` 실행. 사용자 명시적 승인 불필요.
- **완료 승인 확인**: 구현 완료 후 보고 → 사용자(또는 위임 에이전트) 확인 후 done 처리. 자동 완료 없음.
- **검증·테스트 단계 생략**: 에이전트 검증·사용자 테스트 단계는 생략. 완료 확인만 받는다.
- **소스 수정**: 동일하게 `구현 중` 상태에서 진행한다. 기본 hook은 기계 차단 대신 절차 경고를 제공한다.
- **major 전환**: 구현 중 범위가 예상보다 커지면 사용자에게 알리고 major 흐름으로 전환 가능.

**진행 중 작업 항목이 있는 경우** — plan.md YAML 프론트매터 `상태` 필드 기준:

| 상태 | 출력 메시지 | 기본 다음 단계 |
|------|-----------|--------------|
| 설계 중 | "계획서를 작성 중입니다. 이어서 진행할까요?" | 계획서 작성 |
| 설계 완료 | "계획서가 준비됐습니다. 검토 후 구현을 승인해주세요." | 계획서 검토 (계획 승인) |
| 구현 중 | "구현이 진행 중입니다. 이어서 계속할까요?" | `layer1_implement.md` |
| 검증 중 | "에이전트 검증이 진행 중입니다. 이어서 계속할까요?" | `layer1_review.md` |
| 테스트 중 | "사용자 테스트 단계입니다. 테스트 완료 후 알려주세요." | 사용자 확인 대기 |
| 검토 완료 | "검토가 완료됐습니다. 완료 처리를 승인해주세요." | 완료 처리 (완료 승인 확인) |
| 완료 승인 | "완료 승인됐습니다. done으로 이동할까요?" | 작업 항목 완료 처리 |

**진행 중 작업 항목이 없는 경우:** 세션 시작 시 두 경로를 한 줄로 안내한 뒤 요청을 기다린다 — **요청**("○○ 만들어줘/고쳐줘") 또는 **논의**("○○ 논의하자" — 토론 모드).

**진행 중 토론 확인 (토론 모드 안전망):** 토론은 `tasks/active/`에 등록되지 않으므로 별도로 확인한다. `workspace/exploration/discussion/`에 상태 마커가 `진행 중`인 문서가 있으면, 진행 중 작업 항목 현황과 함께 짧게 표시한다 — "진행 중 토론: [주제] (이어서 논의하려면 말씀해 주세요)". 폴더가 없거나 진행 중 문서가 없으면 침묵한다.

**issue 확인:** 세션 시작 시에는 확인하지 않는다. 작업 항목 완료 후 local `workspace/issues/`에 기록할 항목만 안내한다.

**workspace/ 자체가 없는 경우:** "workspace/가 없습니다. 프로젝트 초기화(Layer 0)가 필요합니다. 지금 시작할까요?"

| plan.md 상태 | 라우팅 | inject |
|-------------|--------|--------|
| 설계 중 | 계획서 작성 이어서 | `layer1_design.md` |
| 설계 완료 | 계획서 검토 (계획 승인 대기) | — |
| 구현 중 | 구현 이어서 | `layer1_implement.md` |
| 검증 중 | 에이전트 검증 이어서 | `layer1_review.md` |
| 테스트 중 | 사용자 테스트 대기 | — |
| 검토 완료 | 완료 처리 (완료 승인 확인 대기) | — |
| 완료 승인 | done 이동 처리 | — |

**단, 아래 조건 중 하나라도 해당하면 신규 요청으로 처리한다:**
- 현재 작업 항목과 무관한 파일·기능을 명시적으로 언급
- "별개로", "새로", "다른 거" 등 분리 의도가 명확한 발화
- 현재 작업 항목 범위 밖의 버그·기능 보고

**신규 여부가 모호한 경우:** "지금 [작업 항목명] 진행 중입니다. → 이 작업 항목의 일부로 처리할까요, 새 작업 항목으로 분리할까요?"

---

**[신규 요청] active 작업 항목이 없거나 명확히 새 요청인 경우 → 의도 판단**

> `workspace/project_rules.md`의 라우팅 힌트가 있으면 아래 순서보다 **우선 적용**한다.

**판단 우선순위 (순서대로 적용):**

1. **명시적 유형 선언** — "버그야", "새 기능", "리팩터링", "논의하자/토론하자" 등 사용자가 유형을 직접 말함 → 즉시 해당 유형으로 라우팅
   - **토론 모드 우선 판정:** "논의/토론/discussion 모드/의견 나누자" 명시 발화는 **2단계(동작 서술 분류)보다 먼저** 토론 모드로 라우팅한다. "이거 개선 논의하자"처럼 개발 동사가 섞여 있어도 토론 모드다 (개발 동사를 보고 리팩터링/새 기능으로 선점하지 않는다).
2. **동작 서술 vs 추가 요청** — "~하면 ~가 돼" / "~이 이상해" 형태 → 버그 수정 / "~해줘" / "~만들어줘" 형태 → 새 기능 또는 리팩터링
3. **키워드 힌트** — 아래 테이블 참조 (힌트일 뿐, 결정적 기준이 아님)
4. **불명확** → 2단계 진단

| 발화 패턴 (힌트) | 판단 유형 | 자동 로딩 |
|---------------|---------|---------|
| "~기능 만들어줘", "~추가해줘", "~구현해줘" | 새 기능 설계 | `workflows/new_feature.md` + `layer1_design.md` + `personas/task_designer.md` |
| "~버그", "~안 돼", "~에러", "~오류", "~이상해", "~이상하게", "예상이랑 달라", "안 맞아", "틀린 것 같아" | 버그 수정 | `workflows/bug_fix.md` + `layer1_review.md` + `personas/code_reviewer.md` |
| "이어서 해줘", "계속해줘", "어디까지 했어" | 작업 항목 재개 | → "태스크 재개" 섹션(`agent_rules_detail.md`) |
| "코드 봐줘", "검토해줘", "리뷰해줘" | 작업 결과 검토 | `workflows/code_review.md` + `layer1_review.md` + `personas/code_reviewer.md` |
| "리팩터링", "정리해줘", "개선해줘", "느려", "무거워", "복잡해" | 리팩터링 | `workflows/refactoring.md` + `layer1_design.md` + `personas/task_designer.md` |
| "논의하자", "토론하자", "~에 대해 의견 나누자", "discussion 모드" | 토론 모드 | `inject/discussion_mode.md` + `personas/discussion_partner.md` |
| "전체 확인", "정합성 점검", "전체 점검", "충돌 확인" | 전체 정합성 점검 | `layer2_checkpoint.md` + `personas/integration_auditor.md` |
| "초기화", "프로젝트 설정", "Layer 0" | 프로젝트 초기화 | `layer0_init.md` + `personas/architect.md` |
| "MPA 시스템 업데이트", "업그레이드" | MPA 버전 업데이트 | `layer0_update.md` + `personas/architect.md` |
| "규칙 바꿔줘", "inject 수정", ".mpa/runtime 수정" | MPA 파일 수정 | → `agent_rules_detail.md` "MPA 파일 수정 세부" 섹션 |

**판단 후 반드시 고지 — 라우팅 결과 + 정정 옵션:**

```
→ [버그 수정]
   로드: workflows/bug_fix.md · layer1_review.md · personas/code_reviewer.md
  ↪ 다른 유형이면: 새 기능 / 개선 / 단순 질문
```

- 로드한 파일 전체를 명시한다 — 사용자가 에이전트가 무엇을 읽었는지 확인할 수 있어야 한다.
- workflows 파일이 없는 유형(전체 정합성 점검, 초기화 등)은 로드 파일만 나열한다.
- 두 번째 줄은 가능한 다른 유형을 짧게 보여 사용자가 한 단어로 정정할 수 있게 한다.
- 정정 옵션은 발화 맥락에 맞는 유형 2~3개만 보여준다 (가능한 전체 유형을 다 나열하지 않는다).

**유형 불명확 시 — 2단계 진단 (라우팅 추정조차 어려운 경우):**
1. "지금 [기능]이 의도한 대로 작동하고 있나요?" → 아니오: 버그 / 예: 질문 2
2. "새 기능 추가인가요, 기존 기능 개선인가요?" → 새 기능: 설계 / 개선: 리팩터링

**라우팅 정정 발생 시:** 정정된 유형으로 즉시 재라우팅 + local `workspace/issues/`에 `methodology_improvement` issue로 기록.

## 작업 항목 생성

세부 절차: `inject/layer1_design.md` 참조.

**핵심 규칙:**
- plan.md를 채팅이 아닌 **파일로 먼저 저장**한다 (휘발 방지). 모든 작업 항목 plan.md에는 `## 실행 TODO` 체크리스트를 반드시 포함한다. **실행 TODO에는 이번 작업 항목이 끝나기 전 증빙을 갖춰 완료 처리할 수 있는 구현·검증·문서화·즉시 확인 가능한 사용자 결정/승인만 둔다.** 운영 중에만 알 수 있는 사항, 장래 관찰, 별도 범위의 후속 작업은 TODO에 넣지 않는다. 사용자·운영자가 수행할 후속 행동은 `운영 시 안내 사항`으로, **구현·설계·검증이 추가로 필요한 후속 작업은 별도 작업 항목으로 분리한다.** 상태를 실제 증빙에 맞춰 동기화한다. **이번 변경이 운영 방식에 주는 영향은 체크박스·완료 조건에 넣지 않고, major plan은 `검증 결과` 뒤의 별도 최상위 `## 운영 시 안내 사항`에 정보성으로 기록한다.** minor plan은 별도 검증 결과가 없으므로 마지막 체크리스트 섹션 아래에 둔다. 규모가 큰 작업 항목은 같은 폴더의 `TODO.md`를 상세 증빙 원본으로 만들고 plan.md의 TODO에서 링크한다.
- **자기 점검**: 모든 plan.md에 적용 (같은 스레드, 체크리스트 기반) — `inject/layer1_critique.md` "자기 점검" 섹션
- **독립 비평**: 기준 충족 시만 (서브에이전트 전용) — `inject/layer1_critique.md` "독립 비평 세션이 필요한 기준" 섹션
- 같은 스레드 비평·새 스레드 비평·자기비평은 폴백으로 사용하지 않는다. 서브에이전트 도구가 없으면 사용자에게 위험을 고지하고 독립 비평 없이 진행할지 묻는다.

**minor 작업 항목 경량 처리 (계획 승인 생략 / 완료 승인 확인 경량화):**

> 새 작업 항목을 생성하기 전엔 실패비용부터 추정해야 한다 → `core/agent_rules_detail.md` "실패비용 추정 기준" 섹션을 반드시 즉시 읽는다.

세부 절차: `core/agent_rules_detail.md` "minor 경량 처리 절차" 섹션 참조.

> **minor → major 전환**: 구현 중 예상 범위를 초과하거나 가치 결정이 생기면 즉시 사용자에게 알리고 major 흐름으로 전환한다.

**검증 격리 (major 전용):**
- **에이전트 검증**(`검증 중` 단계): 비평과 동일하게 **서브에이전트로 실행** — 구현 컨텍스트 격리. 1차(changelog 미참조) → 2차(changelog 대조) 두 단계 서브에이전트 호출. 상세: `inject/layer1_review.md` "실행 환경" 섹션.
- 서브에이전트 사용 불가 환경 → 자가 검증으로 대체 (위험 고지 후 진행).
- **명시적 승인 없이 구현을 시작하지 않는다** (계획 승인, major 전용 — minor는 자동 승인)
- 승인 요청은 내부 절차명을 노출하지 않고 평이하게 묻는다(GATE2의 "완료: [...]. → 확인 후 완료 처리해 주세요." 문구와 대칭): *"계획을 승인하고 구현으로 넘어갈까요?"*

**승인 시 처리:**
1. **approve 명령 실행** — 상태 전환과 해시 기록을 원자적으로 처리:
   ```bash
   python3 .mpa/runtime/hooks/plan_hash.py approve workspace/tasks/active/yyyymmdd_[태스크명]/plan.md
   ```
   - plan.md 상태가 `설계 완료`(또는 minor의 `설계 중`)일 때만 실행된다.
   - 자동으로 상태를 `구현 중`으로 전환하고 승인해시를 기록한다.
   - 이미 `구현 중`인 경우 approve가 거부된다 — plan.md를 직접 수정해 상태를 우회할 수 없다.
   - 이 해시가 계획 승인 재검증의 기준이 된다.

**승인해시 생성 규칙:**
- 모든 신규 major·minor plan의 `승인해시`는 요구사항 명세에서 계산된 **`reqspec-v1:<16자리 소문자 16진수>`**만 허용한다. 따라서 공통 템플릿의 `승인대상: 요구사항 명세`와 `## 요구사항 명세`를 지우지 않는다.
- 최초 값은 `plan_hash.py approve`만 기록한다. 사용자 승인 뒤 요구사항 명세가 바뀐 경우에는 `plan_hash.py renew-spec --summary`만 갱신한다.
- 날짜, `user-approved-*`, 자연어 승인 문구, 임의 체크섬을 `승인해시`에 직접 입력하지 않는다. 그런 기록이 발견되면 진행 상태를 임의로 유지하지 말고, 사용자 승인 이력을 확인해 `설계 완료`으로 복구한 뒤 정상 명령으로 다시 승인한다. 구형 plan은 자동 변환하지 않고 최신 템플릿 구조로 `승인대상`·요구사항 명세를 정리한 뒤 사용자 재승인을 받아야 한다.
- `구현 중`, `검증 중`, `테스트 중`, `검토 완료`, `완료 승인` 상태는 유효하고 현재 요구사항 명세와 일치하는 승인해시가 반드시 필요하다. 접두사 없는 구형 해시는 보존된 과거 이력을 읽을 때만 허용하며, active 작업의 승인 이후 상태에는 사용할 수 없다.

**요구사항 명세 재검증 (해시 기반 경고):**
- `승인해시`가 `reqspec-v1:`로 시작하는 새 형식 plan은 `## 요구사항 명세`만 비교한다. 접두사 없는 구형 plan은 과거 이력 읽기에서만 기존 본문 규칙을 유지한다. active 작업의 승인 이후 상태에서 접두사 없는 해시·알 수 없는 접두사·명세 형식 불일치는 오류로 처리한다.
- 명세 밖 실행 계획·변경 기록·검증 결과의 보완은 즉시 기록하고 구현 단위 종료·검증 진입·상태 요청·완료 검토 중 먼저 오는 지점에 누적 보고한다.
- 명세 변경 또는 위험 신호는 변경분을 사용자에게 제시하고 승인받은 뒤 `renew-spec --summary`로 승인 기록을 갱신한다. 명시적으로 `MPA_GATE=block`을 설정한 환경에서만 불일치를 차단한다.

## 작업 항목 완료

> **공통 원칙 — 완료 보고의 증거 기반:** "완료했다"고 보고할 때는 서술만으로 주장하지 않는다. 실제 변경 근거(수정된 파일의 핵심 줄 인용, 실행한 명령의 출력, 통과한 테스트 결과 등) 중 최소 하나를 인용해 보고에 포함한다. 인용할 근거가 없다면 작업 항목이 실제로 끝나지 않았다는 신호다.

**minor 작업 항목 — ⛔ 완료 승인 확인: 사용자(또는 위임 에이전트) 확인 후 done 처리**

구현 완료 후 아래 형식으로 보고하고 확인을 기다린다:
```
완료: [무엇을 했는가].
→ 확인 후 완료 처리해 주세요. 수정이 필요하면 말씀해 주세요.
```

> 발화가 완료로 인정되는지 판단이 필요하다 → `core/agent_rules_detail.md` "완료 인정 판별 기준" 섹션을 반드시 즉시 읽는다.

사용자가 완료를 확인하면:

1. **plan.md `상태`를 `완료 승인`으로 업데이트**
2. **INDEX.md 업데이트** — mv 전에 해당 active/hold 행을 제거하고 위 "INDEX.md 유지보수 원칙"을 수행한다.
3. `workspace/tasks/active/yyyymmdd_[태스크명]/` → `workspace/tasks/done/yyyymmdd_[태스크명]/` 이동

> minor 완료에서는 changelog, 에이전트 검증, 사용자 테스트 단계, docs 업데이트, 정합성 점검 제안을 생략한다. 필요한 항목이 생기면 minor가 아니라 major로 전환한다.

---

**major 작업 항목 — ⛔ 완료 승인 확인: 명시적 완료 요청만 처리한다.**

> 발화가 완료로 인정되는지 판단이 필요하다 → `core/agent_rules_detail.md` "완료 인정 판별 기준" 섹션을 반드시 즉시 읽는다.

사용자가 완료를 요청하면:
1. **plan.md `상태`를 `완료 승인`으로 업데이트** (완료 승인 확인 통과 기록)
2. **INDEX.md 업데이트** — mv 전에 해당 active/hold 행을 제거하고 위 "INDEX.md 유지보수 원칙"을 수행한다.
3. `workspace/tasks/active/yyyymmdd_[태스크명]/` → `workspace/tasks/done/yyyymmdd_[태스크명]/` 이동
4. `plan.md`의 "완료 시 문서 업데이트 대상" 확인 후 `docs/` 반영
5. **전체 정합성 점검 제안** — 여러 변경의 상호작용을 확인할 필요가 있으면 사용자에게 전체 정합성 점검을 제안하고, 현재 소스·Runtime 규칙·최신 문서를 직접 대조한다. 과거 결정의 근거가 현재 기준만으로 불명확할 때만 done 이력을 선택적으로 참조한다.
6. **methodology issue 확인** — local `workspace/issues/`에 방법론 개선 issue가 있으면 필요 시 수집을 제안한다. 수집·review·triage는 map-product source에서만 실행한다.

> INDEX.md가 손상된 경우 점검 상태는 재확인이 필요하다 — plan.md로 복구할 수 없다.

## 작업 항목 종료 시 (공통)

**정정 회고 (강제):**

세션 종료 직전 한 가지를 자가 회고한다 — 한 줄 짧게 답한다. 회고 자체를 건너뛰지 않는다.

> **이번 세션에서 내가 잘못 판단한 것 / 사용자가 정정한 것이 있는가?**

- **있음:** 어떤 패턴인지 식별하고 local `workspace/issues/`에 `methodology_improvement` issue로 기록.
- **없음:** "정정 회고: 없음"이라고 명시한다. (회고 자체를 건너뛰지 않음으로 다음 세션에도 회고 습관이 유지된다.)

> **회고의 한계 인지:** LLM은 자신이 체계적으로 잘못 판단하는 패턴은 인식하지 못한다.  
> 이 회고는 "사용자가 명시적으로 정정한 것"과 "스스로 의식한 오판"만 잡는다.  
> 완전한 검증 메커니즘이 아니다 — 일부라도 잡는 차선책이다.

MPA 시스템 개선 발견 시 → local `workspace/issues/`에 `methodology_improvement` issue 기록.
형식: `agent_rules_detail.md` "issue 기록" 섹션 참조.
