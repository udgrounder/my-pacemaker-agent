# 필요한 역할 문서만 사용하는 작업 가이드

이 프로젝트는 다른 프로젝트에 설치할 에이전트 작업 가이드와 템플릿을 개발한다. 모든 작업은 최소 plan.md를 유지하고 필요한 내용만 추가 문서로 분리한다. major/minor로 문서 수를 정하지 않는다.

| 문서 | 답하는 질문 | 작성 조건 |
|---|---|---|
| plan.md | 무엇을 왜 달성하고 무엇이 완료인가? | 항상 |
| implementation.md | 어떻게 설계하고 어떤 순서로 구현하는가? | 내용/인계의 분리 이익이 있을 때 |
| verification.md | 무엇으로 기준 충족을 확인하는가? | 검증 입력을 분리할 이익이 있을 때 |
| ui_design.md | 화면과 사용자 흐름을 어떻게 표현하는가? | 화면 설계 기준이 필요할 때 |

예를 들어 재시도 기능의 '정해진 실패를 처리한다'는 완료 기준은 plan에 둔다. 구조/오류 분류/재시도 간격의 설계와 변경 순서·진행은 implementation 또는 plan의 해당 섹션에 둔다. 오류 주입·횟수 확인 방법은 verification 또는 plan에 둔다. 같은 기준을 여러 문서에서 다시 정의하지 않는다.

얇은 작업은 변경 순서와 확인 방법을 plan에 몇 줄로 적으면 된다. 템플릿의 모든 칸을 채우거나 파일을 늘리는 것이 목표가 아니다. 문서 타입에 따라 역할을 정하되 서브에이전트 실행은 독립성과 실제 분리 이익을 따로 판단한다. 현재 모델보다 높은 모델을 자동 선택하지 않는다.

별도 지시서/폴더는 기본적으로 만들지 않지만 큰 작업·독립 조사·산출물 분리 관리가 유리하면 필요한 것만 만든다. 상위 plan에 목적·담당·의존성·경로·결과를 연결한다. 폴더 분리로 승인·병렬 수정 권한을 확대하지 않는다.

## HTML로 화면 디자인 확인하기

UI 디자인을 HTML로 보여 달라고 요청하면 에이전트가 작업 폴더에 HTML 미리보기를 작성하고, 렌더링을 확인한 뒤 열어 보여 주고 파일 링크를 제공한다. 예를 들어 '로그인 화면 디자인을 HTML로 보여줘'라고 요청할 수 있다. 작은 작업은 plan에서, 별도 화면 문서가 있으면 ui_design.md에서 미리보기 경로와 확인 버전을 연결한다. 미리보기는 화면 구성·흐름·상태를 확인하는 자료이며 예시 데이터·가상 동작은 표시한다. 디자인 확인과 실제 제품 구현/서버 연동 완료는 구분한다. 미리보기 도구를 사용할 수 없으면 여는 방법과 렌더링 미확인을 안내한다. 모든 UI 작업에 HTML이나 추가 문서를 강제하지 않는다.

## 에이전트가 관리하는 연결

Runtime의 inject/task_documents.md가 정본이다. 새 작업은 plan_minimal_template.md를 사용한다. 문서구성 roles-v1의 선택 목록과 요구사항 밖 mpa-doc JSON 등록은 에이전트가 관리한다. 선택 목록은 비어 있어도 정상이다. 존재하는 파일을 자동 선택하지 않는다.

승인 전에는 선택한 입력의 존재와 내용 대응을 확인한다. 기존 approve는 plan 상태/명세 해시만 정상 기록한다. 메인은 검토한 역할 기준을 spec/basis_sha256에 연결하고 변경 여부를 확인한다. checksum은 의미 검토를 대신하지 않는다. 문서 연결 오류만으로 재승인하지 않는다. 기존 plan/changelog 복구 거래를 유지한다.

task_documents.py inspect는 구성·선택 문서·기준 변경을 읽기 전용으로 검사한다. inputs는 지정 역할의 입력을 JSON으로 반환한다. 구현/검증 입력은 승인 상태·현재 명세해시·복구 미잔존을 먼저 확인하며, 해당 단계가 사용하는 문서의 연결을 검사한다. 전체 inspect/audit에서는 모든 등록을 확인한다. 단일형도 1차 설계 기준을 유지하고 2차에 실행·진행 기록을 포함한다. 이 도구가 실제 호스트의 접근을 차단하거나 모델 선택을 강제한다고 주장하지 않는다.

## 독립 검증

1차는 승인 요구사항·설계 기준·검증 방법·실제 제품 소스로 판정한다. 구현 실행/진행/완료 주장·changelog·전체 작업 diff는 전달하지 않는다. 2차는 1차 결과와 실행 기록을 대조한다. 구현 문서가 통합되어도 고정된 설계 기준 섹션만 재사용하면 매번 수동 발췌할 필요가 없다.

현재 작업을 최초 적용 사례로 사용한다. 사용 이익은 추가 질문·누락 제약·불필요한 읽기·전달 전 정리 부담으로 확인하고, 형식 검사 성공을 속도/비용 개선으로 표현하지 않는다.

reqspec 이전 구형 단일 계획서를 비평할 때는 목적·핵심 기능·구현 계획 등 원본 기준을 보존하고 진행/결과 기록을 제외한다. 새 제목으로 강제 변환하지 않으며 구형 해시의 실행 승인 정책은 그대로 유지한다.

기존 단일형/legacy 승인 방식과 done 이력은 자동 변환하지 않는다. 필요한 경우 명세·승인·실패 증거·이력을 보존하고 명세 밖 상세만 이동한다. Runtime 수정과 dist 동기화는 source 작업이며 실제 설치본 배포는 별도 요청에서 수행한다.
