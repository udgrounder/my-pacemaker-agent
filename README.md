# my pacemaker agent

> **AI agent와의 협업은 구조가 있어야 이어진다. my pacemaker agent는 그 구조를 프로젝트에 만들고 유지하는 도구다.**

## 무엇인가

my pacemaker agent는 AI agent와 프로젝트를 계속 함께 진행할 때, 작업의 맥락·결정·검증을 잃지 않도록 돕는 협업 방법론이다. 자연어로 요청하면 agent가 작업의 성격을 파악하고, 필요한 계획·검토·기록 흐름을 프로젝트 안에 남긴다.

AI가 코드를 만들 수 있다는 것만으로는 프로젝트가 안전하게 이어지지 않는다. 세션이 바뀌면 맥락이 사라지고, 작은 가정이 큰 변경으로 이어지거나, 무엇을 왜 결정했는지 잊기 쉽다. 이 도구는 그 문제를 사람의 판단과 agent의 실행을 분리하는 작업 구조로 다룬다.

## 언제 유용한가

다음처럼 한 번의 답변보다 프로젝트의 연속성과 검토가 중요한 경우에 특히 유용하다.

- 기능을 여러 단계로 설계·구현하고, 중간에 방향을 확인해야 할 때
- 세션이나 담당 agent가 바뀌어도 작업 배경과 결정 이유를 이어 가야 할 때
- 버그 수정·리팩터링·새 기능의 위험도에 맞춰 검토 수준을 달리하고 싶을 때
- 작업 중 얻은 개선점을 이슈로 남기고, 필요한 것만 다음 개선으로 연결하고 싶을 때

작은 변경까지 무겁게 만들기 위한 도구는 아니다. 변경의 실패 비용에 맞춰 짧게 진행하거나, 영향이 크면 사용자 확인을 늘리는 방식으로 작동한다.

## 시작하기

설치 가이드를 참조하도록 설정된 agent에게 **설치할 프로젝트 폴더를 함께 알려** 설치를 요청하면 된다.

```
/Users/me/projects/my-service 에 설치해줘
```

agent가 지정한 프로젝트 위치와 사용할 agent를 확인하고, 필요한 작업 환경을 준비한다. 기존 설치본은 자동으로 바꾸지 않으며, Runtime update도 사용자의 명시 요청과 확인 절차를 거쳐 진행한다.

설치 방법과 지원 환경은 [설치 가이드](install.md)에서 확인한다.

## 왜 만들었나

AI agent는 강력하지만, 틀린 판단도 그럴듯하고 자신 있게 제시할 수 있다. my pacemaker agent는 그 한계를 없애려 하기보다, 사용자가 의도를 분명히 하고 결과를 확인하며 필요한 결정을 직접 내릴 수 있도록 협업 구조를 제공한다.

이 도구는 agent가 대신 결정하거나 책임지는 방식이 아니라, 작업의 흐름·기억·검증을 정리해 사용자가 원하는 결과에 도달하도록 돕는다. 작업을 진행하며 의도가 더 선명해지는 과정을 자연스럽게 받아들이고, 확인과 보정을 반복할 수 있게 한다.

> ⚠️ 계속 작업 중인 도구입니다. 작동하지만 모든 상황을 완벽하게 보장하지는 않습니다.

---

## 이렇게 사용한다

설치된 프로젝트에서 agent에게 자연어로 작업을 요청하면 된다.

```
로그인 기능 요청을 작업 항목으로 등록해줘
결제 API 연동 버그 수정을 작업 항목으로 등록해줘
사용자 목록 페이지 리팩터링을 작업 항목으로 등록해줘
```

agent는 작업의 실패 비용을 판단해 적절한 흐름을 고른다.

- 작은 변경은 짧은 계획과 확인을 거쳐 진행한다.
- 영향이 큰 변경은 요구사항과 계획을 먼저 검토하고 승인받은 뒤 진행한다.
- 구현 뒤에는 검증 결과를 보고하고, 사용자의 완료 확인 뒤에 작업을 마무리한다.

### 작업 계획서가 작업의 중심이다

새 작업은 먼저 **작업 계획서**로 정리한다. 이 문서에는 사용자가 원하는 결과와 범위, 중요한 결정과 제약, 실행할 일, 진행 상태와 검증 결과가 함께 기록된다.

따라서 작업 계획서는 단순한 할 일 목록이 아니다. 사용자와 agent가 같은 목표를 확인하는 기준이며, agent는 이 문서를 중심으로 계획을 세우고 지시를 해석하며 구현·검증을 이어 간다. 사용자는 중요한 계획을 확인하고, 완료 전 결과를 다시 확인한다.

진행 중인 작업 계획서는 `workspace/tasks/active/[작업명]/plan.md`에 만든다. 작업이 완료되면 같은 작업 폴더가 `workspace/tasks/done/`으로 이동해, 계획과 실행·검증 이력이 함께 보존된다.

중단된 작업은 다음처럼 이어갈 수 있다.

```
로그인 기능 이어서 진행해줘
진행 중인 작업 계획서 기준으로 어디까지 했어?
```

agent는 해당 작업 계획서를 읽어 합의한 목표, 마지막 진행 상태, 남은 실행과 검증을 확인한 뒤 이어서 진행한다.

## 기존 설치본 업데이트

- **릴리즈:** 사용자가 명시적으로 요청하거나 배포에 필요한 경우에만 새 Runtime release를 만든다. 변경·검증만으로 자동 생성하지 않는다.
- **배포:** 사전 확인, 사용자 승인, rollback 책임자 확인 뒤에만 Runtime을 갱신한다. 기존 프로젝트 데이터·문서·agent 설정·일반 소스는 보존한다.
- **복구:** 문제가 있으면 배포 전 backup을 사용해 Runtime과 필요한 관리 설정을 함께 복원한다.
- **이력 정리:** 일반 배포·업그레이드는 이력을 자동 삭제하지 않는다. 사용자가 정리를 요청하면 전체 후보를 먼저 확인하고, 삭제 대상 승인 뒤에만 처리한다.

상세 절차와 운영 조건은 [설치 가이드](install.md)를 따른다.

## 프로젝트는 이렇게 나뉜다

이 도구는 협업의 원칙, 모든 프로젝트에 공통인 방법, 각 프로젝트의 실제 데이터를 분리한다. 각 층은 바뀌는 주기와 책임자가 다르기 때문에 분리되어 있다.

| 구분 | 의미 |
|---|---|
| 왜 | 협업의 원칙과 판단 기준 |
| 어떻게 | Runtime이 제공하는 공통 작업 방법 |
| 무엇을 | 프로젝트마다 쌓이는 작업·기억·문서 |

마스터 프로젝트는 이 방법론을 만들고 배포하는 곳이다. 설치용 Runtime, agent와 연결하는 설정, 가이드, 그리고 방법론 자체를 개선하기 위한 이슈와 작업 기록을 관리한다. 설치된 프로젝트는 이 방법론을 적용해 실제 제품·서비스를 함께 만드는 곳이다.

이 분리 덕분에 방법론을 업데이트해도 프로젝트 데이터와 사용자가 만든 결과물은 보존한다. 반대로 특정 프로젝트에서 생긴 기억·작업 기록은 다른 프로젝트에 섞이지 않는다.

### 설치된 프로젝트에서 보는 구조

```
[project]/
├── .mpa/                 ← 프로젝트에 적용된 공통 작업 방법
│   ├── runtime/           ← agent가 따르는 공통 규칙·작업 흐름
│   ├── config/            ← 이 설치본에만 적용되는 설정
│   └── backups/           ← 업데이트 전 상태를 되돌리기 위한 복구본
├── workspace/             ← 이 프로젝트와 함께 자라는 작업 데이터
│   ├── memory/            ← 프로젝트의 목적·구조·도메인 규칙·누적 학습
│   ├── tasks/             ← 작업 계획서, 진행 상태, 완료 이력
│   │   ├── active/        ← 진행 중인 작업별 계획서
│   │   └── done/          ← 완료한 작업의 계획·실행·검증 이력
│   ├── issues/            ← 방법론 개선으로 이어질 수 있는 관찰
│   └── exploration/       ← 토론·조사·사례처럼 자유롭게 탐구한 기록
└── docs/                  ← 개발에 필요한 문서와 진행 과정에서 생성된 문서
```

`workspace/` 안에서는 기억이 다음 작업의 맥락이 되고, 진행 중인 작업과 완료 이력이 이어진다. agent가 세션을 다시 시작해도 이 공간을 읽어 이전 결정과 현재 상태를 파악한다. `docs/`에는 개발에 참고할 문서와 작업 과정에서 만들어진 결과 문서를 남긴다. 따라서 작업 계획·상태를 관리하는 공간과 프로젝트 문서를 구분하면서도, 개발에 필요한 문서를 함께 축적할 수 있다.

### 작업은 어떻게 이어지는가

1. 사용자가 자연어로 원하는 결과를 요청한다.
2. agent가 변경의 실패 비용을 살펴, 작업 계획서에 목표·범위·결정·실행·검증 기준을 정리한다.
3. 필요한 경우 사용자가 작업 계획서의 계획과 중요한 결정을 확인한 뒤 구현한다.
4. agent는 같은 작업 계획서에 진행과 검증 결과를 이어 기록하고, 사용자가 완료를 승인하면 작업은 이력으로 남는다.

이 과정의 핵심은 agent가 사용자의 가치 판단을 대신하지 않는다는 것이다. agent는 조사·설계·구현·검증을 돕고, 방향과 중요한 선택은 사용자가 확인한다.

## 이슈는 개선의 재료로 남긴다

프로젝트에서 반복되는 불편, 방법론의 개선점, 검토가 필요한 관찰은 프로젝트의 이슈로 기록한다. 이슈는 곧바로 공통 방법론을 바꾸는 요청이 아니다. 먼저 해당 프로젝트에서 관찰을 남겨 두고, 사용자가 수집을 요청하면 여러 프로젝트의 후보를 함께 검토한다. 사용자가 채택한 항목만 별도 작업으로 반영한다.

즉, **관찰 → 프로젝트 이슈 기록 → 사용자 요청에 따른 수집·검토 → 채택한 개선의 반영** 순서다. 이 흐름은 한 프로젝트의 관찰이 다른 프로젝트에 영향을 주기 전에 사용자가 판단할 수 있도록 하기 위한 것이다.
