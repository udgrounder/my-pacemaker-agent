# 작업 완료 시 보조 자료 정리 제안 독립 비평

- 검토 대상: `workspace/issues/20261118_task_completion_artifact_cleanup.md`의 2026-11-18 사용자 보완 및 개선 방향
- 성격: 논의 제안의 독립 비평. 구현·삭제·완료 작업 재작성은 수행하지 않았다.
- 판정: 현재 필요성을 기준으로 정리하는 방향은 타당하다. 아래 P1 두 항목은 실제 삭제 규칙을 적용하기 전에 구체화해야 한다. 나머지는 작은 운영 규칙으로 보완 가능하며 원본 전량 보관이나 별도 증빙 문서 체계를 요구하지 않는다.

## 근거와 해석 범위

대상 제안 전체와 다음 정본의 관련 절만 대조했다. 실제 완료 작업 사례는 추가 열람하지 않았다. 따라서 아래 실패 시나리오는 현재 발생한 손실의 주장이 아니라 제안 실행 시 가능한 조건이다.

- `.mpa/runtime/core/agent_rules_detail.md`의 「승인 기록 처리」, 「승인 이력 저장과 복구」, 「계획서와 변경 이력 관리」, 「작업 항목 완료 처리」
- `.mpa/runtime/inject/task_documents.md`의 「작성·승인·기준 확인」, 「전환·완료」
- `workspace/memory/shared/architecture.md`의 「보관·복구 자산의 용도 구분」, 「shared/ 파일은 로그가 아니라 현재 상태 스냅샷」, 「작업 계획은 현재 기준, changelog는 변경 이력」

이는 plan.md가 아니므로 계획서 양식·게이트·승인해시의 누락을 결함으로 취급하지 않았다. 영구보존 의무나 별도 법적 보관 의무도 자료에서 확인되지 않았으므로 가정하지 않았다.

## 적용 전 막아야 할 핵심 결함

### P1-1. 지적의 종결과 그 파일 전체의 역할 종료를 구별해야 한다

**문제조건 → 손실/영향:** 한 검토 파일에 해결된 지적, 최종 검증 결론, 수용 위험의 전제가 섞여 있거나 한 스냅샷이 여러 지적의 근거를 함께 담을 수 있다. 지적 대부분이 종결됐다는 이유로 파일과 종속 자료를 묶어 삭제하면, 아직 유효한 결론을 지탱하는 유일한 관측값이나 재현 입력까지 사라질 수 있다. 반대로 한 항목만 유효하다는 이유로 전체 묶음을 보관하면 제안의 축약 목적을 달성하지 못한다.

**현재 제안의 관련 근거:** 「개선 방향」은 “지적별로” 상태를 확인하고 “필요한 내용만” 최종 문서에 반영하도록 이미 요구한다. 다만 “해결됐거나 처리 불필요한 검토·평가 원본”과 이를 뒷받침한 자료를 함께 정리한다는 문장에서, 항목별 판단이 파일 전체 삭제 가능 판단으로 넘어가는 조건은 명시되지 않았다.

**구체 보완:** 삭제 가능 조건을 한 문장으로 고정한다. 해당 파일이 소유한 정보 중 현재 필요한 정보가 없거나, 필요한 정보가 알맞은 정본에 저장·대조되어 원본 의존이 해소된 때만 삭제한다. 요약으로 대체할 수 없는 원문이 현재의 구체적 재현·복구에 필요하면 그 최소 원문만 남긴다. 혼합 파일은 필요한 부분을 기존 최종 문서에 옮기거나 축약하고 나머지를 정리한다. 검토 전체·모든 근거의 복제는 요구하지 않는다.

**숨은 가정:** 지적 상태와 자료의 모든 소비 관계가 일대일이라는 가정은 성립하지 않을 수 있다. “해결됨”은 지적의 처리 결과이며, 그 자료에 남은 정보 전체의 보존 판정은 아니다.

### P1-2. 정보 이관 성공 확인과 승인 경계 확인이 삭제보다 앞서야 한다

**문제조건 → 손실/영향:** 판단 이유를 plan/changelog로 옮기려다 저장에 실패하거나, 참조만 제거한 뒤 내용 이관을 놓치거나, 승인 명세 블록에 포함된 링크를 단순 정리로 고치면 원문은 사라지고 최종 기록은 불완전해질 수 있다. 마지막 경우에는 명세 내용과 승인해시의 관계까지 달라진다. 이미 사용자에게 확인받은 검증 결론의 유일한 근거를 지운 뒤 참조를 없애는 것만으로는 그 결론의 적절성이 보장되지 않는다.

**현재 제안의 관련 근거:** “삭제 대상의 참조·승인 무결성을 함께 정리하고 남길 정보와 실제 파일 상태를 확인”한다는 목표는 있다. 정본은 의미 있는 결정 변경 이력을 먼저 저장하고 성공 확인 후 plan을 교체하도록 요구하며, 요구사항 명세 변경은 기존 승인 절차를 따른다. `task_documents.md`는 내용 대응 검토와 checksum을 구별하고 문서 연결 문제만으로 재승인하지 않도록 한다.

**구체 보완:** 순서를 `대상·잔존 정보 판정 → 적합한 정본에 최소 정보 저장 → 저장 내용과 현재 결론 대조 → 참조·등록·승인 영향 확인 → 삭제 → 실제 파일 상태·연결 확인`으로 둔다. 내용 이관·대조 실패 시 해당 대상만 삭제하지 않는다. reqspec-v1 명세 밖 기록 정리는 해시 갱신 사유가 아니며, 명세 블록 변경이나 legacy 본문 해시 영향이 생기면 기존 승인 경로를 따른다. 정리를 위해 승인해시를 다시 계산하거나 지적을 종결시키지 않는다.

**미해소 결정:** 정리가 사용자 완료 확인 전 준비인지, 확인 후 완료 처리의 일부인지 명확하지 않다. 최소안은 완료 확인 전에 남길 결론과 정리 범위를 정돈하고, 확인 후 실행 시 그 기준이 달라지지 않았는지 대조하는 것이다. 판정이 완료 기준·위험 수용·사용자 결정에 영향을 주면 그 변경을 먼저 확인받는다. 모든 삭제에 별도 승인을 추가할 필요는 없지만 기존 완료 확인을 범위가 달라진 정리의 승인으로 확대해서는 안 된다.

## 운영 규칙으로 보완할 사항

### P2-1. “처리 불필요”의 판정 책임과 근거 수준

**문제조건 → 손실/영향:** 담당 에이전트가 검증 불가나 불편한 지적을 처리 불필요로 분류하고 원문을 정리하면 현재 미확인·실패가 정상 완료로 바뀔 수 있다. 반대로 모든 기각 항목에 별도 TODO나 긴 변명 문서를 만들면 정리 비용만 커진다.

**현재 제안의 관련 근거:** 지적별 상태 확인과 자동 후속 TODO 금지는 적절하다. 다만 누가 상태를 확정하고, 처리 불필요와 위험 수용·미확인을 무엇으로 구분하는지는 열려 있다. 정본은 현재 실패·미충족 증빙과 유효한 제외 범위를 유지하고 완료 기준을 결과에 맞춰 낮추는 정리를 금지한다. `task_documents.md`는 메인이 review와 선택 문서의 미완료/미확인을 대조하도록 한다.

**구체 보완:** 기존 메인 담당자가 각 지적을 현재 요구사항·실제 결과와 대조해 정리 책임을 맡는다. 처리 불필요는 예를 들어 중복, 잘못된 전제, 이미 승인된 범위 밖임을 짧게 확인한다. 최종 결론·위험·승인 범위에 영향을 주는 기각 이유만 기존 plan/changelog에 남기고, 사소한 중복 기각까지 영구 목록화하지 않는다. 해결 확인이 안 된 항목을 처리 불필요로 바꾸지 않으며 유효한 위험 수용은 위험과 적용 조건을 남긴다. 범위나 완료 기준을 바꾸는 판정만 기존 사용자 확인 절차로 보낸다.

**판정:** 독립 재검토나 새 승인 체계를 항상 추가할 사안은 아니다. 기존 메인의 대조 책임을 정리 단계에도 연결하면 된다.

### P2-2. 참조 정리의 의미는 링크 삭제보다 넓지만, 전수 조사까지 확대할 필요는 없다

**문제조건 → 손실/영향:** 최종 문서가 “검토 통과, 상세는 삭제한 파일 참조”만 남기거나 선택 문서 등록이 삭제 파일을 계속 가리키면 결과 이해·후속 실행·검사가 깨질 수 있다. 다른 작업이 그 자료를 현재 입력으로 쓰는 경우에는 소유 작업의 완료만으로 자료 역할이 끝나지 않는다.

**현재 제안의 관련 근거:** 참조·승인 무결성 정리와 다른 작업 자산의 별도 판단은 이미 있다. 그러나 해당 작업이 생성한 자료를 다른 작업이 소비하는 경우의 최소 확인 범위는 정해지지 않았다. 정본은 plan이 요구사항·승인의 정본이고 선택 문서는 등록된 기준 checksum과 의미 대응을 관리한다고 설명한다.

**구체 보완:** 해당 작업의 plan/changelog·선택 문서 등록·관련 최종 문서와 알려진 후속 연결을 확인한다. 그 문서가 현재 필요로 하는 내용은 새 정본의 실제 위치로 연결하고 단순 과거 작업 링크는 과거 참조임을 드러내거나 제거한다. 등록 기준을 바꾸면 내용 대응을 확인한다. 다른 작업의 현재 의존이 확인되면 그 의존 부분만 이관·보존한다. 잠재적 숨은 참조를 완전히 찾겠다는 이유로 done 전체를 읽거나 모든 원문을 남기지는 않는다.

**구현 시 기술결정:** 링크 탐색 방식, 등록 갱신 방법, 삭제 후 검사 명령은 구현 시 정할 문제다. 현 논의에서 도구까지 지정할 필요는 없으며, 기계적 참조 부재가 의미상 의존 부재의 증명은 아니라는 점만 유지하면 된다.

### P2-3. 한 번의 완료 정리가 새 보관 사업으로 커지지 않도록 종료 범위를 둔다

**문제조건 → 손실/영향:** 모든 자료에 장기 보존 사유를 작성하고 모든 해소 지적의 이력을 별도 정리하면 저장 용량보다 판단·재서술·검증 비용이 커진다. 반대로 파일명이나 크기만으로 일괄 삭제하면 정본·release·복구 자산을 잘못 포함할 수 있다. 중도 실패를 완료로 숨기면 다음 담당자는 어떤 정리가 실행됐는지 알기 어렵다.

**현재 제안의 관련 근거:** 새 요약 파일과 전체 복제를 금지하고 기존 기록에 필요한 만큼만 남기는 방향은 과잉보관을 이미 억제한다. 적용 범위는 “해당 작업이 생성한 보조 자료”이다. architecture의 release/deploy backup은 독립 정리 절차가 있으며, 승인 복구 정본은 `.plan-renewal.json`뿐 아니라 확보 파일·충돌 근거의 대조도 요구한다.

**구체 보완:** 이번 완료의 보조 자료와 확인된 연결에 범위를 한정하고, 기존 done 일괄 정리는 별도 요청으로 분리한다. 자료 목록·새 요약·영구 삭제 manifest를 의무화하지 않는다. 기존 작업 기록에는 필요한 이관 위치, 현재 남긴 예외와 이유, 미실행·실패 범위만 짧게 남긴다. 재개가 필요하면 실제 파일 상태부터 확인한다. 파일 이름이 snapshot이라는 이유로 release/deploy backup·사용자 원본·복구 충돌 근거를 같은 절차에 넣지 않는다. 반대로 정상 복구가 끝난 일시 자료를 무기한 보호 자산으로 취급하지 않는다.

**구현 시 기술결정:** 삭제 도중 실패했을 때의 재시도·기록 순서와 임시 복구 방식은 구현 단계에서 정한다. 실제 변경에 필요한 최소 중단 복구만 설계하고, 모든 원본을 별도 archive로 옮겨 삭제를 대체하는 기본안은 채택하지 않는다.

## 이미 처리된 조건과 추가로 요구하지 않을 것

- 과거 검증 사용 사실만으로 보관하지 않는 기준, checksum은 원문 복원 수단이 아니라는 기준은 명확하다. 이를 동일한 결함으로 다시 지적하지 않는다.
- 현재 유효한 제약·수용 위험·후속 조치·핵심 결정 이유·승인·검증 결론을 남기는 원칙이 있다. 해결된 지적의 근거를 전부 없애자는 제안으로 읽지 않는다.
- 처리 불필요한 항목의 자동 TODO화 금지, 원문 전체 복제와 새 요약 파일 억제는 적절하다. 검토마다 영구 처분표를 요구하지 않는다.
- 사용자 원본·제품 산출물·진행 중 승인 복구·다른 작업 자산의 구별은 이미 있다. 보완 대상은 이 구별의 실행 순서와 공유 의존의 판단이다.
- 제안은 아직 방향 기록이며 실제 삭제·Runtime 구현을 완료했다고 주장하지 않는다. 현재 실패한 구현이나 완료 이력 손상으로 판정하지 않는다.

## 최소 권고

기존 개선 방향에 다음 세 가지 계약만 명확히 추가하면 의도와 운영 안전성을 함께 지킬 수 있다.

1. 지적 종결 후에도 파일에 현재 필요한 정보가 남는지 판정하고, 최소 정보 이관·저장·대조가 끝나야 해당 원본을 정리한다.
2. 메인이 기존 완료 기준·위험·승인 범위를 바꾸지 않은 채 상태를 확정하고, 의미가 바뀌는 결정만 기존 사용자 확인·승인 경로를 따른다.
3. 정본과 알려진 현재 의존의 참조를 먼저 연결하고 삭제 후 실제 상태를 확인한다. 실패한 대상은 미정리로 드러내며, 기존 완료 이력 전수 조사·원문 전량 보관·새 영구 요약 체계는 기본값으로 만들지 않는다.
