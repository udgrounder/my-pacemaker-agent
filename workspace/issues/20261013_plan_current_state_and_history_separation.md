# 계획서의 현재 유효 정보와 변경 이력 분리
**처리 상태**: 후속 4건 및 보완 검증 지적 해결·독립 재검증 완료, 사용자 결과 확인 대기
**연결 작업**: `workspace/tasks/active/20261013_plan_current_state_history/plan.md`
**타입**: 방법론 개선
**발견 상황**: 사용자가 계획서 작성 과정에서 불필요해지거나 잘못된 방향에서 남은 내용이 누적된다고 설명하고 별도 변경 이력 파일 분리에 대한 의견을 요청함.
**적용 범위**: 모든 프로젝트

## 현재 방식
계획서 템플릿에 명세 변경 이력이 있고 별도 changelog 템플릿에도 명세 대비 변경 사항을 기록한다. 현재 판단과 과거 기록의 배치·정리 기준이 불명확하면 폐기된 접근과 중복 기록이 계획서에 남을 수 있다. 사용자 보고이며 개별 계획서의 잔존 내용 전수 검증은 수행하지 않았다.

## 개선 방안
- plan.md는 현재 유효한 목적·범위·완료 기준·제약·결정·가정·실행 항목·검증 현황을 담는다. 현재 결정을 이해하는 데 필요한 이유는 유지한다.
- 별도 변경 이력에는 날짜, 변경 대상, 이전/이후 판단, 변경 이유, 명세 영향, 필요한 승인·검증 근거를 기록한다. 기존 changelog.md 확장을 우선 검토해 문서 수와 중복을 줄인다.
- 폐기된 접근·해결된 질문·취소된 실행 항목은 필요한 변경 근거를 이력에 보존한 후 계획서에서 정리한다. 이미 수행한 작업의 증빙은 보존한다.
- 변경 시 현재 계획과 이력을 같은 작업 단위로 갱신한다. 의미 있는 결정 변경만 기록하고 사소한 문장 수정까지 수동 이력으로 누적하지 않는다.
- 목적·범위·완료 기준·위험 제약 등 승인 대상 변경은 기존 승인·해시 갱신 절차를 유지한다. 문서 정리를 통한 의미 변경도 동일하게 취급한다.
- 에이전트는 평소 최신 계획을 읽고, 과거 판단 확인이 필요한 경우 관련 이력만 선택적으로 읽는다.

## 개선 방향 보고 — 2026-10-13

### 확인한 원인
- plan_template은 취소한 구현 단계를 취소선으로 남기도록 하고, 초기 생략 판단을 보존한 채 실행 중 변경 기록을 추가하도록 한다.
- layer1_implement는 changelog의 명세 밖 보완을 plan의 실행 중 변경 기록으로 다시 정리하도록 한다.
- layer1_review는 두 문서의 변경 기록 일치를 확인한다. 중복 기록이 검증 규칙에도 연결되어 있다.
- hooks/plan_hash.py의 renew_spec은 plan 안의 명세 변경 이력 섹션을 요구한다. 템플릿에서 해당 표만 제거하면 승인 갱신이 실패할 수 있다.

### 권장 문서 구조
- plan.md: 현재 요구사항, 현재 채택한 접근과 핵심 이유, 유효한 제약·가정, 미해결 질문, 현재 작업의 실행·검증 상태, 문서 반영 대상과 운영 안내, 이력 링크.
- changelog.md: 의미 있는 계획·결정 변경을 시간순으로 보존하는 변경 이력과 실제 구현 변경·증빙. 계획 변경과 구현 결과는 섹션으로 구분해 예정 작업이 구현 완료처럼 읽히지 않도록 한다.
- 별도 history.md는 기본적으로 추가하지 않는다. 기존 changelog를 확장하고 기록 정본을 하나로 둔다.
- 완료된 유효 실행 항목과 증빙은 유지한다. 폐기·대체된 항목은 이력 보존 뒤 현재 계획에서 제거하거나 현재 접근으로 교체한다.
- 현재 결정을 이해하는 데 필요한 이유와 재발 방지 제약은 계획에 남긴다. 유효한 제외 범위를 불필요한 과거 내용으로 오인해 지우지 않는다.

### 변경 처리 절차
1. 변경 전후와 이유를 정리하고 명세·위험 영향을 판별한다.
2. 요구사항·위험 변경은 사용자에게 변경분을 제시해 승인받는다. 승인 전에는 기존 유효 계획과 승인 기록을 유지하고 변경안은 후보로 구분한다.
3. 변경 이력과 현재 계획을 같은 갱신 단위로 저장한다. 이력에는 날짜·대상·이전 판단·새 판단·이유·명세 영향·관련 승인/증빙을 남긴다. 원문 전체 복제는 기본 요구하지 않으며 명세 변경의 이전/이후 내용을 추적할 수 있게 한다.
4. 취소 항목·해결된 질문·틀린 가정·대체된 접근과 그 의존 참조를 정리한다. 구현 결과에 맞추기 위해 완료 기준이나 미충족 증거를 삭제하지 않는다.
5. 현재 계획의 실행 항목과 검증 기준이 서로 일치하고 변경 이력이 보존되었는지 확인한다.

### 절차 적용 시점
- 결정·가정·접근이 실질적으로 바뀌면 관련 부분을 즉시 갱신한다.
- 설계 검토 제출 전, 구현에서 검증으로 넘어가기 전, 작업 재개 시에는 폐기 내용·중복·잘못된 참조를 짧게 확인한다.
- 문장 다듬기나 체크 상태 변경만으로 이력 항목을 만들지 않는다. minor는 의미 있는 변경이 있을 때 필요한 이력만 기록하고 빈 이력 파일을 강제하지 않는다.

### 승인·검증 보존
- plan의 현재 승인해시는 유지하고 명세 변경 승인 이력의 저장 위치만 changelog로 옮기는 방향을 검토한다.
- 요구사항 명세 정리는 기존 해시 계약에 따라 처리한다. 의미가 같다는 에이전트 판단만으로 승인해시를 임의 재계산하지 않는다.
- 승인해시와 이력을 갱신하는 도구는 두 파일의 일부 저장 실패 때 불일치를 남기지 않게 구현·검증한다.
- 독립 1차 검증은 현재 plan과 실제 결과를 판단하고, 2차 검증에서 이력과 승인 변경 근거를 대조한다. 폐기한 가정의 영향·승인 없는 기준 완화·누락 변경은 2차에서도 확인한다.

### 적용 순서와 완료 기준
1. 템플릿과 core 규칙에 문서 역할·기록 정본·정리 기준을 정의한다.
2. 설계·구현·발견·검증·재개·minor 절차와 승인 갱신 도구 및 관련 테스트를 함께 수정한다. sub_template과 glossary 등 연관 참조도 점검한다.
3. 새 작업부터 적용한다. 진행 중 작업은 재개 시 필요한 부분을 전환하고 기존 이력을 먼저 보존한다. 구형 plan의 승인 갱신은 계속 지원하며 완료 이력을 일괄 재작성하지 않는다.
4. 방향 변경, 틀린 가정, 취소 단계, 명세 재승인, 구형 계획 재개, 부분 저장 실패 사례로 확인한다. 승인 없는 명세 변경 차단과 독립 검증 원칙도 유지해야 한다.
5. 검증 후 source Runtime을 dist에 동기화한다. 릴리즈·설치 프로젝트 배포는 별도 명시 요청으로 처리한다.

완료 판단: plan만 읽어 현재 유효한 실행 방향을 이해할 수 있고, changelog에서 변경 전후와 근거를 추적할 수 있으며, 폐기 내용이 현재 지시로 읽히지 않고 승인·증빙이 손실되지 않는다.

## 검증 중 정정 회고
독립 2차 대조에서 architecture 문서의 실제 수정과 계획서의 참고 전용 표기가 다르고, 이미 완료한 전체 테스트·Runtime 일치 확인이 내역서의 남은 확인에 남아 있음을 발견했다. 변경 이유를 이력에 먼저 기록한 뒤 현재 계획·남은 확인을 갱신했다. 문서 현재성 점검은 계획 본문뿐 아니라 수정 대상 분류와 상태 기록에도 적용해야 한다.

후속 독립 재검토에서는 외부 변경의 검사 이후 교체/원복 타이밍과 승인 쌍의 최종 확인 누락을 재현했다. 이전 검증에서 이 타이밍을 놓쳐 잔여 지적 0개로 보고했다. 상세 근거는 연결 작업의 `independent_review_crosscheck_20261013.md`에 보존한다. 새 복구 절차의 필수 로드 연결과 Markdown 섹션 계층 누락도 확인했다. 수정은 아직 실행하지 않았으며 현재 plan의 미해결 상태를 갱신했다.

보완 작업에서 파일 이동 직후 내부 플래그 기록 전 인터럽트 경계와 프론트매터 없는 plan의 audit 사유 누락을 추가 발견해 해결했다. 실제 inode 판정·no-clobber 설치·최종 대조 및 복구 우선 라우팅을 확인했다. 독립 1차·2차가 실제 SIGINT 두 경계와 최종 219개 테스트를 확인했고 미해결 필수 지적은 없다. 상세는 연결 작업의 `repair_review_summary.md`에 보존한다.
