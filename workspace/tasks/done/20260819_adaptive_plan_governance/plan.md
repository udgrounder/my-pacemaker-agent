# 태스크 계획서: 적응형 계획 거버넌스

## 요구사항 명세

### 요청 기준

계획서 전체의 사소한 보완이 반복 사용자 승인을 요구하지 않게 하되, 합의한 결과와 안전 경계는 계속 보호한다.

### 목적

사용자와 확정한 요구사항과 개발 중 갱신되는 실행 계획을 분리하여, 정상적인 조사·구현·검증 보완은 자율적으로 진행하고 명세 변경만 명시적으로 승인받는다.

### 범위·제외 범위

새 plan 형식·해시 훅·코드 게이트·관련 지침·사용자 문서를 같은 운영 모델로 맞춘다. 기존 plan을 일괄 변환하거나, 최초 계획 승인 및 완료 승인 확인을 제거하지 않는다.

### 완료 기준

새 템플릿은 요청 기준·목적·범위·제외 범위·완료 기준·사용자 결정·변경 불가 제약을 구조적으로 제공한다. 최신 plan의 승인해시는 `reqspec-v1:` 접두사로 명시하고, 접두사 없는 기존 해시는 구형 규칙을 유지한다. 명세 밖 보완은 해시를 바꾸지 않고 기록·누적 보고되며, 명세 또는 위험 신호 변경은 승인 뒤 체크섬 이력을 갱신한다. 실행 TODO에는 이번 태스크 종료 전 증빙을 갖춰 완료 처리할 수 있는 항목만 두며, 운영 영향은 체크리스트·완료 조건과 분리한 운영 시 안내 사항으로 사용자에게 알린다. minor는 전용 템플릿을 사용하고, 이 정책은 source·설치 Runtime 회귀 테스트로 검증된다.

### 사용자 결정

요구사항 명세만 승인·체크섬 보호 대상으로 둔다. 최신 형식은 `reqspec-v1:<체크섬>`으로 승인해시에 버전을 표시하고, 접두사 없는 기존 해시는 자동 변환하지 않는다. 명세 밖 변경은 즉시 기록하고 자연스러운 점검 지점에서 누적 보고한다. 명세 변경은 사용자 승인 후 상태를 되돌리지 않고 새 체크섬과 이력을 기록한다.

### 변경 불가 제약

외부·비가역 영향, 보안·권한·개인정보, 공개 호환성, 비용·일정, 새 가치 판단은 즉시 사용자 확인 대상으로 남긴다. `dist/.mpa-workspace/`는 source에서만 동기화하며 직접 편집하지 않는다.

**파생 출처:** `mpa_glossary_and_layering` — 표준 `plan.md` 구조를 적용한 뒤, 승인해시가 실행 계획의 정상적 보완까지 사용자 재승인 대상으로 만드는 마찰을 확인함

### 요청 원문

> 실제로 개발하면서 더 좋은 생각이나 문제가 되는 부분이 있으면 계속 계획서를 보완하면서 진행해야 하는데 그때마다 사용자에게 강제하려 한다. 사용자 의도를 벗어나지 않도록 한 안전장치는 유지하되, 계획서의 정상적 보완까지 재승인을 요구하지 않도록 절차를 반영한다.

### 목적

사용자가 승인한 목표와 위험 경계는 보존하면서, 에이전트가 개발 중 발견한 실행 계획의 개선을 기록하고 계속 진행할 수 있게 한다.

### 요구사항

- 계획서에서 사용자와 합의한 요구사항 명세와 살아 있는 실행 계획을 구분한다.
- 요구사항 명세는 `요청 기준`, `목적`, `범위·제외 범위`, `완료 기준`, `사용자 결정`, `변경 불가 제약`으로 구성한다.
- 요구사항 명세의 완료 기준은 체크박스가 아닌 불변 선언문으로 작성한다. 실제 확인 상태·증빙·테스트 결과는 명세 밖 `검증 결과`에 체크리스트로 기록한다.
- 명세를 바꾸지 않는 구현·조사·테스트·기록의 보완은 재승인 없이 진행할 수 있게 한다.
- 명세 밖 변경은 즉시 변경 기록에 남기고, 구현 단위 종료·검증 진입·사용자 상태 요청·완료 검토 중 먼저 오는 시점에 누적 요약으로 보고한다.
- 누적 변경이 한두 문장으로 설명하기 어렵거나 구현 방향을 실질적으로 교체하면, 다음 단계 전에 별도 진행 보고를 한다.
- 명세 변경 또는 정의된 위험 신호가 발생하면, 변경 내용을 좁혀 사용자에게 명시적 확인을 요청한다. 확인을 기다리는 동안 외부 영향 없는 조사·대안 비교는 계속할 수 있지만, 명세 변경·위험한 실행은 하지 않는다.
- 사용자가 명세 변경을 승인하면 새 명세 체크섬과 이전·새 체크섬, 변경 요약, 승인 시각을 원자적으로 기록한다. 이때 태스크 상태는 유지하며, 명세 밖 변경은 체크섬을 갱신하지 않는다.
- 해시 비교, 훅 경고, 계획·발견·구현·검토 지침, 템플릿, 기존 plan 호환 규칙의 의미를 일치시킨다.
- Runtime 배포본(`dist/.mpa-workspace/`)과 설치본을 같은 내용으로 동기화하고 검증한다.

### 확정된 운영 정책

#### 요구사항 명세와 실행 기록의 분리

`## 요구사항 명세`만 사용자 승인과 체크섬 보호 대상이다. `## 실행 계획`, `## 실행 중 변경 기록`, `## 검증 결과`는 살아 있는 실행 기록으로, 목적·범위·완료 기준·사용자 결정·위험 제약을 바꾸지 않는 한 에이전트가 갱신한다.

```text
요구사항 명세         → 무엇을 왜 어디까지 할지, 어떤 결과가 필요한지
실행 계획             → 그 결과에 도달하는 방법과 순서
실행 중 변경 기록     → 개발 중 무엇을 왜 보완했는지
검증 결과             → 완료 기준을 어떤 증빙으로 확인했는지
```

#### 명세 밖 변경의 기록·보고

명세 밖 변경은 발견 즉시 `변경 내용 / 이유 / 명세 영향 없음`을 기록하고 구현을 계속한다. 사용자는 구현 단위 종료·검증 진입·상태 요청·완료 검토 중 먼저 오는 지점에서 마지막 보고 이후의 변경분을 누적 요약으로 받는다. 이 보고는 승인 요청이 아니며, 사용자가 방향을 바꾸지 않는 한 에이전트는 다음 단계로 진행한다.

#### 명세 변경과 체크섬 갱신

명세를 바꿔야 한다면 에이전트는 변경된 명세 항목, 발견 이유, 사용자·호환성·비용·위험 영향, 권장안과 대안을 제시한다. 사용자가 승인한 뒤에만 전용 명령이 새 요구사항 명세의 체크섬을 계산해 `승인해시`를 갱신하고, 명세 변경 이력에 다음을 남긴다.

| 항목 | 기록 내용 |
|---|---|
| 이전 체크섬 | 변경 전 승인된 요구사항 명세 식별값 |
| 새 체크섬 | 변경 후 승인된 요구사항 명세 식별값 |
| 변경 요약 | 사용자에게 제시한 명세 변경분 |
| 승인 시각 | 사용자의 명시 승인에 대응하는 기록 시각 |

이 경로는 최초 승인용 `approve`와 분리한다. 최초 승인은 `설계 완료 → 구현 중` 상태 전환을 수행하지만, 명세 변경 재승인 기록은 이미 진행 중인 태스크의 상태를 바꾸지 않는다.

#### 위험 신호 기본안

아래 신호가 하나라도 확인되면 누적 보고를 기다리지 않고 변경분을 사용자에게 제시한다. 단순 불확실성은 먼저 조사하고, 조사 뒤에도 경계 통과 여부가 불명확할 때만 확인을 요청한다.

- 요구사항 명세의 목적·범위·완료 기준·사용자 결정·위험 제약 변경
- UX·우선순위·비용·단순성 같은 가치 판단의 신규 선택
- 배포·외부 호출·결제·발송·데이터 변환·삭제 등 외부 또는 비가역 영향
- 인증·권한·비밀값·개인정보 처리의 변경
- 공개 API·CLI·설정·데이터 형식·모듈 간 계약의 호환성 변경
- 사용자가 합의한 예산·일정·지원 범위의 증가 가능성
