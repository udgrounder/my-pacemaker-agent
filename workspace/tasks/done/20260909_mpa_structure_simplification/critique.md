# 구조 개선 계획 독립 비평

## 비평 결과

**판정: 보완 필요.** 아래 두 항목의 로드 계약·복구 검증 기준을 계획에 명시한 뒤 구현 승인 대상으로 제시해야 한다. 구현과 테스트 실행은 하지 않았다. 지정된 정체성·아키텍처·계획·첨부 지도와 Runtime 규칙, 실제 운영 코드·기존 테스트를 읽어 검토했다. contracts.md는 존재하지 않는다.

### 🚨 실패 시나리오

#### C1 — D1 이동 뒤 minor가 상세 정책을 건너뛰거나 major 설계 컨텍스트까지 추가 로드한다

- **대상:** dependency-map.md의 `문서 이동 명세` D1 및 `대표 요청별 정책 도달성 검증표`; plan.md의 구현 3단계.
- **근거:** D1은 작업 생성 상세를 `inject/layer1_design.md`에 통합하고 core에 “계획 작성 직전 design 로드”를 남긴다고 한다. 그러나 검증표의 minor 실행 경로는 `core → detail 실패비용·minor 경량 처리 → 승인 기록 처리`이며 design을 거치지 않는다. 실제 detail의 `minor 경량 처리 절차` 2번은 공통 template을 직접 읽어 plan을 작성한다. 반면 design은 앞부분에서 persona와 shared 메모리를 필수로 읽고, 이후 `작업` 절에 이르러 minor 분기를 선언한다.
- **실패 조건·영향:** 구현자가 검증표대로 minor의 기존 직접 경로를 유지하면 design으로 옮긴 공통 상세에 도달하지 않을 수 있다. 반대로 D1의 무조건 design 로드를 적용하면 minor가 종전보다 많은 설계 컨텍스트를 먼저 읽는다. 두 해석 모두 현재 계획 문구에 부합하므로, “정책 행동 유지”와 “필요한 규칙만 로드”를 무엇으로 판정할지 결정되지 않았다.
- **필요한 보완:** D1에서 옮기는 세부 규칙마다 major 전용인지 minor 공통인지 구분한다. minor 공통 규칙의 정본과 직접 도달 경로를 지정하고, design 전체를 읽는지 지정 절만 읽는지도 명시한다. minor 실행·계획만 요청의 두 검증 행에 template과 D1 상세의 실제 경로를 포함하고, 필수 역할/메모리 로드의 전후 차이도 확인한다. 이는 기술 설계 보완이며 별도 사용자 가치 결정을 요구할 사안은 아니다.

#### C2 — deploy의 복구 설명을 rollback에도 적용해 기존 동작을 잘못 고정할 수 있다

- **대상:** dependency-map.md의 `배포·실패 복구 순서 보존`과 `호환 검증 설계` 5번.
- **근거:** 지도는 deploy·rollback을 함께 언급한 뒤 예외 경로에 “각 복구가 실패해도 다음 복구를 시도하는 구조”를 보존한다고 서술한다. 실제 `release_manager.py`의 `rollback`(1910행 부근 이후)은 `previous` 복원 시 `shutil.rmtree(target)`와 `previous.replace(target)`를 별도 복구 예외 수집 없이 실행하고, config 복구 오류는 삼킨다. 이는 deploy의 recovery_errors 수집·후속 복구 지속 구조와 다르다. 실패 주입표에는 issue batch·backup 압축처럼 deploy 전용 지점이 포함되지만 rollback별 기대값은 분리되어 있지 않다. 기존 `test_rollback_receipt_failure_restores_applied_runtime`는 source receipt 실패 후 rule.md가 복원되는지만 확인한다.
- **실패 조건·영향:** ZIP 추출은 rollback에서도 재사용되므로 staging 실패·손상 backup·권한 오류를 검증해야 한다. 그런데 공통 설명을 기대값으로 삼으면 현행 rollback의 실패 동작을 테스트 보강 단계에서 새로 고치거나, deploy 테스트 통과만으로 rollback 보존을 주장할 수 있다. 전자는 이번 작업의 관측 가능한 동작 변경 금지에 어긋나고, 후자는 복구 호환성의 검증 공백이다.
- **필요한 보완:** 위 예외 순서 설명의 적용 범위를 deploy로 한정하고 rollback의 실제 정상·예외 순서를 별도로 기록한다. 실패 주입표를 명령별로 구분하여 rollback의 archive 검증/해제 실패, 교체 실패, config 복원 실패, source receipt·target history 실패 및 복구 자체 실패에서 확인할 Runtime/config·receipt/history·임시 경로·lock 상태를 정한다. 기존 취약한 실패 동작을 발견하면 현행 보존 대상으로 명시하고, 개선은 별도 범위로 기록한다. 모든 지점을 새 테스트로 중복 작성할 필요는 없지만 기존 테스트 이름과 미검증 관측값을 연결해야 한다.

### ⚠️ 숨은 가정 (파급효과 높은 순)

1. **deploy와 rollback의 실패 복구 성질이 같다:** 실제 예외 처리 구조가 다르므로 C2의 공통 기대값으로 호환성을 판정할 수 없다.
2. **계획 작성은 모두 design을 경유한다:** minor는 detail에서 template으로 직접 진입하므로 C1의 이동 대상별 경로 구분이 필요하다.

### ❓ 미해소 비가시적 위임

- **C1:** minor 공통 정책을 어느 경로에서 읽게 할지, design 로드 범위를 어디까지로 할지가 구현자 선택으로 남아 있다.
- **C2:** rollback의 기존 복구 한계를 보존할지 공통 설명에 맞춰 수정할지가 검증 기대값 작성자에게 넘어갈 수 있다. 이번 작업은 동작 보존으로 고정해야 한다.
- 별도의 사용자 목적·범위 결정 누락은 발견하지 못했다. 위 항목은 구현 승인 전에 에이전트가 구체화할 기술 계약이다.

### 🔧 구조적 문제

- **선행조건:** C1 경로표와 C2 명령별 실패 기대값은 구현 2단계의 회귀 기준선·3단계의 정책 도달성 검사보다 먼저 확정해야 한다. 테스트 구현 과정에서 정본과 기대 동작을 새로 결정하면 변경 전 기준선의 독립성이 약해진다.
- **아키텍처 충돌 위험:** architecture.md는 minor 절차의 정본을 detail에 두고 워커가 core를 미리 읽었다고 가정하지 않는다. D1의 공통 상세 이동은 이 경계를 명시적으로 연결해야 한다. 또한 rollback을 deploy처럼 복구하도록 조용히 바꾸는 것은 명세의 관측 가능한 동작 보존 제약과 충돌한다.
