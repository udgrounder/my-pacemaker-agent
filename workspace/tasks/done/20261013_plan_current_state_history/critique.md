# 독립 계획 비평

**대상:** `workspace/tasks/active/20261013_plan_current_state_history/plan.md`
**판정:** 저장 계약·기록 순서·호환 범위를 보완해야 한다.
**방법:** 설계 대화 없이 계획과 실제 Runtime·테스트를 검토했다. 후속 복구 JSON 제안은 추가 검토했다. 작업 소스는 수정하지 않았다.

## 비평 결과

### 🚨 실패 시나리오

1. **[높음] 두 파일 사이 프로세스 종료로 승인 기록과 해시가 어긋난다.**
   - 대상: 구현 단계 3, 저장 실패 반례.
   - 근거: `hooks/plan_hash.py::renew_spec`은 기존 내부 이력과 해시를 한 `write_plan`으로 저장한다. 새 changelog 배치는 두 번 저장하므로 개별 `os.replace`만으로 동일 성질을 유지할 수 없다.
   - 판정: 예외 발생 시 원복만으로는 프로세스 종료·원복 실패를 처리하지 못한다.
   - 개선: 독점 생성하는 복구 기록에 호출 직전 원본과 예상 결과 체크섬·배치·원래 파일 존재 여부를 보존한다. 잔존 시 check/audit/게이트/approve/renew-spec이 복구 필요를 판정한다. changelog 실패, plan 실패, 원복 실패, 두 저장 성공 후 복구 기록 제거 실패를 각각 검증한다. 제거 실패도 성공으로 출력하지 않는다. 원본/예상 작성본과 다른 외부 편집이 있으면 무조건 원복하지 않고 중단한다.

2. **[높음] plan에서 과거 판단을 먼저 지우고 이력 저장에 실패하면 증거가 사라진다.**
   - 대상: 계획 정리·minor 기록 순서.
   - 근거: `templates/plan_template.md`는 초기 생략 표 보존을 요구하고, `inject/layer1_implement.md`는 단계 종료 때 기록을 종합하며, `core/agent_rules_detail.md` minor 절차는 changelog 기본 생략이다. 계획에는 이 지시를 대체하는 저장 선후 조건이 없다.
   - 판정: 승인 도구 복구만 해결해도 일반 문서 정리에서 증거 소실이 남는다.
   - 개선: 의미 있는 이전 판단·실패 증빙을 changelog에 성공적으로 기록한 뒤 plan을 교체한다. 실패 시 이전 plan을 유지한다. 현재 미해결 실패·위험은 plan에 남기고, 재검증 필요가 된 기존 성공 결과는 과거 증거와 현재 효력을 구분한다. minor에서도 의미 있는 정리에는 이력을 먼저 생성한다.

3. **[중간] 기존 내부 표와 접두사 없는 구형 해시를 같은 호환 경로로 취급하면 갱신 후에도 승인 불일치가 남는다.**
   - 대상: 구형 배치 판별 가정.
   - 근거: `plan_hash.py::compute_for_plan`은 형식 표지 없는 plan을 전체 본문 legacy 해시로 계산한다. `renew_spec`은 이력 추가 이전에 새 해시를 계산한다. `tests/test_plan_hash.py`에는 header만으로 legacy 계산을 유지하고 승인 이후 legacy 해시를 거부하는 테스트가 있다. `core/agent_rules_detail.md`는 구형 plan 재승인을 요구한다.
   - 판정: 표 위치 호환성과 해시 형식 호환성은 별개다.
   - 개선: reqspec-v1 + 내부 표, reqspec-v1 + 표 없음, 접두사 없는 legacy, 미지원 해시를 구분한다. 앞의 두 경우만 각각 내부/changelog 갱신을 허용하고 legacy는 기존 재승인 절차로 보낸다. 정확한 헤딩만 판별하고 링크·인용·중복/손상된 헤딩을 조용히 수용하지 않는다.

### ⚠️ 숨은 가정 (파급효과 높은 순)

- **복구 JSON 원본이 이전 승인 명세라는 가정:** 갱신 호출 시 새 명세 본문과 이전 해시가 함께 있는 것은 정상이다. `tests/test_plan_hash.py::test_renew_spec_preserves_status_and_records_history`가 본문 변경 후 갱신한다. 원복은 호출 직전 바이트 보존이며 이전 승인 명세 복원이 아니다. 복구 설명과 테스트도 이를 구분해야 한다.
- **과거 판단을 2차 검증만 보면 충분하다는 가정:** `inject/layer1_review.md`는 1차에 changelog를 전달하지 않는다. 현재 완료 기준·미해결 위험·미충족 증거를 plan에서 제거하면 1차가 필요한 사실도 놓친다. plan에 현재 유효한 기준과 미해결 상태를 유지하는 경계를 명시한다.
- **헤딩 존재만으로 안전한 배치를 판별한다는 가정:** 이력 헤딩이 요구사항 명세 안에 있거나 중복되면 해시 대상이 변하거나 잘못된 위치에 기록된다. 섹션 위치·중복을 검증하고 잘못된 입력은 저장 전 거부한다.

### ❓ 미해소 비가시적 위임

- **반복 갱신:** 동일 해시로 반복 호출할 때 기록 추가/거부 정책을 명시한다. 새 명세 변경과 실패 재시도를 구분한다.
- **기존 changelog:** 승인 기록을 추가하는 정본 섹션, 해당 섹션이 없는 기존 문서의 추가 방식, 줄바꿈·파이프 escaping을 정한다. 기존 상세 구현 기록을 덮지 않는다.
- **복구 자료 수명:** 오류 시 보존하는 복구 기록을 기본 history 파일 추가 금지 결정과 구분한다. 위치·이름·성공 시 제거·실패 시 보존·복구 순서를 안내한다.
- **최초 approve 실패:** 현재 approve는 상태와 해시를 별도 `set_field`로 저장한다. 이 기존 위험을 이번에 처리할지 범위 밖으로 둘지 명시한다. 잔존 복구 기록을 approve로 우회하지 못하게 하는 것은 필수다.

### 🔧 구조적 문제

- **단계 의존성:** 이력 저장 계약 → 새/기존 갱신 구현·실패 검증 → 새 템플릿 적용·규칙 정리 → Runtime 동기화·독립 검증 순서를 명시한다. 현재 템플릿 변경이 도구보다 먼저여서 중간 새 plan은 renew-spec에 실패한다. 구현은 단일 순차로 유지한다.
- **참조 범위:** `core/session_protocol.md`도 changelog 기반 재개를 설명하지만 수정 목록에는 없다. core·inject·templates에서 취소선/초기 판단 보존/실행 중 변경 기록/명세 변경 이력 참조를 확인해 연쇄 수정한다.
- **아키텍처:** source/dist 경계·immutable 과거 자산 보존의 직접 충돌은 발견하지 못했다. shared architecture의 현재 계약은 구현 결과에 맞춰 갱신한다. 새 배치 때문에 1차 changelog 격리를 완화하지 않는다.
