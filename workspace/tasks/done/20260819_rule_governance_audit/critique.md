## 비평 결과

### 🚨 실패 시나리오

1. **감사 기준 자체가 충돌할 때 판정이 재현 불가능하다.** 계획은 권위 순서를 매핑한다고만 하고(계획서 76~77행), 충돌 발견 시 어느 문서를 최종 기준으로 삼고 어떤 방식으로 ``발견 사항``으로 남길지는 정의하지 않는다. 예를 들어 실행 규칙, 프로젝트 규칙, 사용자 문서가 서로 다른 지시를 내리면, 감사자가 임의의 권위를 선택해 결과를 낼 수 있다. 이는 메타 워크플로우가 진입점 통치를 맡고 작업 워크플로우가 정본이라는 아키텍처 정의(architecture.md 128~137행)와도 직접 연결되는 핵심 판정이다.

2. **배포 완결성 확인이 존재하지 않는 release를 전제로 실패할 수 있다.** Step 6은 release package·manifest·receipt를 대조 대상으로 삼지만(계획서 86행), 현재 release가 없을 때의 최소 검증 단위와 결과 상태(해당 없음/차단/검증 불가)가 없다. architecture.md는 release bundle과 대상 deploy backup을 서로 대체할 수 없는 자산으로 규정한다(15행, 21~24행). 따라서 산출물이 부재한 상태에서는 package 기준 감사와 install 경로 감사가 섞여, 배포 결함을 “확인되지 않음”으로 누락하거나 source 결함으로 오판할 수 있다.

3. **“대표 사용자 요청” 검증이 실제 실행 증거 없이 서술 검토로 끝날 수 있다.** Step 7은 단순 질문·규칙 수정·전체 점검·배포·재개 라우팅을 재현 검토한다고 하나(계획서 87행), 각 시나리오의 입력 문구, 기대 라우트, 관찰할 hook/파일 결과, 실패 판정이 없다. 특히 architecture.md는 진입 PM 스레드와 단계 워커의 적재 규칙이 다르다고 명시한다(135~137행). 이 경계가 검증 모델에 없으면 문서상 링크만 따라가고 실제로는 잘못된 스레드에 메타 규칙이 적재되는 실패를 잡지 못한다.

4. **읽기 전용 감사가 기록 생성과 충돌해 절차 위반으로 분류될 수 있다.** 변경 불가 제약은 감사 중 ``.mpa-workspace/``, ``dist/``, 배포 산출물, receipt, 과거 이력을 바꾸지 않는다고 하지만(계획서 53~56행), Step 8과 수정 대상 표는 audit_report 및 INDEX 변경을 예정한다(88행, 98~105행). 어떤 기록이 감사 산출물로 허용되는지, INDEX 갱신이 기준선 이전/이후 어느 시점에 일어나는지 정하지 않아, 감사 도중 상태·증거가 변화한 것처럼 보이는 재현성 문제가 생긴다.

### ⚠️ 숨은 가정 (파급효과 높은 순)

1. **“권위 순서”가 이미 존재하고 단일 선형 순서라는 가정.** 계획은 이를 작성 대상으로만 둔다(76~77행). 그러나 architecture.md는 메타/작업/단계 워크플로우와 역할·스킬을 별도 구성 층위로 정의하고(117~137행), project 규칙도 모든 세션에서 최우선 로드되는 확장 지점이다(89~92행). 동률·범위별 우선권·충돌 해소 원칙이 없으면 감사 보고서의 결론이 감사자별로 달라진다.

2. **규범 문장이 정규화 가능한 표면 표지로 나타난다는 가정.** Step 2의 추출 표지(`must/should/금지/예외/원칙/기본값`, 82행)는 frontmatter 상태값, 표, 파일 경로 소유권, “직접 수정 금지” 같은 구조적 제약을 포괄하지 않는다. 실제 아키텍처의 배포 경계·additive-only·불변 bundle 계약(architecture.md 7~15행, 26~30행)은 산문 키워드 탐색만으로 완전하게 추출되지 않는다.

3. **용어의 ‘외부 표준 충돌’을 평가할 권한과 출처가 있다는 가정.** Step 3은 외부 표준과의 충돌을 분류하지만(83행), 에이전트 가정은 외부 계약이 있을 때만 공식 문서 대조를 추가한다고 제한한다(62~64행). 어떤 용어가 법·보안·도구 고유 용어인지, 외부 조사에 무엇을 사용할지, 미검증 시 어떤 라벨을 붙일지가 없어 내부 정의 우선 원칙과 외부 표준 평가가 일관되지 않다.

4. **‘실제 실패 사례 또는 현재 위험 모델’의 증거가 감사 범위 안에서 확보된다는 가정.** 제한 삭제를 보류하는 기준은 제시됐지만(96행), 위험 모델의 정본, 증거 최소 요건, 증거 부재 시 유지/완화 후보의 차이가 없다. 그 결과 증거 부족이 “제한 유지”라는 기본값으로 굳어져, 요청한 과도한 제약의 식별 목적을 약화시킬 수 있다.

### ❓ 미해소 비가시적 위임

1. **발견 사항의 동치·중복 병합 규칙이 없다.** Step 2~6이 같은 근본 원인(예: source/dist 불일치)을 각각 규칙, 용어, 실행성, 배포 결함으로 보고할 수 있다. 최종 보고서의 한 항목화 기준, 근거 연결 방식, 심각도 산정 책임이 없으므로 보고서가 중복되거나 영향이 과장될 수 있다(계획서 82~88행, 133행).

2. **‘의도적 중복’ 판정을 감사자에게 위임한다.** 같은 내용이면 정본화하되 실행 안정성용 중복은 결함이 아니라고 했지만(94행), 의도 여부를 입증할 출처·기준이 없다. source↔dist 복제처럼 아키텍처에서 요구된 중복과, 누락된 동기화로 우연히 같은 내용을 가진 중복을 구별할 수 없다.

3. **source↔dist 비교의 기준 버전과 허용 차이를 정하지 않았다.** Step 1/7은 차이를 확인·검증한다고 하지만(81행, 87행), architecture.md는 Runtime이 sync-runtime으로만 dist에 동기화되고 release는 immutable archive라고 구분한다(7~15행). 현재 source, dist, 특정 release 중 어느 조합을 비교하며 생성 파일·버전 메타데이터·의도적 제외를 어떻게 제외할지 수행자 판단으로 남아 있다.

4. **후속 조치의 소유자와 트리아지 기준이 없다.** 즉시 조치/후속 태스크/기록만으로 나눈다고 하나(47행), 이번 태스크는 직접 변경 금지다(37행). 따라서 “즉시 조치”가 무엇을 뜻하는지, 이슈와 새 태스크 중 어디에 기록할지, major/minor와 사용자 승인 게이트를 누가 결정할지가 빠져 있다. 아키텍처의 ‘파생 태스크를 먼저 등록한 뒤 원 태스크 종료’ 규칙(73~76행)을 실행할 수 없다.

### 🔧 구조적 문제

1. **판정 모델보다 추출·감사가 앞선다.** Step 2~6은 대규모 발견을 생성하는데, 그 결과를 판정할 권위 매트릭스와 심각도/증거 모델은 사전 조사에서 “작성”만 하며 완료 산출물·승인 조건이 없다(76~88행). 의존 관계상 기준선과 권위/판정 스키마를 먼저 확정한 후에 규칙 추출, 용어·실행성·비례성·배포 검사를 수행해야 같은 문제를 일관되게 분류할 수 있다.

2. **실행 레이어와 설명 레이어를 구분한다고 하면서 교차 규칙의 판정 위치가 없다.** 완료 기준은 양 레이어를 구분하라고 요구하고(45행), Step 5는 준수 비용을 실행 레이어에만 적용한다고 제한한다(118행). 하지만 README나 guidebook의 강한 지시가 agent 행동을 사실상 유발할 때(진입점/복사 안내 등), 설명 결함인지 실행 제약인지 복합 결함인지 분류 경로가 없다. 결과적으로 중요한 사용자 유도 결함이 ‘문서 품질’로 축소될 위험이 있다.

3. **배포 감사가 규칙 감사와 한 단계에 결합돼 검증 심도가 불균형해진다.** 배포는 설치·update·rollback의 파일 계약과 절차적 안전성을 함께 다뤄야 하지만(계획서 86행), Step 6은 자산·진입점·버전·안내를 한 번에 확인한다. architecture.md의 deploy transaction, additive migration, rollback backup 계약(15행, 26~30행)을 검증하려면 경로별 입력/출력/실패·복구 상태를 별도 체크리스트로 분해해야 한다. 그렇지 않으면 파일 존재성만 검사하고 transaction 안전성은 놓친다.

4. **독립 검증이 감사 산출물의 검증이 아니라 원본 규칙 재검토와 중복된다.** Step 4와 Step 7 모두 라우팅·상태·예외를 추적하지만(84행, 87행), Step 7이 무엇을 독립적으로 검증하는지—추출 데이터, 발견 항목, 권고안, 또는 실제 경로—가 정의되지 않는다. 독립성의 입력과 기대 출력이 없으므로 같은 해석을 반복해 확증 편향을 줄이지 못한다.
