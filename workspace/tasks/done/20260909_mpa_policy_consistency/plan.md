# 작업 계획서: MPA 규칙 정합성과 경량 검증 보완

**파생 출처:** 2026-09-09 프로젝트 가치·개선 방향 검토 및 사용자의 “보완을 위한 계획서 작성해줘” 요청.

전체 보완 순서: **이 작업 → [효과 측정 체계](../../hold/20260909_mpa_effectiveness_evaluation/plan.md) → [구조 개선](../../hold/20260909_mpa_structure_simplification/plan.md)**. 후속 작업은 hold에 등록하고, 각각의 구현 범위는 해당 계획서 검토 후 승인한다.

## 요구사항 명세

### 요청 기준

앞선 검토의 다섯 개선 축(규칙 충돌, minor 최소 검증, 승인·hook 보장 범위, 효과 측정, 내부 복잡도)을 실행 가능한 순서로 보완한다. 계획 작성 후 사용자가 “첫번째 계획서 부터 작업 진행해줘”라고 요청하여 이 계획의 구현을 승인했다. 릴리즈·배포는 포함하지 않는다.

### 목적

같은 상황에서 읽은 문서에 따라 에이전트 행동이 달라지는 문제를 줄이고, 작은 작업의 절차 부담을 낮추면서 결과 확인은 유지한다. 사용자가 규칙·검사·사용자 판단의 실제 경계를 이해할 수 있게 한다.

**상위 제품 원칙: “사용자를 필요 이상으로 불편하게 하지 않는다.”** 모든 작업 유형에 적용한다. 질문·승인·기록·알림을 설계할 때 사용자에게 필요한 판단과 실제 위험 통제에 기여하는지 확인하고, 에이전트가 처리할 수 있는 부담은 에이전트가 맡는다.

### 범위·제외 범위

- 범위: 독립 비평/검증 폴백, minor 사전 확인·자동 승인·최소 확인, 정책 원본과 메모리 참조 관계, 승인·hook 보장 범위의 설명, 이 정책들의 회귀 검증, source/dist 동기화.
- 공통 적용: 위 정책에서 사용자에게 요청하는 질문·승인·수동 작업·알림을 감사해, 유효한 기존 의도·답변·승인을 재사용하고 불필요한 중단을 제거한다. minor에만 한정하지 않는다.
- 제외: hook 차단 범위 확장, 새로운 승인 인증 시스템, 상태·승인해시 형식 변경, 기존 plan 마이그레이션, 릴리즈 생성·설치 프로젝트 배포, 효과 측정 도구 구현, release_manager 모듈 분리. 뒤의 두 항목은 연결된 후속 작업에서 다룬다.

### 완료 기준

1. 대상 정책마다 정의 원본이 하나이고, core·workflows·inject·persona·현재 memory·가이드에서 반대 행동을 지시하는 문구가 없다. 정책 지도에서 발견한 해당 정책의 활성 호출자를 모두 조사·수정 범위에 포함한다. 관련 파일 목록과 변경 전후 행동표가 작업 폴더에 남는다.
2. 독립 **비평**은 대화 상속 없이 필요한 파일만 전달한 서브에이전트의 유효한 산출물까지 확보해야 완료다. 도구 없음·격리 불가·호출 실패·산출물 누락이면 미완료로 기록하고 한계를 알린 뒤 사용자에게 비평 없이 진행할지 확인한다. 일시 오류에 한해 재시도는 1회까지이며 격리 불가는 재시도하지 않는다. 자기 점검을 독립 비평으로 표기하지 않는다. 독립 **구현 검증**은 같은 실패 조건에서 현재 core 규칙대로 한계를 알리고 자가 검증할 수 있다. 자가 검증으로도 확인 못 한 것은 미확인으로 남긴다. 두 폴백을 구분한다.
3. minor는 명확한 실행 요청이 이미 있으면 중복 “진행할까요?” 없이 간결한 공통 plan 작성·자동 approve 후 진행한다. 사용자가 계획만 요청했거나 실제 의도·위험이 불명확하면 구현하지 않는다. 완료 승인 확인은 유지한다.
4. minor는 별도 검증 단계·문서를 요구하지 않되 변경에 맞는 최소 확인과 근거를 기록한다. 문구는 diff/내용 확인, 설정은 파싱/적용 확인, 동작 변경은 관련 기존 테스트 또는 재현으로 확인한다. 새 테스트·전체 테스트는 일괄 강제하지 않는다. 확인할 수 없으면 미확인 이유를 보고하며 검증됐다고 주장하지 않는다.
   - 동작 변경의 허용 범위: 요청 범위 안의 작고 가역적인 수정이어도 외부 동작이 바뀌면 fast-path를 일단 멈추고 실패비용을 재판정해 결과를 보고한다. 기존 minor 조건을 모두 충족하고 공개 계약·보안·외부 연동에 영향이 없을 때만 minor로 재개한다. 예상 밖 범위/계약 변경, 위험 상승, 판정 불확실이면 해당 구현을 진행하지 않고 major/critical로 전환하여 범위·필요 승인을 확인한다. 외부 동작 변경 자체를 항상 major로 승격하지도, 재판정 없이 허용하지도 않는다.
5. 승인해시는 명세 변경 감지이며 사용자 신원·이해·구현 적합성을 증명하지 않음을 명시한다. hook의 기본 경고, 선택 critical 차단, off/block 설정, 지원 도구/입력 경계는 실제 코드와 일치하게 설명한다.
6. 정의/참조 누락을 검출하는 검사와 사례별 정책 검토를 구분한다. 문자열 검사만으로 의미적 정합성이나 실제 에이전트 준수를 입증했다고 보고하지 않는다.
7. 전체 기존 단위 테스트와 추가된 관련 회귀 검증이 통과하고 source/dist Runtime이 일치한다. 기존 사용자 편집과 과거 완료·release 이력은 보존한다.
8. 대상 흐름의 사용자 개입마다 필요 이유와 기존 정보로 대체 가능한지를 `policy-audit.md`에 기록한다. 동일 범위·위험의 재질문/재승인, 에이전트가 판단 가능한 실행 방법 질문, 사용자에게 내부 기록 관리를 떠넘기는 요구를 제거한다. 필요한 질문은 관련 항목을 묶어 영향·권장안과 함께 제시한다. 이미 충족한 승인을 다시 받는 것은 보호가 아니며, 필요한 최초 승인·변경 승인·완료 판단은 유지한다.
9. 위험 재판정과 제한된 재시도는 에이전트가 수행한다. 기존 범위·위험 안이면 사용자 응답을 기다리지 않고 계속하며 결과는 다음 의미 있는 보고에 묶는다. 실제 사용자 결정·권한·중요 위험 변화가 있을 때만 해당 행동을 멈춰 확인한다. 중요한 실패·미확인 결과를 숨기지 않는다.

### 변경 불가 제약

- 기존 major 구현 승인·완료 승인, 선택 critical 보호를 약화하지 않는다. 승인해시·상태를 임의로 채우지 않는다.
- 정책 원본 통합 시 우선순위를 드러내며, 단순히 오래된 문서를 기준으로 최신 정책을 되돌리지 않는다.
- 구현 시 `.mpa/runtime/`를 수정하고 `release_manager.py sync-runtime`으로 dist에 반영한다. release·배포는 별도 명시 요청 때만 실행한다.
- 현재 `.mpa/runtime/core/agent_rules.md`와 dist 대응 파일의 사용자 편집(로그 규칙 등)을 보존한다.
- 소스 전용 검토 자료·평가 도구를 Runtime에 배포하지 않는다.

## 실행 계획 (Implementation Plan)

### 사전 조사

- core는 독립 비평의 자가 대체를 금지하지만 `inject/_agent_execution_priority.md`, `layer1_critique.md`, `workspace/memory/shared/architecture.md`는 허용한다.
- core의 minor 자동 승인과 detail/layer1_design의 선행 응답 대기는 충돌한다.
- core는 minor 검증 단계를 생략한다. 이를 “확인 없음”과 구분해야 한다.
- `code_gate.py`는 알려진 편집 도구·경로를 검사하며 기본 warn, 선택 critical 예외, 미상 경로 허용 등이 있다. 승인 명세 비교는 `plan_hash.py`가 담당한다.
- 앞선 검토에서 `python3 -m unittest discover -s tests -q`: 142 tests, OK. 이는 보완 전 단위 테스트 기준선이며 실제 호스트의 hook 실행 보장은 아니다.
- active 계획은 없었고 INDEX는 비어 있었다. hold 폴더도 없었다.

### 구현 단계

1. **정책·참조 지도 작성** — `policy-audit.md`에 대상 정책 ID, 정의 원본, 호출자, 상충 문구, 기대 행동을 기록한다. 이유: 일부 문구만 고치고 다른 진입점이 남는 오류 예방. core는 라우팅·경계, detail은 minor 상세, `_agent_execution_priority.md`는 비평/검증 실행 방식으로 책임을 나눈다.
2. **비평·검증 정책 정합화** — core의 최신 구분을 기준으로 실행 우선순위, critique/review, persona, memory의 충돌을 제거한다. 이유: 다른 문서를 읽어도 같은 폴백을 선택하게 한다. 지침에서 “서브에이전트=자동 격리”로 단정하지 않고 대화 상속 없이 필요한 파일만 전달하도록 명시한다.
3. **minor 경량 흐름 보완** — detail/design/implement/core/template에서 중복 선행 확인을 정리하고 최소 확인·미확인 보고를 일치시킨다. 구현 fast-path 자체에서 정본을 참조하게 한다. 이유: 단계 워커의 품질 확인 누락을 예방한다. 외부 동작 변경 시 중단·재판정·보고와 위험 상승 시 major/critical 전환을 유지한다.
4. **보장 범위·현재 메모리 정리** — 기존 가이드에 보장표를 작성하고 agent spec의 실행 주장은 코드 확인과 실제 호스트 확인을 구분한다. 이유: 문서의 약속이 코드보다 강해지지 않게 한다. 호스트에서 직접 확인하지 못한 항목은 미확인으로 남긴다.
5. **정책 회귀 검증** — 원본 참조 누락/오래된 금지 문구를 검출하는 제한된 정적 검사와 사례별 독립 검토를 추가한다. 이유: 정적 검사와 의미 검토의 한계를 구분하면서 재발을 줄인다. 기존 gate 테스트로 경고·차단 동작 불변을 확인한다.
6. **통합 검증·동기화·문서 반영** — source 확인 후 sync-runtime, 전체 단위 테스트, source/dist 대조, 독립 구현 검증을 수행하고 근거를 남긴다. 이유: 배포 후보의 정책과 source가 일치해야 한다. release는 만들지 않는다.

### 예상 조용한 결정

- 새 거대 정책 엔진을 도입하지 않고 기존 정의 파일과 참조를 정리한다.
- 과거 done/토론/immutable release는 당시 기록으로 보존하고 현재 권위 있는 문서만 정리한다.
- “최소 확인”은 별도 상태나 사용자 승인 관문으로 만들지 않는다.
- 단계 1의 정책 지도에 사용자 개입의 필요 이유·재사용 가능한 정보·에이전트 처리 가능 여부를 추가한다. 단계 3·4에서 중복 질문·수동 기록·과도한 내부 절차 안내를 줄이고 단계 5에서 아래 사례로 검토한다.
- 정책 테스트는 특정 문장 전체 일치보다 원본/참조와 알려진 충돌을 검사한다. 자연어의 모든 모순을 기계적으로 판별한다고 주장하지 않는다.

- 최소 확인이 다시 큰 체크리스트가 됨 → 단계 3에서 문구/설정/동작별 필요한 확인만 기록; 별도 문서·새 테스트 일괄 강제 금지.
- 서브에이전트에 전체 대화가 상속되어 독립 비평이 아님 → 단계 2·5에서 입력 계약 검토. 같은 모델의 상관된 오류까지 제거한다는 주장은 하지 않는다.
- 단위 테스트 통과를 실제 호스트 지원 증거로 오인 → 단계 4·6에서 확인 환경·미확인을 분리.

### 고정 사례표

구현 시 `policy-audit.md`에 각 사례의 로드 경로·인용 근거·확인 방법·결과(충족/실패/미확인)를 기록한다. 아래 정책 사례는 모두 문서 경로 대조가 충족돼야 완료하며, 실제 호스트 실행의 미확인은 별도 열로 표시한다.

| 사례 | 진입점 | 기대 행동 |
|---|---|---|
| 명확한 minor 수정 요청 | core → detail/design | 중복 확인 없이 계획·자동 approve, 최소 확인 |
| 계획만 작성 요청 | core → design | 계획 작성 후 구현 대기 |
| minor 구현 워커 직접 진입 | layer1_implement | core를 읽지 않아도 최소 확인 정본에 도달 |
| 새 기능의 독립 비평 | workflows/new_feature → critique | 사용자 소유 새 작업 생성 없이 격리 서브에이전트 사용 |
| 작업 결과 검토 | workflows/code_review → review | 독립 검증과 자가 검증 한계를 구분 |
| 비평 도구 없음/격리 불가 | critique → 실행 우선순위 | 비평 미완료 기록·생략 여부 사용자 확인 |
| 비평 호출 오류/빈 산출물 | 동일 | 일시 오류만 1회 재시도, 실패하면 같은 폴백 |
| 구현 검증 호출 실패 | review → 실행 우선순위 | 한계 고지·자가 검증, 확인 불가 항목 별도 기록 |
| 요청 안의 가역적 동작 수정 | implement → 실패비용 기준 | 중단·재판정·보고, minor 조건 충족 시 재개 |
| 예상 밖 공개 계약 변경/위험 상승 | 동일 | major/critical 전환·범위 및 승인 확인 |
| 확인 수단 없음 | minor 최소 확인 | 미확인 이유·남은 확인 보고; 통과 주장 금지 |
| 범위·위험이 같은 유효한 승인 존재 | major/minor 공통 | 기존 승인 재사용, 같은 확인 반복 금지 |
| 에이전트가 해결할 실행 방법 선택 | 모든 작업 흐름 | 근거를 기록하고 진행, 사용자에게 기술 판단 전가 금지 |
| 사용자 판단이 필요한 관련 질문 여러 개 | 설계/변경 확인 | 판단할 내용·영향·권장안을 묶어 질문 |
| 내부 재판정 결과 위험 변화 없음 | implement | 응답 대기 없이 재개, 다음 의미 있는 보고에 통합 |
| 기록·상태 정리 필요 | 모든 작업 흐름 | 에이전트가 갱신, 사용자에게 수동 파일 관리 요구 금지 |
