검토일: 2026-09-09. 설계 대화 없이 계획서·project_identity·architecture와 관련 Runtime 실제 문서를 대조했다. `contracts.md`는 존재하지 않는다. 원본 plan과 Runtime은 수정하지 않았다. 반례 탐색·조용한 결정 추출·의존성 맵 분석 방법을 적용했다.

### 🚨 실패 시나리오

#### F1 — 정합성 대상에서 실제 작업 진입점과 minor 실행 경로가 빠짐 (높음)

- 조건: 구현자가 계획의 수정 대상 파일 표를 완료하고, 새 기능 워커 또는 구현 워커가 자기 단계 파일을 읽는다.
- 근거: 계획의 완료 기준 1은 `core·inject·persona·현재 memory·가이드`만 열거하고 수정 대상에는 `workflows/`와 `inject/layer1_implement.md`가 없다. 그러나 `workflows/new_feature.md:45,84`는 독립 비평을 **새 스레드**에서 하도록 명시한다. `workflows/code_review.md:14,19,104` 역시 새 스레드를 강제한다. `inject/layer1_implement.md:125`는 minor이면 **아래만 처리**하도록 한 뒤 변경 항목 체크와 보고만 나열한다. 파일 줄 인용 하나는 변경된 동작을 확인했다는 증거가 아니다.
- 실패: 비평의 새 스레드 금지 정책과 새 기능 워크플로우가 계속 충돌하고, minor 최소 확인이 구현 fast-path에서 누락된다. architecture의 “작업 워크플로우가 정본” 및 “단계 워커는 자기 작업 워크플로우만 로드” 원칙 때문에 core 수정만으로 해결되지 않는다.
- 필요한 보완: 위 파일을 명시적 조사·수정 범위에 포함하고 `workflows/`·`core/session_protocol.md` 등 활성 진입점의 해당 정책 참조를 감사한다. minor fast-path 자체에 최소 확인 정본 참조와 확인/미확인 기록을 연결한다. 정상 사례도 메인 core를 읽은 경우뿐 아니라 단계 파일로 진입한 경우를 포함한다.

#### F2 — 서브에이전트 도구는 있지만 격리·실행을 완료하지 못하는 환경의 폴백이 미정 (중간)

- 조건: 도구는 제공되지만 대화 상속을 끌 수 없거나 호출 오류·빈 산출물로 비평이 완료되지 않는다.
- 근거: 완료 기준 2는 “서브에이전트로 수행하고, 불가하면”으로 표현하지만 검증 체크리스트는 “비평 도구 불가”만 다룬다. 단계 2는 대화 상속 없이 전달하도록 요구할 뿐 그 능력이 없는 호스트의 판정·처리를 정하지 않는다. 기존 `_agent_execution_priority.md:10`의 조건도 단순한 도구 사용 가능 여부다.
- 실패: 구현자가 도구 존재를 성공으로 간주하거나, 상속된 비평을 독립 비평으로 기록하거나, 무제한 재시도/임의 생략 중 하나를 조용히 선택한다.
- 필요한 보완: “사용 가능”을 필요한 입력 격리와 유효한 산출물 확보까지 포함해 정의한다. 격리 불가·호출 실패·산출물 누락 시 비평 미완료를 기록하고, 제한된 재시도 뒤 동일한 사용자 확인 폴백을 적용하는지 명시한다. 독립 구현 검증도 같은 실패 조건에서 자가 검증 폴백과 미확인 표시를 구분한다. 각 조건을 사례 검토에 추가한다.

### ⚠️ 숨은 가정 (파급효과 높은 순)

- F1의 가정: 상위 core와 설계 지침을 통일하면 실행 워커도 새 정책을 알게 된다. 현재 architecture는 단계 워커의 core 상시 로드를 요구하지 않으므로 이 가정이 틀리면 실행 행동은 그대로 남는다.
- F2의 가정: 서브에이전트 도구의 존재가 컨텍스트 격리와 비평 완료를 뜻한다. 실제 도구 옵션·실패 상태가 다르면 독립성 보장이 사라진다.

### ❓ 미해소 비가시적 위임

#### F3 — “동작 변경도 minor 최소 확인”과 기존 외부 동작 변경 시 fast-path 중단의 경계 (중간)

- 근거: 완료 기준 4는 minor의 “동작 변경은 관련 기존 테스트 또는 재현”을 제안한다. 반면 `inject/layer1_implement.md:138`은 “구현 중 외부 동작·아키텍처·계약 변경이 발생하면 fast-path를 중단하고 major 전환 여부를 사용자에게 보고”하도록 한다. 계획의 단계 3은 위험 상승 시 major 전환만 언급한다.
- 선택이 필요한 지점: 요청 범위 안의 작고 가역적인 사용자 가시 버그 수정도 외부 동작 변경이므로 항상 전환 검토할 것인가, 아니면 예상 밖 동작/계약/위험 변화만 전환 조건인가. 지금은 구현자가 둘 중 하나를 정하게 된다.
- 필요한 보완: minor의 동작 변경 허용 범위와 중단 기준을 명세한다. “요청 범위 내 가역적 버그 수정”, “예상 밖 공개 계약 변경”, “실패비용 상승”에 대한 기대 행동을 분리해 사례표에 기록한다. 기존 major/critical 보호를 유지하면서 전환 기준을 바꾸는지 설명한다.

### 🔧 구조적 문제

- F1은 단순 파일 목록 누락을 넘어 완료 판정 범위 문제다. 단계 1의 정책 지도에서 발견한 활성 호출자를 모두 완료 기준 1과 단계 5의 검토 대상에 반영해야 한다. 목록 밖 활성 워크플로우에서 충돌을 발견했을 때 수정 범위에 포함하는 원칙을 둬야 한다.
- 정적 검사와 독립 사례 검토를 구분한다는 기준만으로 검토의 충분성을 판정할 수는 없다. 위 F1~F3의 조건·로드 진입점·기대 행동·확인 방법을 사례표로 고정하고, 각 사례를 검토 완료 또는 미확인으로 기록해야 한다. 미확인 항목을 모두 통과한 것으로 합산하지 않는다.
