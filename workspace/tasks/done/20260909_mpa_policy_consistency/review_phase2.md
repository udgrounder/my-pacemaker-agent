# 독립 구현 검증 2차

## 검토 범위와 방법

- 승인된 plan.md, 수정 전 review_phase1.md, changelog.md를 현재 Runtime 파일 및 변경 diff와 대조했다. 1차 지적을 구현자 설명만으로 유지하거나 폐기하지 않았다.
- core/detail, 독립 실행 priority, critique/design/implement/review/discovery, workflow, discovery 분류 지침, guidebook, agent-specs의 보장 범위, 현재 architecture/direction 및 정책 테스트를 확인했다.
- 이 검토는 저장소 문서의 정책 경로와 제한된 코드·테스트 대조다. 실제 호스트의 이벤트 호출·참조 로딩·서브에이전트 격리·재시도 동작을 실행 검증한 것은 아니다.

## 1차 지적 재판정

### F1 — 해결 확인

- 현재 `inject/layer1_discovery.md:88`은 신규 태스크만 있는 경우에도 결과 확인 전에는 `테스트 중`, 확인 후에는 `검토 완료`를 유지하며 명시적 완료 승인 뒤에만 `완료 승인`과 done 이동을 지시한다.
- 같은 파일의 순서 안내와 세션 종료 조건도 신규 등록을 완료 승인으로 취급하지 않으며, 유효한 기존 완료 확인은 재사용한다. `layer1_review.md`의 종료 규칙 및 core의 완료 권한과 일치한다.
- 1차 지적의 두 직접 이동 문구가 제거되었고, 신규 태스크 등록만으로 원래 작업을 종료하는 경로는 해당 지침에서 해소됐다.

### F2 — 해결 확인

- 현재 `core/agent_rules_detail.md:48`은 직전 명시적 승인 이력과 승인 당시 명세를 현재 명세·위험과 대조해 동일성이 증명될 때만 정상 approve로 기록을 복구한다. “이미 유효한 승인을 다시 묻지 않는다”가 명시돼 있다.
- 당시 승인된 명세를 복원할 수 없거나 차이가 있으면 기존 불명확/명세 변경 경로를 따른다. 직접 해시 입력도 허용하지 않는다. 동일 승인 재확인을 제거하면서 새로운 승인을 임의 생성하지 않는 경계가 보존됐다.
- 현재 기존 plan을 실제로 마이그레이션하거나 승인 복구한 것은 검증하지 않았다. 이것은 문서상 복구 절차의 재판정이다.

## 검토 중 추가 지적과 재검증

### F3 [P2] 팀 workflow의 새 스레드 단계 표기 — 수정 후 해결 확인

- `workflows/team_collaboration.md:3`은 단계 전환만으로 사용자에게 새 작업 생성·재승인을 요구하지 않는다고 하지만, 같은 파일 `:37`의 팀 Layer 0과 `:57`의 팀 Layer 2 흐름은 여전히 `스레드: 🆕 새 스레드`로 표시돼 있다.
- 특히 개인 Layer 1 이후 팀 Layer 2로 넘어가는 순서도는 별도의 사용자 요청이나 선택 조건 없이 새 스레드를 다음 단계 자원으로 제시한다. `core/session_protocol.md:56`의 inject는 단계 지침이며 새 작업 생성 명령이 아니라는 원칙 및 guidebook 7.2의 현재 작업에서 체크포인트 지침 로드와 해석이 갈릴 수 있다.
- 상단 정본 참조가 있으므로 무조건 새 작업을 생성해야 한다고 단정할 수는 없다. 그러나 실제 단계 표기가 같은 문서의 경계를 흐려 사용자 부담을 재도입할 수 있다.
- 권장: 팀 Layer 0/2를 현재 작업에서 해당 지침을 읽는 방식으로 표시하거나, 새 사용자 작업은 명시 요청이 있을 때의 선택임을 분명히 한다.
- 지적 전달 후 현재 파일을 다시 읽었다. 팀 Layer 0은 팀 대표의 현재 작업에서 단계 지침 로드, 팀 Layer 2도 현재 작업에서 체크포인트 지침 로드로 수정됐다. 정책 테스트의 금지 목록에 기존 `스레드: 🆕 새 스레드` 표기도 추가됐다. 9개 정책 테스트 및 source/dist parity를 다시 확인했으며 통과했다. 따라서 F3도 남은 결함으로 유지하지 않는다.
