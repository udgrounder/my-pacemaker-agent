# 작업 계획서: 전제에 근거한 설계 질문과 가정 관리

## 요구사항 명세

### 요청 기준
사용자 요청: “좋아, 이슈 채택하고 판단한 공통 원칙을 MPA에 반영할 계획서 작성해줘.”
파생 출처: campingtalk-proj의 원천 데이터 단위 확인 전 가정 기반 업무 질문 방지 이슈.
채택 이슈: [보존된 채택·구현 결론](changelog.md). 원본 20261116_unverified_source_granularity_assumptions.md는 처리 완료 후 2026-11-23 사용자 요청으로 삭제했다.

### 목적
확인되지 않은 예외를 실제 업무의 전제로 다루어 질문·요구사항·설계를 연쇄 확대하는 행동을 줄인다. 기존 자료와 사용자 설명으로 업무를 파악하고 실제 결정이 필요한 질문에 집중하면서 중요한 위험의 반례 탐색을 유지한다.

### 범위·제외 범위
적용 범위는 MPA 공통 Runtime의 설계·인터뷰·분석 기법에 질문 전 전제 확인, 미확인 가정의 연쇄 확대 방지, 전제 변경 시 기존 답변·결정·설계 재검토 원칙을 반영하는 것이다. 중요한 가상 위험의 검토를 유지하며 source/dist를 동기화한다.

제외 범위는 개별 프로젝트의 업무 규칙·데이터 모델 설계와 프로젝트 자산 변경, 새 hook·강제 입력 양식·가정별 승인 절차·설정 schema 추가, 릴리즈 생성·설치 대상 배포다. 실제 모델의 지속적 준수 보장은 범위 밖이다.

### 완료 기준
- C1. 관련 문서·데이터 계약·사용자 설명에서 질문의 전제를 먼저 확인하고, 자료로 확인할 수 없는 핵심 사실만 사용자에게 묻는다. 전수 조사나 모든 질문의 증명 의무로 확대하지 않는다.
- C2. 확인된 사실·미확인 가정·현재 범위 밖 가능성을 구별한다. 미확인 예외를 확정 요구사항으로 취급하거나 그 위에 후속 질문·테이블·처리를 연쇄 확정하지 않는다.
- C3. 전제가 바뀌면 그 전제에 의존한 기존 답변·결정·설계의 적용 범위를 재검토한다. 유효한 결정은 유지하고 사용자 의도·위험을 바꾸는 변경에는 기존 승인 절차를 적용한다. 철회된 내용은 기존 changelog 규칙으로 보존한다.
- C4. 가상 반례 탐색을 유지한다. 발생 여부가 미확인이어도 영향이 큰 위험은 가정·영향·현재 범위와의 관련성을 밝혀 검토하며, 필요한 사용자 결정은 기존 의도·위험 기준에 따라 질문한다.
- C5. 일반 설계·인터뷰·분석 기법 직접 사용 경로가 일치하고 기존 질문 최소화·가치/기술 결정·승인·이력 규칙과 충돌하지 않는다.
- C6. 정상·실패·경계 사례 대조, 관련 기존 테스트, diff 검사와 source/dist 일치 결과 및 한계를 기록한다.

### 사용자 결정
이슈를 채택하고 앞선 검토의 공통 원칙으로 계획서를 작성했다. 프로젝트 업무 규칙은 해당 프로젝트에 남긴다. 최초 요청은 계획서 작성까지였으며, 프로젝트 특화 표현을 일반화한 뒤 사용자가 “수정한 계획서대로 구현 진행해줘”로 현행 계획의 구현을 명시 승인했다.

### 변경 불가 제약
유효한 기존 답변을 반복 질문하지 않는다. 반례 탐색과 중요 위험 고지를 유지한다. 승인해시·상태 전이·완료 확인 절차를 변경하지 않는다. 기존 사용자 변경분을 보존하고 dist를 직접 편집하지 않는다. 대상 프로젝트 자산과 immutable release는 변경하지 않는다.

### 에이전트 가정
- 사건의 사실관계는 수집 이슈의 사용자 정정 기록에 근거한다. 대상 프로젝트 업무 문서를 별도 열람해 재검증하지 않았으며 개별 업무 사실이나 데이터 모델에 대한 새 판단을 추가하지 않는다.
- 지침과 사례 대조는 절차상 공백을 줄이는 수단이다. 문서·테스트 통과가 실제 모델의 행동 준수를 보장하지 않는다.
- 공통 원칙과 적용 절차를 나누고 분석 기법 직접 사용 경로도 연결하면 중복과 누락을 줄일 수 있다.

### 결정 대기 항목
없음. 현행 계획의 구현 승인을 받았다.

### 작업 분류 판단 근거
문서 diff로 복구 가능하며 보안·외부 연동·영구 데이터 변경은 없다. 다만 여러 프로젝트의 질문·반례 처리에 영향을 주고 공통 규칙·단계 절차·분석 기법 사이의 배치와 과잉 제한 방지를 설계해야 한다. minor의 “구현 전 설계 결정이 필요 없음”을 충족하지 않아 major로 분류한다.

## 선택 문서
추가 역할 문서 없음. 제한된 관심사의 실행·검증 기준을 이 plan에서 관리한다. 구현·검증 시에는 필요한 changelog와 기존 review 산출물을 사용한다.

### 예상 조용한 결정
고정 라벨·표·새 문서를 강제하지 않고 문맥에 맞는 자연어로 사실·가정·범위를 구별한다. 자료 부족만으로 설계 전체를 중단하지 않고 결과에 영향을 주는 핵심 사실만 최소 확인한다. 새 용어·상태·자동 차단을 만들지 않는다. 판단은 지침으로 유지한다.

### 반례
- 사실 확인을 강조한 결과 미확인 위험을 모두 무시할 수 있다. → C4를 인터뷰·반례 지침에 연결하여 영향 큰 가상 위험을 계속 검토한다.
- 자료 확인을 사용자 질문으로 전부 떠넘길 수 있다. → C1은 에이전트의 기존 자료 확인을 먼저 요구한다.
- 전제가 달라졌다는 이유로 모든 답변을 폐기할 수 있다. → 영향받는 답변·설계만 재검토하고 유효한 결정은 유지한다.
- 인터뷰에만 반영하여 일반 설계·분석 직접 사용에서 재발할 수 있다. → 공통 원칙과 분석 출력 활용 기준까지 연결한다.

### 생략 항목과 사유
UI·외부 기술 조사·새 hook·설정 변경은 자연어 지침 보완 범위와 무관해 생략한다. 역할 문서 분리는 이 계획서에서 실행·검증 기준을 관리할 수 있어 생략한다. 사용자 흐름이 바뀌지 않아 guidebook 개정은 계획하지 않는다. 이력 관리 규칙은 기존 정본을 참조한다.

## 실행 계획
1. **지침 반영:** 승인 뒤 현재 파일·참조 관계를 다시 확인하고 위 5개 Runtime 파일에 소유별 원칙을 반영한다. 이유: 일반 설계·인터뷰·분석 직접 사용의 누락과 중복을 피한다.
2. **정합성 검증·동기화:** 아래 사례와 C1~C5를 대조하고 관련 기존 테스트·diff 검사 후 sync-runtime으로 dist를 동기화하여 파일 목록·내용 일치를 확인한다. 이유: 문구 존재뿐 아니라 판단 기준과 기존 동작 보존을 확인한다.
3. **독립 구현 검증·결과 정리:** 기존 1차·2차 격리 검증으로 기준 대비 구현 및 변경 이력을 대조하고 발견 사항을 반영한다. 실행 정본의 실패 처리·미확인 표시를 따르고 결과·한계를 기록한다. 이유: 구현 의도와 실제 지침의 차이를 확인한다. 사용자 확인 전 done으로 이동하지 않는다.

## 검증 기준
실제 모델 행동 실험과 문서상 사례 대조를 구분하며, 아래 사례는 지침을 읽고 판단 경로를 대조하는 검증이다.

| 사례 | 기대 판단 |
|---|---|
| 질문의 전제와 상충하는 사실이 기존 자료에 명시됨 | 자료와 상충하는 가정으로 후속 질문이나 추가 설계를 확정하지 않는다. |
| 설계 결과를 좌우하는 핵심 사실이 자료에 없음 | 해당 사실만 최소 확인하고 미확인 전제에 의존한 후속 질문을 쌓지 않는다. |
| 사용자가 현재 범위 밖 예외로 설명함 | 현행 요구사항으로 승격하지 않고 후순위 가능성으로 구별한다. |
| 발생 여부 미확인의 중대한 데이터 손실 위험 | 가상 위험임을 밝혀 영향·관련성과 필요한 결정을 검토한다. |
| 전제 A에서 받은 답변 뒤 B가 확인됨 | A에 의존한 답변·설계만 재검토하고 철회 내용은 이력으로 보존한다. |
| 인터뷰 없이 일반 설계·분석 기법 직접 사용 | 미확인 예외를 실제 결정 공백으로 자동 승격하지 않는다. |
| 질문·가정이 없는 단순 작업 | 새 확인 단계·고정 서식을 추가하지 않는다. |
| 코드 반례 탐색 | 입력 누락·실패·동시성 등 기존 탐색을 유지한다. |

관련 기존 테스트는 test_policy_consistency.py, test_structure_loading.py, test_task_documents.py, test_contract_reference.py에 대해 각각 python3 -m unittest discover -s tests -p '<파일명>'으로 실행한다. 문구를 복제하는 새 테스트는 만들지 않는다.
git diff --check, Runtime source/dist 상대 파일 목록·내용 일치, 문서 참조와 기존 승인·이력 규칙의 충돌 여부를 확인한다. 기존 미커밋 변경분을 구별하여 기록하고 덮어쓰지 않는다.
계획서 연결은 task_documents.py inspect <plan> --before-approval로 확인하며 구현 승인 뒤에는 현행 명세 해시 검사를 사용한다.
