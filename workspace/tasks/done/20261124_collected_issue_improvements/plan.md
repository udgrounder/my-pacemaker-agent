# 작업 계획서: 수집 이슈 4건 반영

## 요구사항 명세

### 요청 기준
최초 요청: “2번은 그 범위로 하고, 3건 모두 채택해서 계획 세워줘.” 2번은 소프트웨어 시스템의 개발·수정·검증 시 로그 보안 주의사항으로 한정한다.
추가 요청: “기록 위치를 명확히 하는 범위로 채택하고, 기존 계획에 추가해줘.” Layer 2 이슈는 점검 결과·미해결 항목의 저장 위치 명확화로 한정한다. 이후 사용자 “계획 승인할게. 4건 모두 구현해줘.”로 전체 구현을 승인했다.

### 목적
작업 디렉터리에 따른 hook 오판을 없애고, 개발 로그의 인증 정보 노출과 공용화 문서의 운영 준비 절차 누락을 예방한다. Layer 2에서는 INDEX 날짜 마커와 점검 결과·미해결 항목의 저장 위치를 구분한다.

### 범위·제외 범위
- A. Claude·Codex의 hook 실행 명령, 프로젝트 루트·대상 경로 판정, 기존 MPA hook 등록의 안전한 갱신과 회귀 검증.
- B. 소프트웨어 개발·수정·검증 시 애플리케이션·서비스·스크립트 등의 로그에 인증 정보·비밀값을 평문으로 기록하지 않는 공통 원칙 및 관련 변경의 구현·검증 점검.
- C. 공용화·모듈 이동 작업에서 새 소비자가 도입·운영하는 데 필요한 준비 절차와 실제 사용하는 외부 서비스의 식별을 설계·문서 검증에 반영.
- D. Layer 2 점검 결과·미해결 항목의 저장 위치와 INDEX에 기록할 날짜 마커의 내용 경계를 명확히 한다.
- source Runtime과 배포본 동기화 및 관련 설치 안내 갱신까지 포함한다.
- 일반 대화·일반 문서 작성의 보안 정책 확대, 프로젝트별 마스킹 구현, 새 자동 검사 hook 일괄 도입, 원천 프로젝트 문서 수정, 릴리즈 생성·외부 프로젝트 배포는 제외한다.
- Layer 2 마커 폐지·기록 주기나 완료 판정 변경, 과거 INDEX 마커·점검 보고서 일괄 이관, 설치 프로젝트 직접 수정은 D의 범위에서 제외한다.

### 완료 기준
- A1. 프로젝트 루트와 하위 작업 폴더에서 동일한 파일 요청·작업 상태에 대해 code_gate가 같은 허용·경고·차단 결과를 낸다. 기존 warn/block/off 및 선택 critical 승인·해시 보호 의미를 유지한다.
- A2. session_start·turn_end도 루트와 하위 폴더에서 동일한 작업을 식별한다. Git 유무·공백 경로·하위 Git 저장소에 의해 소유 프로젝트를 잘못 선택하지 않는다.
- A3. 신규 hook 명령이 해당 Runtime을 실행하며, 설치 도구 재실행은 식별 가능한 구형 MPA 명령만 안전하게 갱신한다. 사용자 hook·혼합 설정·알 수 없는 사용자 수정 명령은 보존한다.
- B1. 개발 시스템의 로그 보안 원칙과 적용 조건이 공통 규칙·구현·검증 지침에 일관되게 반영된다. 특정 언어·HTTP에 한정하지 않고 프로젝트의 마스킹 방식은 존중한다.
- B2. 관련 로그·외부 호출 코드를 신설·수정할 때 정상·실패 경로의 노출 여부를 확인한다. 일반 대화·문서와 무관한 작업에 일괄 점검·새 도구 설치를 강제하지 않는다.
- C1. 공용화·이동 작업의 완료 기준에 새 소비자의 도입 가능성이 포함되고, 인프라 리소스·권한·배포 설정·확인·장애 대응 중 해당하는 절차의 누락을 검증한다.
- C2. 상세 운영 문서로의 유효한 링크를 허용하고 중복 복제를 강제하지 않는다. 현재 사용하는 외부 서비스는 구체적으로 식별하고, 대안 서비스 비교는 혼동 가능성이 있는 경우에만 요구한다.
- D1. Layer 2 실행 지침과 상세 규칙에 INDEX에는 `[Layer 2 완료] YYYY-MM-DD` 한 줄만 기록하며 점검 계기·정정 내역·미해결 메모를 넣지 않도록 명시한다. 기존 완료 조건·주기·과거 마커 보존 정책을 유지한다.
- D2. 점검 결과·미해결 항목의 기본 저장 위치를 `workspace/exploration/checkpoints/YYYYMMDD_<주제>.md`로 명시한다. 프로젝트의 명시적 기록 위치가 있으면 우선하고 같은 점검의 기존 결과 문서는 재사용한다. 미해결 항목은 결과 문서에 남기며 방법론 개선만 local `workspace/issues/`로 연결한다.
- D3. 결과 문서의 저장 위치·미해결 상태·관련 issue/작업 연결을 보고한 뒤 기존 완료 절차를 따른다. 결과 저장 실패 시 INDEX로 내용을 대신 옮기거나 새 완료 마커를 쓰지 않는다.
- X1. 관련 source 테스트와 Runtime/source-dist 정합성이 통과하고, 확인하지 못한 호스트 실제 연동은 미확인으로 구분한다.

## 설계 기준

### A. hook 실행과 루트 판정
- `.mpa/runtime/hooks/`에 공통 루트 판정 helper를 두고 code_gate·session_start·turn_end에서 사용한다. 스크립트 위치의 실제 Runtime 소유 루트를 우선 검증하며, 다른 프로젝트를 가리키는 환경변수나 Git 최상위를 무조건 신뢰하지 않는다. 환경변수·cwd 상위 탐색은 소유 Runtime과 일치 여부를 검증하는 보조 근거로 사용한다.
- 요청 파일의 상대 경로는 입력 cwd(없으면 프로세스 cwd) 기준으로 먼저 절대화한 뒤 소유 프로젝트 루트에 상대화한다. 프로젝트 상태 조회는 소유 루트 기준으로 수행한다. Bash mv 감시도 실행 cwd와 작업 상태 루트를 분리한다.
- 루트 식별 불가·다른 프로젝트·루트 밖 경로는 정상 프로젝트인 것처럼 허용 prefix를 적용하지 않는다. 기존 fail/warn 정책과 선택 critical 보호를 유지하는 오류 처리를 설계·검증한다.
- Claude 명령의 프로젝트 경로를 따옴표로 보호한다. Codex는 Git 최상위 탐색만으로 소유 프로젝트를 정하지 않고 가장 가까운 유효 Runtime과 실제 실행 스크립트가 일치하도록 한다. 비 Git·중첩 저장소도 지원한다.
- hook 명령 wrapper는 호출된 작업 폴더를 바꾸지 않고 식별한 Runtime 스크립트의 절대 경로를 실행한다. 입력 cwd가 없을 때도 원래 프로세스 cwd로 상대 파일을 해석할 수 있어야 한다. 환경변수로 원래 cwd를 새로 우회 전달하는 프로토콜은 추가하지 않는다.
- install.py는 정확히 식별 가능한 기존 MPA 생성 명령만 교체한다. 사용자 entry·matcher·추가 필드와 사용자 hook 순서를 보존하고, 손상 JSON·알 수 없는 수정 명령은 보존·안내한다. 재실행 시 중복 생성하지 않는다.
- 설정 저장은 임시 파일 검증·교체 등 원본 보존이 가능한 방식으로 수행한다. 저장 실패 시 기존 파일이 그대로 남아야 하며 실패를 보고한다. 기존 파일 권한을 유지하고, 알 수 없는 사용자 변경을 덮는 설치 전체 transaction이나 광범위한 설정 재작성은 도입하지 않는다.
- plan_hash.py는 전달받은 plan 경로를 처리하는 도구이므로 이번 루트 helper 적용을 일괄 강제하지 않는다. hook과의 승인·해시 연동만 회귀 검증한다. source에서 발견되지 않은 구형 config.toml을 새로 만들거나 대상 프로젝트에서 탐색·수정하지 않는다.

#### 루트·경계 오류의 기대값
| 조건 | warn | block | off |
|---|---|---|---|
| 검증된 소유 루트가 없어서 상태 조회 불가 | 경고·exit 0, critical 검사 미확인 명시 | 진단·exit 2 | 기존처럼 미검사·exit 0 |
| 환경변수·입력 cwd가 다른 프로젝트를 가리키나 스크립트 소유 루트는 유효 | 다른 프로젝트 상태를 선택하지 않고 소유 루트 판정 | 동일 | 미검사·exit 0 |
| 경계 밖 파일 요청, 소유 루트 유효 | workspace 허용 prefix를 적용하지 않고 소유 루트의 일반 소스 판정 | 동일 | 미검사·exit 0 |
| 소유 루트의 선택 critical 승인·해시 오류 | 기존처럼 exit 2 | 기존처럼 exit 2 | 기존처럼 미검사·exit 0 |

경계 밖 파일 요청도 선택 critical 검사를 생략하지 않는다. 루트 미확인 warn은 검사 통과의 증거가 아니며 별도 진단을 남긴다. session_start·turn_end의 루트 식별 실패는 작업 없음으로 위장하지 않고 진단 후 exit 0으로 종료해 새 종료 차단을 만들지 않는다.

### B. 개발 로그 보안
- core/agent_rules.md의 소스 로그 규칙에 개발 시스템이 남기는 로그의 인증 정보·비밀값 평문 기록 금지를 명시한다. 로그 비활성화·민감 필드 제외·마스킹 등 구체 수단은 프로젝트 규칙을 따른다.
- layer1_implement.md와 layer1_review.md에는 관련 코드 변경 시에만 적용하는 짧은 확인 항목을 둔다. 헤더뿐 아니라 URL·본문·예외·오류 응답을 통한 노출도 확인한다.
- Node.js의 기존 민감 정보 로그 금지와 정합성을 유지한다. 모든 도메인 memory나 자동 검사기를 새로 만들도록 요구하지 않는다.

### C. 공용화·이동 문서
- layer1_design.md에 새 소비자의 도입·운영 준비를 해당 작업의 완료 기준으로 잡도록 추가하고, layer1_review.md에서 같은 관점의 누락을 대조한다.
- 특정 원천 프로젝트·클라우드 이름을 공통 합격 조건으로 쓰지 않는다. 적용 가능한 준비 절차, 실제 구현의 서비스 식별, 유효한 운영 문서 연결로 일반화한다.

### D. Layer 2 점검 기록 위치
- core/agent_rules_detail.md의 「실제 점검 완료 기록」과 inject/layer2_checkpoint.md의 산출물·종료 절차를 맞춘다. 완료 날짜 한 줄은 INDEX, 점검 계기·정정 내역·결과·미해결 항목은 점검 결과 문서로 구분한다.

## 실행 계획

### 사전 조사
이전 검토에서 루트 요청은 exit 0, nested 요청은 warn 오경고·block exit 2를 확인했다. 현재 install.py의 실행 경로 보완만으로는 입력 cwd 오판이 해결되지 않는다. 기존 등록 감지는 갱신을 생략한다. 구현 전 현재 코드·테스트 fixture·설정 보존 계약을 재확인한다.

1. **hook 루트·경로 해석과 설정 갱신 구현:** 원래 실행 cwd·소유 루트·요청 파일의 해석 계약을 먼저 고정한 뒤 A 기준을 구현하고 실제 임시 프로젝트 Runtime을 사용하는 fixture로 기존 및 신규 동작을 확인한다. 생성 명령과 helper의 결합 및 설정 저장 실패 시 원본 보존까지 확인한다. 이유: 작업 상태 오판과 승인 보호의 회귀를 먼저 제거한다.
2. **개발 로그 보안 규칙 반영:** B 기준을 공통·구현·검증 지침에 반영한다. 이유: 로그 노출 방지 의무와 프로젝트별 수단의 경계를 일치시킨다.
3. **공용화 문서 검증 반영:** C 기준을 설계·검토 지침에 반영한다. 이유: API 사용법만으로 문서 완료를 판정하는 누락을 막는다.
4. **Layer 2 기록 위치 명확화:** D 기준에 따라 INDEX 한 줄과 점검 결과 문서의 역할·경로·미해결 항목 연결을 명시한다. 이유: 날짜 마커를 점검 로그로 확대 해석하는 재발을 막는다.
5. **통합 검증·동기화·문서 갱신:** 관련 단위 테스트, 전체 source 테스트와 source/dist parity를 확인한다. 이유: helper 추가와 공유 지침 수정의 배포 누락·교차 회귀를 확인한다.

실패비용 critical이므로 각 구현 단계 결과를 보고·확인한다. 사용자가 4건 모두 구현하도록 승인한 범위에서는 테스트와 결과 대조를 거쳐 연속 수행하고 같은 실행 승인을 반복 요청하지 않는다. 범위·위험 변경은 기존 승인 절차를 따른다.

### 예상 조용한 결정
- 같은 source와 공유 검토 지침을 수정하므로 네 이슈를 한 작업으로 묶되 완료 기준 A/B/C/D를 분리한다.
- 마스킹 전용 hook 신설과 서비스 비교 설명 일괄 강제를 선택하지 않는다. 원칙의 적용 의무와 검증 수단 선택을 구분하기 위해서다.

### 반례
- 실행 명령만 고친 경우 입력 cwd 오판이 남는다 → helper와 경로 해석 및 실제 생성 명령 회귀를 함께 검증한다.
- 입력 상대 파일을 프로젝트 루트에 바로 붙이면 다른 파일을 판정한다 → 실행 cwd 절대화 후 소유 루트에 상대화한다.
- 중첩 Git·다른 프로젝트 환경변수·symlink가 외부 작업 상태를 선택한다 → 소유 Runtime 일치와 경계 검증을 포함한다.
- 재설치가 사용자 hook까지 변경한다 → 알려진 관리 명령만 제한적으로 교체하고 혼합·사용자 수정 명령 보존을 확인한다.
- 명령 wrapper의 cd 뒤 JSON cwd가 없으면 상대 요청의 의미가 바뀐다 → wrapper는 cwd를 보존하고 실제 생성 명령으로 nested·cwd 누락·상대 경로 조합을 실행한다.
- 설정 저장 중 실패하면 병합이 정확해도 사용자 hook이 손상된다 → 원본 보존 저장과 실패 주입·기존 바이트/권한 대조를 수행한다.
- 문서 검증이 모든 작업에 운영 체크리스트를 강제한다 → 공용화·이동 작업 및 해당되는 준비 절차로 조건을 제한한다.
- 호스트가 hook 자체를 실행하지 않는다 → 단위/명령 검증으로 호스트 통합까지 보장하지 않으며 실제 확인하지 못한 범위를 보고한다.
- Layer 2 결과 저장에 실패하거나 같은 날 기존 문서가 있다 → INDEX로 로그를 대신 기록하지 않고, 같은 점검은 기존 문서를 재사용하며 별도 점검은 구분된 경로에 저장한다. 저장 실패 시 새 마커를 쓰지 않는다.
- 미해결 항목을 모두 방법론 issue로 만든다 → 결과 문서에 우선 기록하고 기존 자산 분류·관련 작업/issue 연결만 적용한다.

## 운영 시 안내 사항
실제 설치 프로젝트의 구형 hook 등록은 Runtime 교체만으로 갱신되지 않는다. 최신 Runtime을 별도 배포한 뒤 install.md의 `--repair-hooks --dry-run`으로 범위를 확인하고 명시적으로 hook 설정을 갱신한다. 사용자 수정 명령은 보존·수동 확인 대상으로 남는다. 실제 Claude·Codex 호스트의 자동 호출은 그 환경에서 확인한다. 이번 작업은 source 구현·배포본 동기화까지 수행했으며 릴리즈 생성·설치 프로젝트 배포는 하지 않았다.

Claude·Codex의 기본 설치에서 `PreToolUse`는 편집 도구에만 연결되므로 Bash `mv` 감시는 자동 호출되지 않는다. 기존 검증에서는 생성된 hook 명령에 Bash 입력을 직접 전달해 감시 동작을 확인했다.
