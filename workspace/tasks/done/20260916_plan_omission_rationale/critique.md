## 비평 결과

### 🚨 실패 시나리오
- 시나리오 1: 작성 에이전트가 선택적 섹션을 통째로 삭제하거나 `생략 사유: 불필요`만 남겨도 → 계획은 템플릿·절차 문구와 정책 검토만 바꾸며, 저장된 plan.md를 거부하거나 누락을 탐지하는 hook/validator를 추가하지 않는다. 따라서 자기 점검과 구현 후 검토를 거치지 않는 작성 경로에서는 새 “의무”가 실행 가능한 규칙이 되지 않는다. 근거: 완료 기준은 사유를 “의무화”하지만 수정 대상은 템플릿·절차·정책 테스트뿐이고, 반례의 대응도 `layer1_review.md`의 확인 추가에 한정된다.
- 시나리오 2: 템플릿의 어떤 제목이 “선택적 섹션”인지 작성자마다 다르게 해석하는 경우 → 한 작성자는 제목과 사유를 남기고 다른 작성자는 같은 성격의 하위 섹션·표를 삭제하여, major/minor 간 의미가 달라진다. 근거: 1단계가 적용 대상을 “전수 식별”한다고만 하며 그 결과 표나 확정 목록을 수정 대상·완료 기준으로 남기지 않는다. 동시에 범위는 “섹션 단위”라고 제한하면서 표 내부 빈 칸은 제외한다.
- 시나리오 3: source 규칙은 갱신됐지만 `sync-runtime` 결과가 source와 문구상만 같고 실제 설치본에서 생성되는 plan의 동작이 달라지는 경우 → source/dist 문자열 parity와 기존 정책 테스트는 통과해도, dist Runtime을 사용한 major/minor plan 생성·생략 검증이 없어서 배포본의 실제 적용 실패를 발견하지 못한다. 근거: 검증 체크리스트는 “양쪽 규칙과 회귀 테스트”의 일치만 요구하며, 생성된 산출물 fixture나 dist 경로 실행 검증을 명시하지 않는다.

### ⚠️ 숨은 가정 (파급효과 높은 순)
- 가정 1: 템플릿·절차의 자연어 지시와 사후 검토만으로 “의무”를 일관되게 강제할 수 있다 / 틀렸을 때: 누락된 사유가 승인 전·후 모두 남아 규칙의 핵심 목적(판단 추적성)이 달성되지 않는다. 근거: 계획은 `plan_hash.py` 호환성만 조사 대상으로 두고, 사유 존재·내용을 기계적으로 검사할 책임 주체를 정하지 않는다.
- 가정 2: `생략 사유`가 요구사항 명세 checksum에서 제외되어도 충분히 추적 가능하다 / 틀렸을 때: 승인 뒤 에이전트가 사유나 섹션 적용을 바꿔도 `renew-spec` 없이 승인 대상의 실질적 판단 근거가 달라질 수 있다. 근거: 계획은 해시 영향이 없을 것이라는 가정을 두면서, 사유가 요구사항 명세 안과 밖 중 어디에 기록되어 승인 대상이 되는지는 정하지 않는다.
- 가정 3: 한 줄이라는 형식이 작성 부담을 제한하면서도 판단 근거의 최소 품질을 보장한다 / 틀렸을 때: 사실과 조건을 검증할 기준이 없어 `해당 없음`의 변형이나 검증 불가능한 문구가 통과한다. 근거: “조건과 작업의 사실”을 쓰라고만 하고, 허용·불허 예시, 판정 규칙, 실패 시 처리 방식을 계획하지 않는다.
- 가정 4: 과거 plan은 게이트 입력이 아니며 새 규칙과 혼재해도 소비자가 구분할 수 있다 / 틀렸을 때: 기존 plan을 읽는 review/audit 도구나 사람이 과거 형식을 규칙 위반으로 오인하거나, 반대로 신규 plan의 누락을 과거 호환성으로 넘길 수 있다. 근거: 과거 소급 수정은 제외하지만 식별 기준·검사 적용 시작점·호환 판정을 명시하지 않는다.

### ❓ 미해소 비가시적 위임
- 항목 1: “선택적·조건부 섹션”의 완전한 목록과 제목/하위 제목/표의 판정 규칙을 구현 에이전트가 사전 조사 뒤 정하게 남겼다. 이 경계는 사용자 부담과 새 규칙의 적용 범위를 직접 바꾸지만, `결정 대기 항목`은 없음으로 선언되어 있다.
- 항목 2: 사유의 품질을 누가 어떤 입력으로 판정할지 비어 있다. 가능한 방향은 자연어 자기 점검만 적용, review checklist에서만 확인, hook으로 저장/상태 전환을 차단하는 방식이며, 각각 강제력과 기존 승인 흐름 영향이 다르다.
- 항목 3: `생략 사유`를 요구사항 명세의 일부로 둘지, 실행 계획 등의 비해시 섹션에 둘지 결정되지 않았다. 계획은 해시·승인 흐름을 보존해야 한다고 제약하지만 이 표기의 위치가 그 제약을 충족하는지를 결정하지 않는다.
- 항목 4: “기존 테스트를 보완”할 실제 테스트 파일과 fixture, invalid 문구의 예상 결과가 정해지지 않았다. 수정 대상의 `tests/test_todo_policy.py 또는 관련 정책 테스트`는 선택을 구현 단계로 넘긴다.

### 🔧 구조적 문제
- 항목 1: 1단계에서 확정한다는 적용 경계·표준 표기가 이후 변경의 핵심 설계 산출물인데, 계획서는 그 산출물을 승인 전에 제시하지 않는다. 사용자는 경계와 강제 방식이 미정인 계획만 승인하게 되어, 승인 뒤의 1단계가 요구사항 범위를 실질적으로 재정의할 수 있다.
- 항목 2: 5단계가 테스트 설계·테스트 수정·`sync-runtime`·전체 테스트·diff 검사를 한 단계에 묶어 실패 원인과 선행 조건을 분리하지 않는다. 특히 source 정책 테스트가 먼저 새 경계를 검증하지 못한 상태에서 dist를 생성하면, 테스트 실패가 규칙 설계 오류인지 동기화 오류인지 판단할 근거가 없다.
- 항목 3: architecture.md는 Runtime source 수정 뒤 `sync-runtime`으로 dist를 동기화하고 source/runtime-dist parity를 확인하도록 한다. 이 계획은 parity를 체크리스트에만 두고, 어떤 source 파일 집합과 생성된 dist 파일 집합을 비교할지와 동기화 실패 시 source 변경을 어떻게 판정할지를 정의하지 않아 해당 경계의 검증이 재현 가능하지 않다.
