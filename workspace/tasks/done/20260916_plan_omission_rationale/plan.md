# 작업 계획서: 계획서 생략 사유 기록

**파생 출처:** `workspace/issues/archived/legacy/campingtalk-proj/20260825_planTemplateOmissionWithoutRationale.md` — 선택적 계획서 섹션을 생략할 때 판단 근거가 남지 않음

---

## 요구사항 명세

### 요청 기준

사용자는 계획서에서 생략하는 항목에 한 줄 근거를 의무화하는 개선을 먼저 처리해 달라고 요청했다. 이 원칙은 사용자를 필요 이상으로 불편하게 하지 않는다는 기존 원칙을 지켜야 한다.

### 목적

선택적 계획서 섹션을 생략할 때 해당 판단을 나중에 검토할 수 있는 최소 근거를 남긴다. 형식적 `생략` 표기만으로 계획서가 통과하는 일을 막되, 필수 항목에 불필요한 설명을 추가하지 않는다. 에이전트는 **개발 시작 전 계획서 작성 단계**에 생략한 실행 계획 섹션과 사유를 한 표에 평이한 문장으로 기록한다. major에서는 계획서 검토 때 표를 함께 읽을 수 있게 하고, minor에서는 자동 승인 전에 계획서에 기록만 한다. 구현 승인 뒤에는 초기 표를 보존하고, 사용자 목적·범위·완료 기준·결정·제약과 완료 증거를 바꾸지 않는 발견만 실행 중 변경 기록으로 보완한다.

### 범위·제외 범위

- 범위: 공통 plan 템플릿, major 설계·검토 절차, minor 경량 절차에 선택적 **섹션 단위** 생략 시 한 줄 사유를 남기는 기록·검토 규칙을 추가한다. 적용 목록과 기록 방식은 아래 “생략 항목 기록 방식”으로 고정한다. 이 규칙은 Runtime 갱신 뒤 새 템플릿으로 작성한 plan부터 적용한다.
- 제외 범위: 이미 `없음`으로 값을 명시하는 필수 필드의 추가 설명 강제, 표 안의 빈 칸마다 사유 강제, 갱신 전 생성된 활성·완료 작업 계획서의 소급 수정 또는 새 형식 누락 처리, 새 사용자 승인·질문·별도 상태 단계·release 또는 deploy 생성.

### 완료 기준

- 새 plan.md는 실행 계획의 `생략 항목과 사유` 표에 생략한 선택적 섹션과 `[적용 조건] — [이 작업의 사실]`을 한 줄씩 기록한다. 생략이 없으면 표 전체에는 `없음`을 쓸 수 있다.
- major는 구현 승인 전 계획서 검토에서 표를 함께 제시한다. 명확한 실행 요청의 minor는 자동 승인 전 계획서에 표를 기록하고, 별도의 승인 요청이나 반복 요약을 만들지 않는다. `없음`·`해당 없음`·`불필요`만으로 된 **개별 사유**는 기록 근거로 인정하지 않는다.
- major와 minor의 적용 조건 및 예외가 같은 의미로 안내되고, `없음`으로 명시하는 필수 항목과 구별된다.
- major의 설계 자기 점검·구현 후 검토와 minor의 최소 확인에서 생략 사유의 조건·작업 사실을 대조한다.
- 갱신 전 생성된 활성 plan은 승인 당시의 템플릿과 checksum을 유지하며, 새 표·작업 분류 판단 근거의 누락으로 실패 처리하지 않는다.
- source Runtime과 dist Runtime이 동기화되고, 템플릿·절차·검토 기준의 기록 규칙 및 Runtime tree parity를 확인하는 회귀 검증이 통과한다.
- 새 규칙은 사용자에게 생략 이유를 별도로 묻지 않으며, 에이전트가 계획 작성 시 근거를 기록한다.

### 사용자 결정

- 선택적 섹션을 생략할 때 한 줄 근거를 의무화한다.
- 사용자 부담 최소화 원칙을 유지한다.
- 생략 사유의 누락은 에이전트가 개발 시작 전 계획서에 보완하는 작성 품질 항목이며, 사용자 승인·작업 진행을 차단하는 오류로 만들지 않는다.
- minor 자동 승인 전에 표를 기록하는 순서는 절차·최소 확인·회귀 문서 테스트로 확인하되, 기록 누락만으로 자동 승인을 차단하는 새 hook·상태 게이트는 만들지 않는다.

### 변경 불가 제약

- 기존 major 구현 승인 및 minor 자동 승인 흐름을 바꾸지 않는다.
- 생략 사유는 에이전트가 판단·기록하며, 사용자 확인 항목으로 승격하지 않는다.
- 구현 승인 뒤 요구사항 명세 안의 **작업 분류 판단 근거**가 바뀌면, 사용자와 확정한 명세 checksum이 달라지므로 기존 요구사항 명세 확인과 `renew-spec` 절차를 따른다. 실행 계획의 초기 생략 표는 보존한다. 이후 생략·복원 판단은 목적·범위·완료 기준·사용자 결정·변경 불가 제약 또는 완료 증거를 바꾸지 않을 때만 실행 중 변경 기록에 대상 섹션·이전 판단·새 판단·근거·명세 영향을 남기고 다음 의미 있는 보고에 누적한다.
- `.mpa/runtime/` 수정 뒤 `sync-runtime`으로 dist를 동기화하되, 사용자 명시 요청 없이는 release나 deploy를 실행하지 않는다.

### 에이전트 가정

| 가정 | 근거 | 틀렸다면 |
|---|---|---|
| 생략 항목을 한 표에 기록해도 계획서 검토가 충분히 명확하다 | 사용자는 섹션별 빈 제목보다 생략한 항목과 이유를 한곳에서 읽을 수 있다 | 표에 섹션명·사유·기록 시점을 모두 남겨 추적성을 보강한다 |
| 선택적 섹션의 범위는 템플릿과 minor 절차에서 식별할 수 있다 | 현재 템플릿은 major/minor 조건과 `불필요하면 섹션째 생략`을 명시한다 | 식별되지 않는 조건부 섹션은 명시적 적용 목록을 추가한다 |
| 과거 plan을 고치지 않아도 새 규칙의 목적을 달성한다 | 목적은 이후 작성되는 판단의 추적성이며 과거 기록 변경은 사용자 부담과 범위를 키운다 | 과거 기록이 실제 게이트 입력임이 확인되면 별도 마이그레이션 작업으로 분리한다 |
| 완료 증거 영향 경계를 문서 규칙으로 일관되게 판단할 수 있다 | 요구사항 명세의 완료 기준·사용자 결정·제약은 기존 checksum 대상이며, 실행 방법의 보완은 기존 변경 기록 대상이다 | 경계 사례를 템플릿·작성·검토 절차의 공통 표로 명시하고 fixture로 확인한다 |

### 결정 대기 항목 (Open Questions)

없음. 기존 요구사항 명세 checksum 경계는 유지하고, 실행 계획의 생략 사유는 표와 실행 중 변경 기록으로 관리한다.

### 작업 분류 판단 근거

major 판단 근거: 이 작업은 모든 프로젝트의 계획·검토 흐름과 Runtime 배포본에 영향을 주며, 여러 절차 문서와 회귀 검증의 정합성 설계가 필요하다.

## 실행 계획 (Implementation Plan)

### 생략 항목 기록 방식

기존 `minor 판단 근거`는 `작업 분류 판단 근거`로 바꿔 요구사항 명세 안에 둔다. major이면 major 분류 근거를 한 줄로 기록하고, minor이면 아래 네 근거를 정상 작성한다: 단일 관심사·한 파일 범위, 설계 결정 불필요, 즉시 복구 가능, 사용자 취향·의사결정 불필요. 따라서 분류 판단 근거는 사용자와 확정한 명세 checksum에 포함된다.

그 밖의 선택적 실행 계획 섹션은 실제로 생략할 때 제목을 억지로 유지하지 않는다. 대신 실행 계획 안의 `### 생략 항목과 사유` 표에 다음을 한 줄로 기록한다.

| 생략한 섹션 | 생략 사유 |
|---|---|
| [섹션명] | [적용 조건] — [이 작업에서 생략해도 되는 사실] |

기록 대상은 major의 `사전 조사`, 문서 업데이트 대상과 minor 경량 절차가 현재 선택적으로 허용하는 `사전 조사`, `예상 조용한 결정`, `수정 대상 파일`, `참고 파일`, `반례`, `검증 결과`, `실행 중 변경 기록`, `구현 후 발견`이다. `없음`, `해당 없음`, `불필요`, `N/A`만으로 된 개별 사유는 기록 근거로 인정하지 않는다. 필수 항목의 `없음`, 표 안의 빈 칸, 이미 완료된 과거 plan에는 이 표를 강제하지 않는다.

이 기록 방식은 Runtime 갱신 뒤 새 템플릿으로 작성한 plan부터 적용하며, 갱신 전 활성 plan은 승인 당시 형식과 checksum을 유지한다. 에이전트는 major에서는 구현 승인 전 계획서 검토에, minor에서는 자동 승인 전 계획서에 이 표를 채운다. major는 표가 있는 계획서를 검토 대상으로 제시하고, minor는 표를 기록한 뒤 기존 자동 승인 흐름을 이어 간다. 표 자체를 대화에 반복 나열하지 않으며, 목적·범위·위험·완료 증거에 영향을 주는 항목만 사용자에게 짧게 알린다. 이 순서는 새 hook·상태 게이트가 아니라 작성·최소 확인 절차로 관리한다.

구현 중 새 발견으로 생략·복원 판단이 바뀌면 초기 표는 수정하지 않는다. 아래 기준에서 **실행 방법 보완**이면 `실행 중 변경 기록`에 남기고, **명세 변경**이면 기존 사용자 확인과 `renew-spec`을 따른다.

| 판정 | 기준 | 처리 |
|---|---|---|
| 실행 방법 보완 | 같은 완료 기준과 증거를 같은 수준으로 유지하면서 조사 순서·참고 자료·기술적 방법만 바뀜 | 실행 중 변경 기록에 대상 섹션·이전 판단·새 판단·근거·`명세 영향: 없음` 기록 |
| 명세 변경 | 요구사항 명세의 목적·범위·완료 기준·사용자 결정·제약을 바꾸거나, 합의된 검증·문서 산출물·사용자 확인을 줄이거나 다른 것으로 대체함 | 변경 실행 전 사용자 확인 후 `renew-spec`과 명세 변경 이력 갱신 |

`실행 중 변경 기록`의 표는 `대상 섹션 | 이전 판단 | 새 판단 | 근거 | 명세 영향` 열을 사용한다. 처음에는 이 섹션을 생략했더라도 보완이 발생하면 같은 열로 다시 만들고 한 행씩 추가한다. `명세 영향`이 `확인 필요`이면 실행 방법 보완으로 처리하지 않고 명세 변경 경로로 올려, 변경 실행 전 사용자 확인을 받는다. `작업 분류 판단 근거`를 바꾼다면 자동 보완하지 않고 사용자 확인 뒤 `renew-spec`으로 checksum을 갱신한다.

### 사전 조사

`plan_template.md`의 선택적 섹션과 조건을 위 기록 대상 목록으로 대조하고, `layer1_design.md`, `layer1_review.md`, `agent_rules_detail.md`의 기존 작성·검토·minor 경량 지시가 충돌하지 않는지 확인한다. 기존 `plan_hash.py`가 요구사항 명세 checksum만 보호하는 경계를 확인한다.

### 구현 단계

1. **공통 템플릿을 갱신한다** — 실행 계획에 `생략 항목과 사유` 표를 추가하고, `작업 분류 판단 근거`에는 major·minor 각각의 판단 근거를 남기게 한다. / 이유: 초기 계획서에서 생략 판단과 분류 판단을 한곳에 명확히 보여 준다.
2. **작성·경량 절차를 정렬한다** — `layer1_design.md`에는 major가 계획서 검토 전에 초기 표를 작성·자가 점검하게 하고, `agent_rules_detail.md`에는 minor가 자동 승인 전에 초기 표를 작성한 뒤 최소 확인에서 조건·사실을 대조하게 한다. 두 절차에는 초기 표 보존, 기존 checksum 경계, 후속 변경 기록 형식을 같은 의미로 넣는다. / 이유: major·minor 중 어느 경로에서도 기록 시점·후속 보완이 빠지지 않게 한다.
3. **검토 기준을 추가한다** — `layer1_review.md`에 초기 표의 항목·사유와 실제 조건을 대조하고, 후속 생략·복원 판단은 실행 중 변경 기록의 대상 섹션·이전 판단·새 판단·근거·명세 영향을 확인하는 기준을 추가한다. / 이유: 표가 형식적 문구가 되거나 승인 뒤 변경 이력이 사라지는 것을 막는다.
4. **source 회귀 검증을 구현한다** — `tests/test_plan_hash.py`에 `작업 분류 판단 근거`가 요구사항 명세 checksum에 포함되는 fixture를 추가한다. `tests/test_todo_policy.py`에는 템플릿·major 작성 절차·minor 자동 승인 전 기록·최소 확인·검토 기준·변경 기록 열·`확인 필요`의 명세 변경 경로를 검사하는 정책 사례를 추가한다. 이는 문서 절차의 회귀를 확인하며, 새 차단 게이트를 만들지 않는다. / 이유: checksum 경계와 major/minor의 시점·의미를 명시적으로 보존한다.
5. **동기화 후 배포본 검증을 수행한다** — source 정책·checksum 테스트를 먼저 실행한 뒤 `sync-runtime`으로 dist를 동기화한다. `diff -qr .mpa/runtime dist/.mpa/runtime`이 통과한 뒤에만 `tests/test_plan_hash.py`의 임시 fixture로 source와 dist `plan_hash.py`를 각각 직접 실행한다. 이어 `test_policy_consistency.py`를 포함한 전체 테스트와 `git diff --check`을 실행한다. 정책 문서의 dist 동일성은 parity로, hook의 dist 실행성은 직접 CLI fixture로 증명하며 앞 단계가 실패하면 뒤 단계로 진행하지 않는다. / 이유: source 규칙 오류·동기화 오류·설치본 hook 실행 오류를 순서대로 분리한다.

### 예상 조용한 결정

- 생략 항목은 실행 계획의 단일 표에 모은다. 이유: 빈 섹션을 여러 개 남기지 않아 사용자와 검토자가 판단 근거를 한곳에서 읽는다.
- 표준 표기는 `[적용 조건] — [이 작업의 사실]`으로 통일한다. 이유: 한 줄로 충분하면서도 단순한 `없음` 표기를 막는다.
- 생략 사유는 작업 내용에 맞는 사실을 쓴다. `해당 없음`이나 `불필요`만 반복하는 문구는 근거로 인정하지 않는다. 이유: 표기의 목적은 판단을 재검토할 수 있게 하는 것이다.
- `작업 분류 판단 근거`는 major·minor 모두 작성한다. 이유: major에서 minor 전용 제목을 억지로 채우지 않고, 분류 판단 자체를 checksum으로 보호한다.
- optional 섹션이 실제로 필요한 경우에는 생략 사유 대신 정상 내용을 작성한다. 이유: 근거 문구로 필요한 조사·검토를 대체하지 않는다.
