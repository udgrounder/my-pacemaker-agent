## 비평 결과

### 🚨 실패 시나리오
- 시나리오 1: 승인 뒤 구현자가 실행 계획 표의 사유를 "목적·범위·완료 기준·사용자 결정·제약을 바꾸지 않는 보완"으로 판단해 추가·교체한다 → 원래 승인 때는 없던 조사, 문서화, 검증의 생략 판단이 사용자 재확인 없이 정당화된다. 실행 계획 표와 실행 중 변경 기록은 요구사항 명세 checksum 밖이고, 변경 전 표를 보존·대조할 방법도 계획에 없다. 근거: `요구사항 명세 > 변경 불가 제약`, `실행 계획 > 생략 항목 기록 방식`은 구현 중 자동 보완을 허용하며, architecture.md의 checksum 계약은 실행 계획·변경 기록을 해시 대상에서 제외한다.
- 시나리오 2: minor의 명시적 실행 요청에서 자동 승인 후 곧바로 구현이 시작된다 → "개발 시작 전 승인 요청 전에 표를 채우고 제시 메시지에서 요약"한다는 완료 기준을 적용할 시점이 없거나, 자동 승인 성격과 어긋난 별도 제시 흐름이 생긴다. 어느 시점에 누구에게 어떤 요약을 제시해야 하는지 결정되지 않아 minor에서는 기록 또는 안내가 빠질 수 있다. 근거: `완료 기준`은 승인 요청 전 제시를 요구하지만, architecture.md와 agent_rules.md의 minor 경로는 명확한 실행 요청에서 자동 구현 승인을 처리한다.
- 시나리오 3: source Runtime 파일을 수정한 뒤 4단계에서 source/dist 정렬 검사를 실제로 실행한다 → 아직 `sync-runtime` 전이므로 의도적으로 dist가 오래된 상태여서 검사가 실패하거나, 검사를 건너뛰어 검증 결과가 계획과 달라진다. 근거: `구현 단계` 4는 source/dist 정렬 검사를 추가·확인한다고 하고, 5단계가 그 뒤에 `sync-runtime`과 parity 검사를 수행한다고 명시한다. architecture.md는 source 수정 뒤 `sync-runtime`으로 dist를 동기화하는 순서를 정한다.
- 시나리오 4: 새 템플릿에 실제 선택적 섹션이 목록 밖으로 남거나, major와 minor에서 같은 이름의 섹션이 다른 조건으로 허용된다 → 기록 표가 일부 생략을 포착하지 못하면서도 테스트는 계획에 열거한 항목만 검사해 통과한다. 근거: `범위·제외 범위`는 적용 목록을 아래 방식으로 고정하고, `생략 항목 기록 방식`은 제한된 목록을 정한다. 그러나 `에이전트 가정`은 템플릿과 minor 절차에서 식별할 수 있다고만 전제하고, 구현 전 조사 결과가 목록과 다를 때 명세·테스트를 어떻게 갱신할지는 없다.

### ⚠️ 숨은 가정 (파급효과 높은 순)
- 가정 1: 실행 계획의 생략 사유가 바뀌어도 요구사항 명세의 다섯 항목을 건드리지 않으면 사용자 승인 의미는 항상 유지된다. / 틀렸을 때: 문서·조사·반례·검증을 생략하는 판단이 실제 위험과 완료 증거를 바꾸어도 checksum과 `renew-spec` 경로를 우회한다. 근거: `변경 불가 제약`은 다섯 항목만 변화 판정 기준으로 제시하고, `생략 항목 기록 방식`은 그 밖의 보완을 자동 처리한다.
- 가정 2: 한 표의 모든 생략 사유를 승인 제시 메시지에서 요약해도 사용자의 인지 부담이 작다. / 틀렸을 때: 여러 선택 항목이 있는 major 계획에서 사용자가 구현 판단에 필요하지 않은 내부 절차 사유까지 읽고 승인해야 하며, 사용자 부담 최소화 원칙과 충돌한다. 근거: `완료 기준`과 `운영 시 안내 사항`은 각 생략 항목·이유의 제시를 요구하지만, 축약 기준·최대 범위·사용자 판단에 필요한 경우의 구분은 없다. agent_rules.md의 사용자 부담 최소화는 계획·기록 관리를 에이전트가 맡도록 한다.
- 가정 3: "[적용 조건] — [이 작업의 사실]" 형식만으로 사유의 진실성과 충분성을 자기 점검·구현 후 검토에서 판정할 수 있다. / 틀렸을 때: 그럴듯한 사실 문장이 조사나 반례를 대체하고, 검토자가 판단 근거의 원천이나 반증 기준 없이 형식만 통과시킨다. 근거: `예상 조용한 결정`과 `반례`는 단문 표기를 요구·대조한다고 하지만, 사실을 입증할 증거나 사유별 최소 검토 기준은 정의하지 않는다.
- 가정 4: major의 분류 근거를 `minor 판단 근거`에 기록해도 minor 자동 승인 절차의 의미와 형식이 일관되게 유지된다. / 틀렸을 때: major 계획에서 minor 전용 판단란의 역할이 바뀌고, 템플릿·minor 절차·hash 테스트가 서로 다른 의미를 검사할 수 있다. 근거: `생략 항목 기록 방식`은 major면 해당 항목에 major 근거를 쓰고 minor면 정상 작성한다고 하지만, `완료 기준`의 "major와 minor의 적용 조건 및 예외가 같은 의미"를 검증할 명확한 필드 계약은 없다.

### ❓ 미해소 비가시적 위임
- 항목 1: 승인 뒤 어떤 변경이 단순한 "실행 계획 영역의 보완"이고 어떤 변경이 사실상 요구사항 명세 변경인지 판정 권한과 판정 규칙이 에이전트에게 암묵적으로 위임돼 있다. 근거: `생략 항목 기록 방식`은 에이전트가 먼저 다섯 명세 항목 불변을 확인하라고 하지만, 생략 사유가 검증 범위·문서 필요성·조사 필요성에 미치는 영향을 분류하는 기준은 없다.
- 항목 2: minor의 제시 메시지를 자동 승인 전, 자동 승인 후, 또는 다음 의미 있는 보고 중 언제 보낼지 결정되어 있지 않다. 근거: `완료 기준`의 "승인 요청 전"과 `사용자 결정`의 "진행을 차단하지 않는 오류"가 minor 자동 승인 흐름과 만나는 지점이 비어 있다.
- 항목 3: "선택적 섹션"의 정본 목록과 각 항목의 적용 조건을 구현자가 조사 결과에 따라 정할 수 있게 남겨 두었다. 근거: `에이전트 가정`은 식별 실패 시 적용 목록을 추가한다고만 하고, `결정 대기 항목`은 없음으로 닫혀 있다. 목록을 요구사항 명세에서 고정한다는 선언과 충돌한다.
- 항목 4: `tests/test_todo_policy.py 또는 관련 정책 테스트` 중 어느 파일과 무엇을 계약으로 검사할지 결정되지 않았다. 근거: `수정 대상 파일`과 4단계가 대안 경로를 열어 두어, 템플릿·design·review·minor 절차·hash 경계를 하나의 회귀 세트가 모두 검증하는지 검토자가 판정할 수 없다.

### 🔧 구조적 문제
- 항목 1: 사전 기록과 구현 중 보완의 경계가 기록 구조상 검증 불가능하다. `실행 중 변경 기록`은 구현 중 채워지는 가변 표이고 초기 생략 표도 동일 plan.md에서 수정되므로, 검토 단계가 승인 당시 사유와 후속 사유를 구분할 불변 기준이 없다. 근거: `실행 계획 > 생략 항목 기록 방식`은 처음 생략한 `실행 중 변경 기록` 섹션을 보완 시 다시 만들 수 있게 하고, architecture.md는 이 두 영역을 checksum에서 제외한다.
- 항목 2: major와 minor의 규칙을 "같은 의미"로 정렬한다는 목표에 비해 구현 단계는 major `layer1_design.md` 자기 점검, minor `agent_rules_detail.md`, 공통 `layer1_review.md`만 수정한다. minor 단계 모델에는 별도 검증·테스트 단계가 생략되어 있으므로 `구현 후 검토`의 실행 시점과 담당이 명시되지 않으면 major에만 실질 검토가 남는다. 근거: `구현 단계` 2~3과 agent_rules.md의 minor 단계 모델.
- 항목 3: 검증 순서가 source/dist 경계와 맞지 않는다. 정렬 검사를 4단계의 실행 대상으로 둔 뒤 5단계에서 동기화하므로, 변경 직후의 실패를 정상 상태로 취급해야 하는 모순이 생긴다. source 정책·hash 검사와 sync 후 parity·dist 전체 검사를 분리한 실행 순서와 각각의 통과 기준이 필요하지만 계획에는 없다. 근거: `구현 단계` 4~5, `실행 TODO`, architecture.md의 Runtime source/dist 동기화 원칙.
