## 비평 결과

### 🚨 실패 시나리오
- 시나리오 1: 승인 당시 `실행 중 변경 기록`을 생략한 작업에서 구현 중 해당 섹션을 복원해야 할 사실이 발견됨 → 계획은 초기 표를 보존하고 변경 기록에 이전 판단·새 판단·근거를 남기라고 한다(`plan.md:86`). 그러나 실제 변경 기록 표는 `변경 내용 | 이유 | 명세 영향` 세 칸뿐이고(`plan.md:176-180`), 초기 표의 어느 행·섹션을 바꾸는지, 이전 판단과 새 판단을 어느 필드에 보존하는지 정하지 않는다. 같은 섹션이 여러 번 생략·복원되면 검토자는 초기 사유와 각 후속 판단을 일대일로 추적할 수 없으며, 검토 단계도 그 연결을 재현할 증거를 갖지 못한다.
- 시나리오 2: 구현자는 새 발견이 완료 증거를 실질적으로 좁힌다고 보면서도 이를 “목적·범위·완료 기준에는 영향 없음”으로 해석해 비해시 실행 중 변경 기록에만 남김 → `renew-spec` 없이 승인 뒤의 완료 판단이 바뀐다. 계획은 완료 증거 변경을 명세 변경으로 처리한다고 선언하지만(`plan.md:51, 86, 133`), “완료 증거를 바꾼다”의 판정 기준·경계 사례·실패 테스트가 없다. 제안된 checksum fixture도 `작업 분류 판단 근거`만 다룬다(`plan.md:97`). `plan_hash.py`는 요구사항 명세 블록만 checksum 대상으로 한다는 아키텍처 경계(`architecture.md:110-111`) 때문에, 이 잘못된 비해시 분류 자체를 탐지할 수 없다.
- 시나리오 3: source 검증은 통과했지만 `sync-runtime`이 누락·오래된 Runtime 파일을 남김 → dist 대상 전체 테스트가 source 규칙을 읽어 통과하거나, parity 이전에 실행되어 설치본 검증의 근거가 되지 못한다. 구현 단계는 sync 뒤 “전체 테스트, source/dist Runtime tree parity” 순으로 적고(`plan.md:98`), 반례는 parity 뒤 dist 전체 테스트라고 적어(`plan.md:134`) 순서가 서로 다르다. 아키텍처는 source Runtime 수정 뒤 sync를 수행하도록 요구한다(`architecture.md:98-103, 243`). 동기화가 확인되기 전 dist 검증을 신뢰할 수 없는데, 어느 테스트가 `dist/.mpa/runtime`를 대상으로 실행되는지도 계획에 고정돼 있지 않다.

### ⚠️ 숨은 가정 (파급효과 높은 순)
- 가정 1: 에이전트가 “완료 증거에 영향 없음”을 사용자 승인 경계와 일관되게 구분할 수 있다. / 틀렸을 때: 승인 checksum이 보호하지 않는 기록으로 완료 조건을 축소하거나, 반대로 사소한 기록마다 불필요하게 `renew-spec`을 요구해 사용자 부담과 게이트 동작이 모두 흔들린다. 현재 요구사항은 이 판단을 구현자에게 남기고 있다(`plan.md:51, 86`).
- 가정 2: 문서 지시와 문자열 중심 정책 테스트만으로 minor의 “자동 승인 전 기록”과 major의 “승인 전 함께 제시” 시점이 지켜진다. / 틀렸을 때: 명확한 실행 요청을 minor로 분류한 뒤 표를 생성하거나, major 검토에서 표를 실제로 제시하지 않은 채 승인으로 진행할 수 있다. 계획의 변경 대상은 작성·최소 확인·사후 검토 문서뿐이며(`plan.md:94-98, 112-118`), 각 상태 전이 직전에 표 존재와 제시 여부를 확인하는 실행 증거 또는 실패 테스트는 없다.
- 가정 3: `다음 의미 있는 보고`가 모든 실행자와 사용자에게 같은 시점·가시성을 뜻한다. / 틀렸을 때: 판단 변경은 구현 로그에만 쌓이고 사용자는 완료 직전까지 초기 생략 사유가 뒤집힌 사실을 알 수 없다. 이 표현은 후속 판단을 어떤 보고에, 어떤 범위로 보여 줄지 결정하지 않는다(`plan.md:51, 86`).
- 가정 4: 열거된 현재의 생략 대상만 관리해도 템플릿·절차의 미래 선택 섹션이 누락되지 않는다. / 틀렸을 때: 후속 작업에서 조건부 섹션을 새로 추가해도 고정 목록(`plan.md:84`)과 회귀 검증이 함께 갱신되지 않아, 새 섹션은 사유 기록 규칙 밖으로 빠진다.

### ❓ 미해소 비가시적 위임
- 항목 1: 초기 생략 표의 행과 실행 중 변경 기록의 행을 연결할 식별자·필수 필드·다회 변경 규칙이 없다. “이전 판단·새 판단·근거”를 남기라는 서술(`plan.md:86`)과 실제 표 형식(`plan.md:176-180`)이 다르므로, 구현자가 내용을 한 칸에 합칠지 새 행을 만들지 임의로 정해야 한다.
- 항목 2: optional 섹션을 복원해 실제 내용을 추가한 경우, 그것이 단순 실행 계획 보완인지 완료 증거 변경인지 판단할 기준이 없다. 이 선택이 `renew-spec`과 사용자 확인을 좌우하지만, 결정 대기 항목은 “없음”으로 닫혀 있다(`plan.md:62-64`).
- 항목 3: minor의 분류 판단 근거에 적을 “네 판단 근거”의 뜻과 개수가 정의돼 있지 않다(`plan.md:76`). minor 작성자가 필요한 근거 수와 내용, checksum에 들어갈 실제 문장을 조용히 결정하게 된다.
- 항목 4: 사용자 부담을 줄이기 위해 표를 메시지에서 반복하지 않는다는 결정(`plan.md:86`)과 major에서 승인 전 표를 함께 제시한다는 완료 기준(`plan.md:35`)을 동시에 만족시키는 최소 제시 형식이 없다. 목적·범위·위험·완료 증거에 영향이 없다고 누가 판정하는지와, 표의 변경을 사용자에게 언제 알리는지가 비어 있다.

### 🔧 구조적 문제
- 항목 1: source → sync → parity → dist 검증의 의존 순서가 단일하지 않다. 구현 단계는 전체 테스트를 parity보다 먼저 두고(`plan.md:98`), 반례는 parity를 dist 전체 테스트보다 먼저 둔다(`plan.md:134`), TODO는 둘의 순서를 명시하지 않는다(`plan.md:144-145`). stale dist를 대상으로 한 테스트 결과를 유효한 배포본 검증으로 오인할 수 있으므로, 실행 순서와 각 단계의 실패 시 다음 단계 중단 조건이 필요하다.
- 항목 2: major·minor 적용 시점은 결과 문구로만 요구되고 구현 단계에서 검증 가능한 전제 조건으로 분해되지 않았다. major의 계획 검토, minor의 자동 승인 전 기록, 사후 review를 서로 다른 파일에 나누어 수정하지만(`plan.md:94-96`), 테스트 계획은 이 시점의 순서 위반을 재현하지 않는다(`plan.md:97-98, 158-162`). 동일한 규칙이 템플릿에는 있어도 실제 승인 경로에서 늦게 적용되는 회귀를 막지 못한다.
- 항목 3: 초기 표 보존과 후속 변경 추적을 검토하겠다는 기준(`plan.md:96, 159-160`)에 비해, 검증 체크리스트에는 여러 차례 변경·섹션 복원·변경 기록이 비어 있던 초기 상태를 검증하는 사례가 없다. 핵심 추적성 요구가 한 번의 변경만 가정한 채 남아 있다.
