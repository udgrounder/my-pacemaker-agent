## 비평 결과

### 🚨 실패 시나리오
- 시나리오 1: 이미 승인되어 `구현 중`인 plan이 기존 `minor 판단 근거` 구조와 당시의 reqspec checksum을 유지한 상태에서 새 작성·검토 절차가 적용됨 → 계획은 과거 plan을 소급 수정하지 않는다고 제외하지만, 새 절차가 구형 제목·표 부재를 어떻게 판정하는지는 없다. 구현 후 검토가 새 형식을 누락으로 처리하면 승인 당시의 checksum을 바꾸거나 정상 작업을 거짓 실패로 만들 수 있다. `architecture.md`는 접두사 없는 구형 해시를 과거 이력 읽기에서만 유지한다고 하므로, 현재 활성 plan의 호환 경계도 별도로 정해야 한다.
- 시나리오 2: minor가 자동 승인으로 넘어가는 경로에서 표가 파일에 기록되기 전에 기존 자동 승인 상태 전환이 실행됨 → 완료 기준은 “자동 승인 전 계획서에 표를 기록”이라고 요구하지만, 구현 단계 2는 절차 문구를 정렬하는 데 그치고 단계 4의 회귀 검증도 기록 저장·최소 확인·상태 전환의 순서를 실제로 재현하도록 명시하지 않는다. 결과적으로 텍스트 정책은 존재해도 자동 승인 시점의 기록을 보장하지 못한다.
- 시나리오 3: 승인 뒤 어떤 검증 산출물을 다른 산출물로 바꾸는 일이 발생하고, 에이전트가 “같은 수준의 증거”라고 판단해 다섯 열 기록에만 남김 → 계획의 실행 방법 보완 기준은 “같은 수준”을 정의하지 않으며 `명세 영향: 확인 필요`일 때 중단·사용자 확인을 요구하는 규칙도 없다. 합의된 완료 증거가 사실상 교체·약화되어도 `renew-spec` 없이 진행될 수 있다.
- 시나리오 4: source 테스트가 통과하고 `sync-runtime` 및 `diff -qr`도 통과했지만, 이후 “dist 전체 테스트”가 source import 경로에서 실행됨 → 단계 5가 dist에서 직접 실행한다고 구체화한 것은 `plan_hash.py` fixture뿐이다. `test_policy_consistency.py`를 포함한 전체 테스트의 실행 위치·import 대상·dist Runtime을 대상으로 했다는 판정 기준이 없어서, source→sync→parity 뒤 배포본 실행 검증이 실제로는 source만 재검증할 수 있다.

### ⚠️ 숨은 가정 (파급효과 높은 순)
- 가정 1: 현재 활성 계획서에는 새 `작업 분류 판단 근거`와 생략 표를 강제해도 되는 구형/신형 구분이 이미 가능하다 / 틀렸을 때: 승인된 명세의 checksum 경계와 “과거 plan 소급 수정 제외” 제약이 충돌하고, 검토 기준이 활성 작업을 일관되게 처리하지 못한다.
- 가정 2: “같은 수준의 완료 증거”를 모든 작성자와 검토자가 같은 결과로 판정한다 / 틀렸을 때: 보존해야 할 초기 표와 다섯 열 변경 기록이 존재해도, 승인 대상인 완료 기준의 실질적 변경이 실행 방법 보완으로 조용히 처리된다.
- 가정 3: 정책 문구와 문자열 기반 회귀 검사가 minor 자동 승인 전의 영속 기록 순서를 보장한다 / 틀렸을 때: 표가 기록되기 전 자동 승인되는 실제 경로를 테스트가 놓친다.
- 가정 4: `diff -qr`와 source에서 실행하는 전체 테스트가 dist Runtime의 동작 검증을 대신한다 / 틀렸을 때: 동기화 이후에만 드러나는 실행·import·경로 문제를 release/deploy 없이도 발견하지 못한다.

### ❓ 미해소 비가시적 위임
- 항목 1: 새 형식이 도입된 뒤 기존에 생성되었고 아직 완료되지 않은 major/minor plan을 어떤 기준으로 허용·검토할지 구현자에게 위임되어 있다. 적용 시작점, 구형 형식 허용 조건, checksum 재생성 금지를 명시해야 한다.
- 항목 2: 다섯 열의 `명세 영향`이 `확인 필요`일 때 누가 언제 판단하고, 사용자 확인 전 작업을 계속할 수 있는지가 정해져 있지 않다. 이 값은 `없음` 또는 명세 변경으로 확정되기 전에는 변경 실행을 막는지 결정이 필요하다.
- 항목 3: dist 전체 테스트를 어떤 명령·작업 디렉터리·import 경로로 실행해 dist 파일을 실제 대상으로 만들지 정해져 있지 않다. source 검사와 독립된 증거를 만들 실행 방법이 필요하다.

### 🔧 구조적 문제
- 항목 1: 단계 4의 source 회귀 검증에는 minor의 “자동 승인 전 기록”이 문구로 존재하는지 확인하는 내용만 있고, 단계 2에서 요구하는 기록→최소 확인→자동 승인 순서의 실행 검증이 없다. 순서가 이 기능의 핵심 제약이므로 상태 전환을 포함한 실패 fixture를 source 검증에 추가해야 한다.
- 항목 2: 단계 5의 순서가 source→sync→parity→dist로 서술되었지만, parity 뒤 검증 중 dist를 직접 실행하는 대상이 checksum fixture로 한정된다. `test_policy_consistency.py`와 전체 테스트가 dist Runtime을 로드했음을 명시·검증하지 않으면 마지막 dist 단계가 독립된 단계가 아니다.
