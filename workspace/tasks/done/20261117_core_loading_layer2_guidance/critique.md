# 독립 설계 비평

대상: `workspace/tasks/active/20261117_core_loading_layer2_guidance/plan.md`의 `task_documents.py inputs --stage critique` 출력. 설계 대화·진행 기록·계획 원문 전체를 읽지 않았다. 실제 정본·소비 경로·검사 구현과 프로젝트 정체성/아키텍처를 대조했다. 구현 검증이 아닌 승인 전 설계 비평이다.

판정: 아래 P1·P2 항목의 설계 보완이 필요하다. P1은 설치 Runtime만으로 주기를 유지한다는 완료 기준에, P2는 필수 로드·검증 범위 해석에 영향을 준다.

## 🚨 실패 시나리오

### F1. [P1] 새 설치 프로젝트에서 실제 점검을 끝내도 다음 제안의 기준 마커가 생기지 않을 수 있다

- 대상: C3·C4·C7, Layer 2 안내 내용, 실행 계획 3.
- 근거: `inject/layer2_checkpoint.md`의 `완료 기준`과 `세션 종료 시`에는 실제 점검 완료 후 `[Layer 2 완료] YYYY-MM-DD`를 INDEX에 기록하는 지시가 없다. 해당 절차는 현재 `workspace/memory/shared/architecture.md:95-100`에만 존재한다. source 프로젝트 메모리는 새 설치 Runtime에 배포되지 않는다. 계획에는 제안만으로 마커를 쓰지 않는다는 금지만 있고, 실제 점검 완료 시 마커 기록 소유 경로를 복원하는 명시 설계가 없다.
- 반례: 마커 없는 설치본에서 사용자가 전체 점검을 요청해 끝냄 → Runtime 지시만 따르면 여전히 마커 없음 → 다음 major 완료도 계속 집계 미확인으로 남을 수 있다. 모든 설치본에서 실제 누락됐다는 주장이 아니라 현재 실행 문서에 기록 지시가 없다는 발견이다.
- 보완: 실제 Layer 2 완료 판정 후 기존 INDEX 마커를 기록하는 소유 경로와 제안/중단/미완료 시 기록 금지를 함께 지정하고 회귀 대조 사례를 둔다. 새 DB나 hook은 필요하지 않다.

### F2. [P2] 대상 heading 검사는 통과하지만 소비 경로의 필수 로드는 끊길 수 있다

- 대상: C2·C6, 공통·상세 정본 배치 3, 실제 참조 검사.
- 근거: 현재 `tests/test_structure_loading.py`는 독립적인 `assertIn(trigger, start_file)`와 `assertIn(target_section, target_file)`만 확인한다. 계획은 실제 표의 대상과 정확한 heading 검사로 개선하지만 음성 fixture에는 대상 삭제/이름 변경만 명시한다. 이것만으로는 완료 후속 참조 삭제나 minor 직접 경로의 상세 관리 로드 누락까지 반드시 검출하지 못한다.
- 반례: 관리 정본 heading과 core 표를 유지하고 단계 소비 경로의 필수 로드 연결만 제거 → 대상 삭제 fixture와 heading 존재 검사는 계속 통과할 수 있다.
- 보완: 범용 그래프는 필요 없다. 이번 이동의 minor 직접 작성·의미 변경·검증 진입·재개, major 완료→Layer 2 대표 연결에서 출발 참조 제거/오지정도 실패하는 검사를 명시한다. 정적 검사가 실제 모델 준수를 입증한다는 주장은 피한다.

## ⚠️ 숨은 가정 (파급효과 높은 순)

### A1. [P2] 기존 트리거 표를 정확히 검사하면 이번 두 누락만 발견된다는 가정

- 대상: 실제 트리거 표 검사와 변경 범위.
- 근거: `core/agent_rules.md:34`의 표는 `"작업 항목 재개"`를 가리키지만 detail의 실제 heading은 `## 태스크 재개`다. core 본문의 재개 섹션은 이 호환 제목을 명시한다. 기존 테스트의 resume 계약은 본문과 실제 detail heading을 별도로 확인해 표 불일치를 놓친다.
- 영향: 표 전체를 정확히 검사하면 기존 불일치도 실패한다. 구현자가 임의 예외를 넣거나 다시 수동 목록으로 축소할 가능성이 남는다.
- 보완: 검사할 표/본문 범위와 호환 제목 처리 방식을 정한다. 실제 표 참조를 고치는지 제한된 명시 매핑을 두는지 근거를 기록하고 제목 일부 일치로 통과시키지 않는다.

### A2. [P2] 제목·계약 앵커 보존이 이동한 보호 의미까지 대표한다는 가정

- 대상: C2·C6의 의미 보존, 이동 전후 대응표.
- 근거: 현재 core `agent_rules.md:317`은 단일 갱신 담당자, `.plan-renewal.json` 잔존 시 다른 에이전트의 문서 편집 중단, 충돌 증거 보존을 요구한다. `:318`은 과거 성공의 효력이 사라지면 현재 plan에 미확인/재검증 필요를 남겨 1차 검증에서 보이도록 한다. 두 항목은 승인 명령·TOML 앵커 검사만으로 입증되지 않는다.
- 영향: 문단을 옮겼어도 읽는 시점이 늦으면 충돌 전 편집 중단이나 검증 입력의 실패 노출이 무력화된다.
- 보완: 계획이 약속한 의미 대응표에서 두 항목을 별도로 잡고 문서 편집 전·검증 입력 준비 전 도달하는 필수 경로를 확인한다. 새 의미 규칙이 아니라 실제 이동 대상의 보호 조건을 구체화하라는 지적이다.

## ❓ 미해소 비가시적 위임

### D1. [P2] 기존 Layer 2 권장 주기와 새 정본의 관계

- 대상: C4·C7, Layer 2 안내 내용과 `inject/layer2_checkpoint.md` 변경 범위.
- 근거: 실행 inject 상단은 현재 `권장 주기: 3~5개 태스크 완료 후, 또는 스프린트 종료 시`라고 한다. 계획은 detail에 `major 1개 이상 또는 minor만 5개 이상`을 정본으로 만들지만 기존 문구의 처리 방향을 명시하지 않았다. inject는 변경 대상에 포함돼 있다.
- 영향: 기존 문구를 유지하면 설치 Runtime 안에 두 주기 기준이 남는다. 삭제하면 스프린트 종료 시 요청할 수 있다는 운영 권고도 함께 사라질 수 있다.
- 보완: 기존 상단을 새 안내 정본 참조로 바꾸고 스프린트 종료는 사용자 임의 요청의 예인지 별도 제안 조건인지 구분한다. minor 기본 표시 생략과 날짜/종류 미확인 처리는 새 정본에 모으고 복제하지 않는다.

## 🔧 구조적 문제

### S1. [P2] 음성 fixture와 실제 검사가 동일한 검사기를 공유할 구조가 아직 없다

- 대상: 실행 계획 4, 대상 섹션 삭제/이름 변경 fixture.
- 근거: 현재 `tests/test_structure_loading.py`는 모듈 전역 `ROOT`/`RUNTIME_ROOTS`에 의존하고 검사 로직이 `TestCase` 메서드 안에 있다. 계획의 음성 fixture에는 임시 Runtime 또는 메모리 문서 집합을 받을 검사 단위가 먼저 필요하다.
- 영향: fixture 전용 별도 검사로 성공을 주장하거나 실제 source/dist를 변경했다 원복하는 구현 여지가 있다. 후자는 기존 미커밋 변경 보호와 충돌한다.
- 보완: 실제 문서 검사와 음성 fixture가 동일 검사 함수를 쓰도록 경로/문서 입력을 분리한다. 원본 Runtime을 바꾸지 않는 임시 사본 또는 메모리 입력에서 삭제·이름 변경·참조 단절을 주입하고 실패를 확인한다. 새 Runtime hook 도입을 뜻하지 않는다.

비평 한계: 재배치 후 실제 byte 수·source/dist parity·전체 테스트 통과는 구현 전이므로 검증하지 않았다. 기존 `CORE_BASELINE_BYTES=34_731` 유지와 사전 재배치 시뮬레이션은 계획에 있으므로 기준 상향·규칙 삭제를 전제한 결함은 주장하지 않는다. 날짜 모호성·minor 기본 생략은 이미 방향이 명시돼 있어 새 결함으로 중복 제기하지 않았다.
