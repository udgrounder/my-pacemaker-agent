# 작업 계획서: 공통 규칙 로드 크기와 Layer 2 안내 연결 보완

## 요구사항 명세

### 요청 기준
사용자 요청: “남은 공통 규칙 크기 초과와 Layer 2 안내 참조 누락을 해결할 계획서 작성해줘.”
출처: 크기 초과 이슈(20261117_core_loading_size_budget_exceeded.md), Layer 2 참조 누락 이슈(20261117_layer2_status_reference_missing.md), [전체 정합성 점검](../../../exploration/checkpoints/20261117_consistency_check.md). 해결한 이슈 원문 두 파일은 2026-11-18 사용자 요청으로 삭제하며, 발견·해결 근거는 이 작업의 계획/변경 이력·독립 검증에 보존한다.

### 목적
항상 읽는 공통 규칙을 기존 크기 기준 안으로 줄이면서 규칙의 의미·승인 경계를 유지한다. 작업 완료 후 Layer 2 현황·제안을 안내할 실제 정본을 마련하고 필수 로드 트리거가 그 위치로 연결되도록 한다.

### 범위·제외 범위
범위는 Runtime의 공통 규칙·상세 규칙 사이 상세 절차 재배치, 영향을 받는 설계/구현/검토/재개/완료·템플릿 참조 연결, Layer 2 안내 기준 복원, 회귀 검사 보강, 문서·현재 아키텍처 정본 동기화와 source/dist 동기화다.
제외 범위는 크기 기준 상향·검사 삭제, 의미 있는 규칙 삭제·승인 완화, TOML 공개 계약·상태 모델 변경, 새 완료 집계 DB/설정/런타임 hook 도입, 과거 done 작업·승인 기록 일괄 수정, 개별 프로젝트 자산 변경, 릴리즈 생성·대상 배포다.

### 완료 기준
- C1. source와 dist의 core/agent_rules.md가 기존 CORE_BASELINE_BYTES=34,731보다 작다. 기준 상향·우회 없이 기존 크기 검사가 통과하며 변경 전후 바이트 수와 옮긴 절차를 기록한다.
- C2. 이동한 계획/이력·실행 TODO 규칙의 의미를 보존한다. 공통 파일에는 정본 구분·필수 라우팅·승인/복구·증거 보호의 짧은 불변식이 남고 관련 행동 전에 상세 정본을 읽을 연결이 있다. 단순 질문이 모든 상세 파일을 자동 로드하도록 만들지 않는다.
- C3. “Layer 2 현황 표시”의 실제 정본 섹션과 필수 트리거가 일치하며 작업 완료 경로에서도 도달한다. 새 설치본의 Runtime만으로 기준을 찾을 수 있고 source 프로젝트 메모리에 의존하지 않는다.
- C4. 마지막 점검 이후 major 1개 이상 또는 확인 가능한 minor만 5개 이상이라는 기존 제안 기준을 안내용으로 정리한다. minor 기본 현황 표시 생략·사용자 명시 요청 우선·자동 점검 실행 금지를 유지한다. 점검 마커·작업 종류/완료 근거가 없거나 같은 날 선후관계가 모호하면 정확한 횟수나 도래 여부를 추정하지 않는다. 생성일·폴더명을 완료 시각으로 사용하지 않는다.
- C5. 필요한 완료 이력만 선택 참조하고 done을 INDEX에 재등록하거나 이력 내용을 변경하지 않는다. 기존 active/hold 행·정렬·과거 Layer 2 마커를 보존한다. 실제 Layer 2 점검 완료 시에만 기존 형식의 마커를 기록하는 실행 경로를 명시하고, 제안·중단·미완료 시에는 기록하지 않는다.
- C6. 회귀 검사는 실제 트리거→파일/섹션 연결과 이동한 보호 규칙의 접근 가능성을 확인한다. 크기·기존 승인/복구·minor 직접 경로·계약 앵커·source/dist parity 검사 및 전체 기존 테스트가 통과한다. 대상 섹션 삭제/이름 변경뿐 아니라 소비 경로의 출발 참조 삭제/오지정도 실패로 드러나는 음성 fixture를 포함한다. 실제 source/dist 검사와 fixture는 같은 입력 가능한 검사 함수를 사용하며 원본 Runtime에 실패를 주입하지 않는다.
- C7. source/dist·개발자 문서·Layer 2 설명·프로젝트 아키텍처의 정본 참조가 일치한다. 구현과 독립 검증의 결과·한계·남은 문제를 기록한다.

### 사용자 결정
두 이슈 해결의 계획서 작성을 요청했고 독립 비평 반영 후 “작성한 계획서대로 구현 진행해줘”로 현행 계획의 구현을 명시 승인했다. 계획 작성 한정은 이전 요청의 범위이며 현재는 이 계획의 Runtime·회귀 검사·문서 동기화를 진행한다.

### 변경 불가 제약
계획 명세·승인해시·상태 전이·critical gate·승인 복구 우선·사용자 완료 확인·증거 보호·대화 미상속 검증을 유지한다. 기존 사용자 변경분을 보존한다. dist는 sync-runtime으로만 갱신한다. 과거 이력과 immutable release는 재작성하지 않는다.

### 에이전트 가정
- 상세 절차를 기존 detail로 옮겨도 해당 시점의 필수 로드 연결을 함께 고치면 의미를 보존할 수 있다. 참조 검사만으로 실제 모델의 준수까지 보장할 수는 없다.
- 현재 크기 초과는 2,052바이트다. 계획/이력 상세 3,162바이트와 실행 TODO 상세 463바이트를 옮기고 짧은 요약·트리거를 남기면 기준을 충족할 여지가 있다. 구현 전에 메모리상 시뮬레이션으로 여유를 확인하며 기준 미달이면 보존 원칙 안에서 배치를 다시 검토한다.
- 기존 주기 설명은 일부 프로젝트 메모리에만 남아 있고, 완료 시각 근거는 모든 과거 작업에 보장되지 않는다. 정확한 전체 누적 카운터가 존재한다고 가정하지 않는다.

### 결정 대기 항목
없음. 아래 배치·집계 불확실성 처리는 검토 가능한 설계안이며 구현 승인 전에 사용자가 수정할 수 있다.

### 작업 분류 판단 근거
파일 변경으로 복구 가능하고 외부 시스템·보안·영구 데이터 변경은 없다. 다만 공통 실행 규칙의 정본·필수 로드와 완료 후 행동을 재배치하며 경로 누락은 기존 텍스트 검사로 발견하기 어렵다. 설계 판단이 필요해 major로 분류한다.

## 선택 문서
추가 역할 문서 없음. 요구사항·설계·실행 순서·검증 기준을 이 plan에서 관리한다. 독립 비평/구현 검증 산출물과 의미 있는 변경의 changelog는 기존 절차에 따라 작성한다.

## 설계 기준

### 사전 조사
- 현재 core는 36,783바이트, 테스트 기준은 34,731바이트 미만이다. 기존 언어·전제 확인 규칙을 삭제해 크기를 맞추지 않는다.
- core의 “계획서와 변경 이력 관리” 9개 상세 bullet은 3,162바이트, 실행 TODO 상세 문단은 463바이트다. 상세 절차 이동의 우선 대상이다.
- layer1_design/implement/review/discovery, session_protocol, detail의 재개 경로 및 계획 템플릿들이 현재 core의 같은 관리 항목을 참조한다. core에 호환 진입점·짧은 불변식을 남기고 이 소비 경로를 실제 detail 정본으로 연결해야 한다.
- “Layer 2 현황 표시”는 트리거만 존재하고 대상 섹션은 없다. 프로젝트 architecture의 주기 문장을 설치 Runtime에서 발견할 수 없다.
- tests/test_structure_loading.py의 수동 ROUTE_CONTRACTS는 현재 Layer 2 참조를 포함하지 않아 239개 검사 중 크기 실패와 별개로 누락을 놓쳤다.
- TOML contract는 core의 agent-behavior-rules·user-burden-minimization·major/minor-stage-model 및 detail의 agent-rules-detail 앵커를 참조한다. 이 소유 경로·앵커·binding marker는 이동하지 않는다.

### 공통·상세 정본 배치
1. core에는 plan=현재 기준/changelog=변경 이력, 승인·실패 증거 보존, 상세 정본을 읽는 시점의 짧은 요약을 유지한다. 상세 파일 로드 표에 계획 생성/의미 변경/검증 진입/재개 시 detail의 “계획서와 변경 이력 관리”를 읽도록 연결한다.
2. 기존 detail에 같은 제목의 실제 관리 섹션을 두고 9개 bullet과 실행 TODO·운영 안내 분리 규칙을 의미 손실 없이 옮긴다. 승인 복구 절차는 기존 섹션을 참조하며 복제하지 않는다.
3. 관련 단계·템플릿·재개 참조는 상세 정본을 직접 가리키거나 core의 명시된 필수 로드 진입점을 통해 도달하도록 정리한다. 어느 방식인지 참조 표로 증빙한다. 단일 갱신 담당자·복구 marker 잔존 시 편집 중단은 문서 편집 전에, 과거 성공의 효력 상실·현재 미확인/실패 노출은 검증 입력 준비 전에 상세 정본에 도달하는지 별도로 확인한다. 같은 변경 단위에서 이미 읽은 규칙을 매 줄 편집마다 다시 읽게 하지 않는다.
4. core의 잘못된 “인라인에 있음, detail 불필요” 문구를 없애고 detail의 “Layer 2 현황 표시”를 실제 대상으로 지정한다. 완료 처리 상세의 major 후속 안내에서 해당 정본을 참조한다. Layer 2의 9개 점검 절차는 기존 inject/layer2_checkpoint.md에 유지한다. 실제 점검 완료 판정 후 INDEX에 기존 마커를 남기는 절차도 inject의 완료 기준/종료 경로에서 상세 정본으로 연결한다. 실제 점검이 끝나지 않으면 마커를 쓰지 않는다.
   - 실제 트리거 표를 정확히 검사할 때 드러나는 기존 재개 제목 불일치는 표의 대상을 현행 detail heading인 “태스크 재개”로 명시해 해결한다. core 본문의 호환 제목 설명을 유지하고 부분 문자열 일치나 숨은 예외로 통과시키지 않는다. 다른 기존 별칭이 발견되면 원문·실제 정본을 대조해 명시적인 참조 정정으로 처리하며 절차 의미는 바꾸지 않는다.
5. 단순 질문/탐색의 경로는 상세 파일 자동 로드를 추가하지 않는다. 이동한 상세 규칙을 일반 기본 입력에 통째로 다시 포함해 크기 축소 효과를 상쇄하지 않는다.

### Layer 2 안내 내용
- 마지막 유효 점검 마커와 현재 완료 작업을 우선 사용한다. 현재 major 완료가 마커 이후임을 확인하면 최소 major 1개라는 근거만으로 한 줄 제안할 수 있으며 전체 done 폴더를 훑어 정확한 총수를 만들지 않는다.
- minor는 기존처럼 표시를 기본 생략한다. 주기 상태를 명시 확인하거나 사용자 요청이 있을 때, 이미 확인 가능한 완료 근거로 minor만 5개 이상을 판단할 수 있으면 제안한다. 근거가 부족하면 집계 미확인으로 남기고 자료 확인을 위해 전체 완료 이력을 재분석하지 않는다.
- 마커 없음·동일 날짜의 순서 불명·종류/완료 시각 누락·잘못된 마커는 추정 횟수를 만들지 않는다. 같은 날 마커 뒤라는 명시 근거가 있으면 그 근거를 쓸 수 있다. 생성일을 완료 시각으로 대체하지 않는다.
- 안내는 짧은 제안이며 자동 점검·실행 게이트·새 작업 생성·마커 추가가 아니다. 사용자가 점검을 요청하면 횟수와 무관하게 현재 규칙으로 수행한다.
- inject/layer2_checkpoint.md 상단의 독립적인 “3~5개 작업” 권고는 상세 안내 정본 참조로 정리한다. 스프린트 종료는 사용자 임의 점검 요청의 예시로 유지하며 별도 자동 실행/제안 조건으로 쓰지 않는다. guidebook과 architecture도 같은 구분을 사용한다.
- 이 설계는 정확한 자동 카운터나 새 상태 저장을 도입하지 않는다. 그 기능이 필요해지면 별도 범위로 다룬다.

### 예상 조용한 결정과 반례
- **작아졌지만 규칙을 못 찾음:** 이동 전후 절차 대응표와 소비 경로별 로드 검증을 수행한다. 실제 트리거의 target을 검사하고 임의 수동 목록에만 의존하지 않는다.
