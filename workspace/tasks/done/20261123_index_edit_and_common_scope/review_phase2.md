# 2차 구현 검증

- 대상은 `index_edit_and_common_scope`다. `task_documents.py inputs --stage review2`가 반환한 `plan.md`와 `changelog.md`, 호출자가 제공한 `review_phase1.md`, 실제 source/dist Runtime, 관련 회귀 검사, 작업 INDEX를 대조했다.
- 판정은 테스트 진행 가능이다. 1차에서 확인한 두 진입점 누락은 실제 지침에서 해소됐다. 경계 사례는 지침 추적과 임시 데이터 대조로 확인했고, 자동 검사와 각 확인 방법의 범위는 아래에 기록했다.

## 검토 결과

### ✅ 정합성 확인

- **I1–I3 | 현재 작업 행과 명시 요청의 경계.** `core/agent_rules.md:77–85,339–345`와 `core/agent_rules_detail.md:151–158`이 세션 시작 조회의 저장 지시와 완료 뒤 일반 유지보수 지시를 제거한다. 대상의 경로·상태·원문을 식별하고 저장 전후 영향을 대조하며, 다른 행의 누락·경로 불일치는 현재 행 처리 조건이 아니다. `inject/layer2_checkpoint.md:75–86`은 전체 대조를 명시적으로 요청한 경우에만 전체를 확인하고 대조·보고만 요청하면 차이만 보고한다. 수정은 INDEX 정리 요청 범위에서만 한다. 실제 INDEX도 Git 기준본과 대조했을 때 이번 작업 행 하나만 추가됐으며 기존 행과 마커 11개가 보존됐다. 처음 관찰한 대상 행의 낡은 진행 요약은 이 검증 중 대상 행에서 제거된 것을 확인했다.
- **I2·I3 | 1차 지적의 완료 재개 누락 해소.** `core/agent_rules_detail.md:198–204`에 일반 후보 선택 전 분기가 생겼다. 사용자나 현재 작업 선택 기록으로 중단 작업을 특정하면 그 작업의 원본·목적지·행만 확인하고, 목적지만 남아 있어도 `core/agent_rules_detail.md:168–177`의 해당 분기를 적용한다. `hooks/code_gate.py`의 `current_task_plan`이 쓰는 `workspace/tasks/CURRENT_TASK` 값은 폴더명으로 해석된다. `hooks/session_start.py`는 기존의 읽기·안내 코드로 남았고, 이 보완은 선택 기록을 확인하는 재개 지침에서 작동한다. 사용자나 선택 기록이 정확한 대상을 식별하지 못하면 done 전체를 탐색하지 않는다.
- **S1·S2 | 1차 지적의 승인 직전 누락 해소.** `inject/layer1_design.md:183–196`에 최종 사용자 결정 반영 뒤, `approve` 앞에서 변경된 공통 plan·선택 설계·검증 기준을 다시 대조하는 지시가 생겼다. `inject/task_documents.md:30–37`과 `inject/layer1_critique.md:19–25,47–57`이 승인 전 선택 기준 및 자기 점검·독립 비평의 직접·간접 사례 의존을 연결한다. `core/agent_rules_detail.md:160–164,430–447`에서 근거 있는 공통 전제와 프로젝트 전용 계약을 보존하고, 계획 전용 minor는 계획·등록까지만 진행한다. 기존 독립 비평 조건과 명세 변경 승인을 그대로 적용한다.
- **V1 | 경계 근거 보완을 확인.** `tests/test_task_index_policy.py:42–97`에서 저장 전 참조·삭제·늦은 참조 변형과 새 재개·승인 직전·전체 정리 경계를 source/dist 양쪽에서 확인한다. `tests/test_structure_loading.py`는 참조가 끊기거나 오연결된 변형, 사본 동일성, core 크기를 포함한다. 아래 표는 1차에서 부족하다고 본 지침 적용 사례를 독립적으로 대조한 결과다.
- **계획·이력·승인.** changelog의 사용자 요청과 승인 문구는 현재 명세의 현재 행 한정·명시 요청 범위에 부합한다. 재개·승인 직전·Layer 2·사례 확인 보완은 이미 승인한 I2·I3·S2·V1을 충족시키며 완료 기준을 축소하지 않는다. 명세 변경 이력 표에 추가 승인 거래가 없고 현재 `reqspec-v1:a0dc9a3e5c02ad9a`가 유효하다. roles-v1 등록은 비어 있고 `.plan-renewal.json`은 없었다. plan의 생략 항목 없음과 실제 설계·검증 섹션이 맞는다. 1차 관찰과 보완 이유는 검증 원본·changelog에 남아 있다.
- **독립 재실행.** `python3 -B -m unittest discover -s tests` 전체 255개 통과. 두 Runtime 참조 계약 검사가 각각 성공했고, 문서 inspect는 오류 0건, 공통 core는 33,381바이트였다. 대상 파일의 `git diff --check`도 통과했다.

#### 직접 대조한 경계 사례

| 입력 또는 경로 | 확인 결과 |
|---|---|
| 실제 INDEX 기준본과 현재 파일, 임시 문자열에서의 대상 행 등록·갱신·삭제 | 대상 행을 각각 제외하면 동일한 보호 영역이 남는다. |
| 최신 원문에 다른 작업 행이 추가되고 그 뒤 대상 행을 삭제 | 최신 원문에서 추가 행을 보존한 편집만 일치한다. 대상 행 원문이 바뀌거나 같은 경로가 중복이면 확정할 수 없어 보류한다. 무관한 경로 불일치는 영향 범위 밖이다. |
| 임시 문자열에서 표 헤더·구분선·빈 줄·예전 마커 삭제 또는 임시 문구 추가 | 행 이외의 원문 차이가 드러났다. 상세 기준은 결과를 확정하거나 이동하기 전에 보류하고 이후 편집을 보존할 수 있을 때만 영향 부분을 복구하도록 지시한다. 정상 완료 마커 추가는 실제 점검 완료 뒤 해당 줄 한 번만 허용한다. |
| 최소 파생 plan → 행 등록 → 원래 작업 종료 | `inject/layer1_discovery.md:80–98`에서 최소 plan, 안전 기준 로드와 행 등록, 행·출처·plan 대조, 원래 작업의 결과 확인·완료 승인을 순서대로 확인했다. 미승인 plan 자체로 등록을 차단하지 않고, plan 누락·읽기 실패로 식별이 모호하면 해당 행을 보존한다. |
| 유효한 완료 승인과 원본만 존재, 행이 이미 없어졌거나 재등록됨 | 원본과 해당 행을 대조한다. 재등록된 현재 행은 안전 기준에 따라 처리하고, 행이 없으면 그 상태를 확인하고 이동한다. 이동이 실패하면 후속 편집을 보존하는 복구만 허용한다. |
| 유효한 완료 승인과 done 목적지만 존재 | 특정한 경로의 승인·행을 확인한다. 행이 없으면 최종 확인, 남아 있으면 해당 행만 정리한다. 원본·목적지 양쪽 존재 또는 부재, 완료 승인 근거가 없거나 모호한 경우에는 보류한다. |
| 공통 계획 본문은 일반적이나 선택 검증 문서가 익명화한 특정 업무 방식을 유일한 합격 조건으로 강제 | 간접 참조도 합격 조건이면 발견되어야 한다. 관찰 가능한 일반 조건으로 바꾸거나 적용 범위를 다시 확인한다. 최종 검토 중 바뀌었다면 승인 직전에 다시 점검한다. |
| 원천 프로젝트를 출처에만 표시하고 합격 기준을 일반 조건에 둠, 또는 재사용 근거가 있는 공통 전제나 프로젝트 전용 업무 계약 | 출처와 정당한 조건을 유지한다. 업무 사실의 등장 여부보다 합격 조건에서 맡는 역할을 판단한다. |

### ⚠️ 주의 필요

- **검사·변경 기록의 표현 범위를 유지한다.** 영구 회귀 검사는 지침의 위치·문구·순서와 일반적인 설치·계약 경로를 검증한다. 위 임시 INDEX 비교는 독립 검증에서 저장 없이 수행했고 완료 재개·출처 범위 사례는 지침을 따라 판정했다. 실제 호스트의 경합이나 모델 준수는 확인 범위 밖이다. changelog의 세션 시작 저장 제거도 `core/agent_rules.md`에서 조회 전 저장 지시를 없앤 변경을 뜻한다. 사용자 보고에서 hook의 쓰기 로직 변경으로 표현하면 근거와 어긋난다.

### 🔍 에이전트 가정 검증

- 두 보완을 분리 추적하면서 하나의 승인·동기화로 검증할 수 있다는 가정은 유효하다. 상세 규칙과 소비 경로가 나뉘고 사본 동일성과 승인 해시를 확인했다.
- 편집 안전 지침이 가역적이고 체크섬과 텍스트 검사로 동시에 쓰는 호스트나 모델 준수를 입증할 수 없다는 가정은 유효하다.
- 세션 시작 안내와 실제 저장 경로를 구분할 수 있다는 가정은 유효하다. 안내 hook에 소스 변경이 없고 실제 편집 전 지침과 후속 절차가 Runtime 문서에 있다.
