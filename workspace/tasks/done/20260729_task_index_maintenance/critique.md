## 비평 결과

### 🚨 실패 시나리오

- **완료 전 정렬 때문에 완료된 행이 active 위치에 남을 수 있다.** Step 2는 태스크 생성·완료 시 “작성하기 전에 완료일 보정 → 만료 제거 → 정렬”을 수행한다고 한다. 완료 처리에서는 그 뒤 상태와 완료일을 `done`으로 바꾸므로, 최종 행은 다시 정렬되지 않는다. 완료 상태/완료일 반영 후에 정리·정렬하는 순서(또는 두 번의 명시적 정렬)가 필요하다.
- **Layer 2 제안 주기가 보존 기간에 의해 바뀔 위험이 있다.** architecture는 Layer 2 마커 이후의 done 태스크를 타입별로 세어 제안하도록 한다. INDEX에서 3개월 지난 done 행을 제거한 뒤에도 이 계산을 `done/` 원본으로 계속 하는지, INDEX의 최근 행만으로 하는지 계획이 명시하지 않는다. 후자가 되면 오래 걸린 프로젝트에서는 major 완료나 minor 5개 완료 사실이 사라져 Layer 2가 제안되지 않는다.
- **완료일이 비정상인 행이 정리·정렬을 멈추거나 영구 보존될 수 있다.** `-` 이외의 빈값, 잘못된 날짜, 미래 날짜, 중복 태스크명에 대한 처리 규칙이 없다. 세션 시작 전에 자동 유지보수를 실행하는 정책이므로 한 행의 파싱 오류가 INDEX 전체 갱신을 막거나, 비교 불가능한 행을 매번 다른 위치로 이동시킬 수 있다.

### ⚠️ 숨은 가정 (파급효과 높은 순)

- INDEX에 없는 done 폴더를 모두 “만료 정리된 정상 이력”으로 간주하면, 이전 버전의 중단·충돌·수동 편집 때문에 최근 done 행이 누락된 경우도 영구적으로 복구하지 않는다. 이는 재등록 방지와 데이터 복구 중 어느 쪽을 우선할지에 관한 정책 결정이다. 최소한 행이 없을 때 완료일을 신뢰할 수 있는 원천이 없는 이유와, 최근 누락을 허용하는 의도를 명시해야 한다.
- 완료일 보정은 “INDEX를 처음 참조하거나 작성하는 시점”에 실행되지만, 실제로 그 시점을 기억하는 영속 표식은 없다. 행을 보정하면 재실행은 멱등이지만, 보정 중 실패해 일부 행만 기록된 뒤 다음 실행일이 달라지면 동일한 과거 이력이 서로 다른 완료일을 받는다. 한 번의 작업에서 계산한 기준일을 모든 대상 행에 고정하고 원자적으로 저장할지 결정이 필요하다.
- 정렬 순서와 동률 시 태스크명 오름차순은 사용자 요청에 없는데 Open Questions를 “없음”으로 둔다. 특히 태스크명은 날짜와 달리 변경·중복될 수 있으므로, 재현 가능한 2차 키로 태스크 폴더명/ID를 쓸지 사용자 선호 정렬을 확인할지 명시해야 한다.
- “프로젝트 실행 시점의 현지 날짜”는 실행 에이전트/호스트의 시간대를 뜻한다. 협업자가 다른 시간대에서 같은 저장소를 열면 경계일에 다른 결과를 커밋할 수 있다. 프로젝트 시간대 또는 날짜 산출 기준을 고정하지 않는 한 정책은 설치 환경에 종속된다.

### ❓ 미해소 비가시적 위임

- major·minor 완료 승인 뒤 완료일을 기록할 정확한 책임 지점이 파일 목록만으로는 완결되지 않는다. major의 완료 승인/`done` 이동 절차가 `agent_rules.md` 안의 어느 순서에서 행 갱신을 수행하는지, 이동 실패 시 완료일 기록을 되돌릴지 구현자에게 위임돼 있다.
- 정리 대상이 표의 `상태=done` 행으로만 한정되는지, 상태 값이 대소문자·공백·미지 값인 행은 어떻게 처리할지 정해지지 않았다. 자동 삭제 정책에서 분류 실패 행을 보존·경고·차단 중 무엇으로 할지는 안전성에 직접 영향을 준다.
- 신규 설치와 업그레이드 설치의 초기 적용 시점이 분리돼 있지 않다. architecture상 업그레이드는 `.mpa-workspace/`를 덮지만 `workspace/`는 보존한다. 따라서 기존 설치 프로젝트의 보정은 업그레이드 실행 중이 아니라 다음 세션의 규칙 실행에서 일어난다. 이 지연과 첫 세션 이전의 INDEX 상태를 허용하는지 명시해야 한다.
- dist 동기화와 `.mpa-version` 증가의 검증 기준이 없다. 버전 값, 동기화 순서, 실패 시 재실행 절차를 정하지 않으면 배포본과 설치본이 정책은 같아도 버전상 불일치한 상태를 남길 수 있다.

### 🔧 구조적 문제

- Step 4는 done 재등록만 다루고 architecture의 Layer 2 트리거 계산 원천을 갱신·보존한다고 명시하지 않는다. Layer 2는 메타 통치 워크플로우이므로, “INDEX는 캐시, done 폴더는 이력 원본”이라는 PRD에 맞춰 카운트 원천과 마커 이후 범위를 구체적으로 적어야 한다.
- 검증은 현재 INDEX와 날짜 예시에 의존해 실제 설치·업그레이드 경로를 검증하지 못한다. 최소한 새 설치, 기존 `workspace/`를 보존한 업그레이드, 첫 세션의 보정, 그리고 같은 날짜에 재실행했을 때의 멱등 결과를 나눠 확인해야 한다.
- 유지보수 연산의 단일 쓰기 경계가 없다. 세션 시작·생성·완료·Layer 2가 각각 INDEX를 수정할 수 있으므로, 한 실행에서 `상태/완료일 갱신 → 보정 → 만료 제거 → 정렬 → 마커 보존 → 단일 저장`의 순서를 공통 절차로 정의하지 않으면 부분 실패나 동시 실행에서 중복·비정렬 행을 남길 수 있다.
