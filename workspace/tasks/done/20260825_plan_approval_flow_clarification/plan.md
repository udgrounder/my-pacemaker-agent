# 작업 계획서: 사용자 결정 질문과 계획 검토·구현 승인 절차 명확화

## 요구사항 명세

### 요청 기준

계획서를 작성할 때 사용자 결정이 필요한 사항을 찾았더라도, 질문하지 않고 다음 단계로 넘어가는 경우가 있었다. 사용자와 합의한 절차를 Runtime 규칙에 명확히 반영한다.

### 목적

요구사항 명세는 사용자의 의도를 명확히 하는 계약으로 유지하고, 그 밖의 계획·실행 판단은 명세가 맞다는 전제에서 Agent가 수행하게 한다. 질문은 구현 방법을 고르게 하는 것이 아니라 원하는 결과·우선순위·범위·완료 기준·위험 제약을 확인한다. 의도의 공백·모순·실현 불가 제약을 발견하면 발견 내용·영향·권장 보완안·필요한 확인을 알리고 명세를 보완한다. 답변을 반영했거나 질문이 없으면 에이전트 가정과 근거를 계획서에 기록해 즉시 계획서를 작성한다. 작성 중 새 사항도 명세를 바꾸거나 의도의 결함을 드러낼 때만 질문·해시 갱신 대상으로 승격한다. 위험 기준 충족 시 독립 비평을 구현 승인 전에 반영하고, 최종 검토에서는 조용한 결정·미해소 반례를 정보와 위험 고지로 제시한 뒤 명시적 구현 승인을 받도록 절차와 상태 전이를 일관되게 만든다.

### 범위·제외 범위

- 범위: major 설계 절차의 요구사항 명세와 Agent 수행 영역의 경계, 의도 확인 중심의 질문 방향·내용, 의도 공백·모순·실현 불가 제약의 고지·보완, 계획서 작성 전 조건부 질문·가정 기록·즉시 계획서 작성, 작성 후 명세 변경 여부 판별, 독립 비평 적용·기록, 최종 조용한 결정·반례의 정보성 제시, 계획서 파일 저장 시점, `설계 중`·`설계 완료` 상태 의미와 재개 경로, 사용자 대면 구현 승인 문구, 관련 사용자 가이드의 동일 흐름을 정비한다.
- 제외 범위: `사용자 결정`·`결정 대기 항목`의 plan 구조 변경, 요구사항 명세 해시 알고리즘·검증 범위 변경, 신규 hook 또는 결정 대기 항목의 기계적 검사 추가.

### 완료 기준

- 요청 해석에서 사용자 결정이 필요할 때만 질문·답변 대기하고, 없으면 그 질문 단계가 절차상 즉시 통과함이 명시된다.
- 계획서 작성 전 확인이 끝나면 에이전트 가정과 근거를 계획서에 기록하고, 별도 계획서 작성 승인 없이 작성함이 명시된다.
- 사용자 결정이 없을 때는 질문만 생략하고 즉시 계획서를 작성함이 명시된다.
- 계획서 작성 중 새로 드러난 사용자 결정은 질문으로 해소하고, 답변을 요구사항 명세의 `사용자 결정`에 반영한 뒤 최종 계획서 검토로 진행함이 명시된다.
- 새 사항은 사용자 의도를 바꿀 때만 사용자 결정·해시 갱신 대상으로 승격하고, 그 밖의 판단은 Agent가 수행함이 명시된다.
- 질문은 구현 방법이 아닌 사용자 의도를 확인하며, 의도의 공백·모순·실현 불가 제약을 발견하면 영향·권장 보완안과 함께 명세를 보완함이 명시된다.
- 위험 기준 충족 시 독립 비평을 구현 승인 전에 수행·반영하고, 최종 검토의 조용한 결정·반례는 정보와 위험 고지로만 제시함이 명시된다.
- `설계 완료`은 완성된 계획서를 검토하고 조용한 결정·미해소 반례를 제시하며 명시적 구현 승인을 기다리는 상태로만 사용된다.
- 승인 대상과 해시가 `요구사항 명세`임을 유지하고, 실행 계획·조용한 결정에는 별도 해시 검사를 추가하지 않는다.
- Runtime 규칙과 가이드의 상태 재개 설명이 위 흐름과 모순되지 않는다.

### 사용자 결정

- 계획서 작성 전: 요청 해석에서 사용자 결정이 필요한 항목이 있을 때만 질문한다. 답변을 반영했거나 사용자 결정이 없으면, 에이전트 가정과 근거를 계획서에 기록하고 즉시 작성한다. 별도 계획서 작성 승인은 받지 않는다.
- 사용자 결정의 기록 위치: 사용자 답변은 `## 요구사항 명세 > ### 사용자 결정`에 반영한다.
- 계획서 작성 후: 새로 드러난 사용자 결정이 있으면 질문으로 해소한 뒤, 조용한 결정·미해소 반례를 보여 주며 계획서 검토를 요청하고 그 계획에 따른 구현 승인을 받는다.
- 질문·검토 경계: 사용자 의도를 바꾸는 사항만 `사용자 결정`과 해시 갱신 대상으로 삼는다. 그 밖의 조용한 결정·반례는 Agent 판단의 근거와 위험 고지로만 제시한다.
- 해시 범위: 승인해시는 사용자 요청과 관련된 `요구사항 명세`만 기준으로 유지하며, 실행 계획 및 그 밖의 도출물에 별도 해시 검사를 추가하지 않는다.

### 변경 불가 제약

- major의 구현 시작은 계속 사용자 명시적 승인 뒤에만 가능하다.
- minor 경량 흐름의 기존 승인 규칙은 이번 변경으로 확장하거나 강화하지 않는다.
- `.mpa/runtime/` source만 수정하고, 구현·검증 후 정식 동기화 절차로 `dist/.mpa/runtime/`을 갱신한다.

## 실행 계획 (Implementation Plan)

### 사전 조사

- `layer1_design.md`의 1단계가 `설계 완료`을 설정하고 질문을 나중에 수행하는지, `agent_rules.md`와 `session_protocol.md`가 같은 상태를 구현 직전으로 해석하는지 대조했다.
- `plan_hash.py`는 요구사항 명세 checksum과 상태 전환만 담당하며, 사용자 합의대로 변경 범위에서 제외한다.

### 구현 단계

- [x] Step 1 — `inject/layer1_design.md`의 major 설계 절차를 재배치·정정한다: 요청 해석에서 사용자 결정이 필요하면 먼저 질문하고, 답변을 반영했거나 사용자 결정이 없으면 에이전트 가정과 근거를 계획서에 기록해 즉시 작성한다. / 이유: 필요한 사용자 판단만 계획서 작성 전에 확인하고, 이미 요청된 계획서의 작성을 별도 승인 관문으로 만들지 않는다.
- [x] Step 2 — 계획서 작성 중 새로 생긴 사용자 결정은 질문으로 해소해 `사용자 결정`에 기록하고, 그 전까지 `설계 중`을 유지하도록 정비한다. / 이유: 최초 요청에서 보이지 않던 가치 판단도 구현 승인 전에 사용자 권위로 확정한다.
- [x] Step 3 — 사용자 결정이 해소된 완성 계획서 작성 뒤에만 `설계 완료`으로 전환하도록 명시하고, 계획서 검토·조용한 결정·미해소 반례 제시와 명시적 구현 승인 요청의 순서·문구를 정비한다. 사용자 대면 문구는 “결정사항을 반영해 계획서를 보완했습니다. 계획서를 검토하시고 구현을 승인해주시면 구현을 진행하겠습니다.”를 기본으로 한다. / 이유: `설계 완료`의 의미를 최종 계획 검토와 구현 승인 요청 단계로 일치시킨다.
- [x] Step 4 — `core/agent_rules.md`와 `core/session_protocol.md`의 상태 표·재개 안내를 수정해 `설계 중`에서는 조건부 질문 해결·계획 작성 재개를, `설계 완료`에서는 계획 검토와 구현 승인만 수행하도록 맞춘다. / 이유: 세션을 재개해도 어느 질문 또는 승인 단계인지 잃지 않으며, 계획서 작성과 구현의 승인 대상을 구분한다.
- [x] Step 5 — `guidebook/guidebook.md`의 계획 수립·재개 설명을 Runtime 계약과 같은 순서로 고치고, source 규칙 간 참조를 대조한다. / 이유: 사용자 문서가 실제 동작과 다른 상태 전이를 안내하지 않게 한다.
- [x] Step 6 — 관련 텍스트 계약을 검토하고 기존 단위 테스트를 실행한 뒤, `release_manager.py sync-runtime`으로 source Runtime과 dist Runtime을 동기화·검증한다. / 이유: 설치 대상 Runtime에도 같은 절차가 배포되며, 해시·minor 계약이 의도치 않게 바뀌지 않았음을 확인한다.

### 예상 조용한 결정

- 질문 없는 경우의 처리: 사용자 결정 질문만 생략하고, 에이전트 가정과 근거를 계획서에 기록해 즉시 작성한다. / 권장: 불필요한 질문과 중복 승인 관문을 모두 없앤다.
- 조용한 결정의 최종 검토: 사용자 가치 판단으로 승격할 필요가 없는 구현상 권장안은 계획서 검토에서 가시화하고, 사용자가 이견이 없을 때 구현 승인으로 진행한다. / 권장: `사용자 결정`과 구현상 판단을 혼동하지 않는다.
- 구현 승인 요청: 질문으로 해소한 결정사항을 계획서에 반영한 뒤 “결정사항을 반영해 계획서를 보완했습니다. 계획서를 검토하시고 구현을 승인해주시면 구현을 진행하겠습니다.”라고 요청한다. / 권장: 사용자에게 현재 반영 결과와 바로 다음 행동을 함께 알린다.

- 질문이 없는 태스크에도 에이전트가 사용자 결정 답변을 기다린다. → Step 1에 포함: 사용자 결정이 없으면 질문을 생략하고 즉시 계획서를 작성한다.
