# 독립 계획 비평

대상: `plan.md` — 역할별 작업 문서와 독립 작업지시서 도입
검토일: 2026-10-14
입력: 해당 plan, project_identity, architecture, layer1_critique, _agent_execution_priority. plan_hash 최초 승인 및 layer1_review 1차 전달 부분만 제한 탐색했다. 설계 대화는 전달받지 않았다. Runtime 변경·실제 모델 호출은 수행하지 않았다.

## 전체 판정

**보완 필요.** 아래 네 실행 경계를 계획에 구체화한 뒤 구현 승인 대상으로 제시해야 한다. 특히 같은 명세 해시를 유지한 하위 기준 수정과 diff를 통한 1차 입력 누출은 현재 fixture 목록으로 탐지 여부를 보장하지 못한다. 새 승인 체계나 다중 문서 거래를 요구하는 비평은 아니다.

## 주요 문제

### 1. 같은 명세 해시에서 하위 문서 변경을 놓칠 수 있다

- 대상: 문서 구성 식별·기준 연결, 검사·호환·전환, 반례 5.
- 근거: 하위 기준은 reqspec-v1 승인해시이고 helper는 파일/형식/연결만 검사한다. 내용 대응 검토 후 표시하지만 verification 판정 기준 또는 design 계약이 이후 수정될 때 그 확인을 무효화하는 규칙은 없다. 구현/검증 문서 편집은 명세 해시를 바꾸지 않는다.
- 실패 시나리오: 검토된 verification의 실패 사례 삭제 또는 design 계약 변경 → 기존 기준 해시 유지 → 재개 검사 통과 → 예전 내용 대응 확인에 의존해 실행.
- 심각도: 높음.
- 보완안: 하위 계약/검증 기준 변경 시 대응 확인을 무효화하고 메인이 다시 대조하는 규칙을 둔다. 진행 체크 변경은 제외한다. 확인한 내용의 버전 또는 확인 후 변경 여부를 최소한으로 식별하고 단순 해시 복사를 인증으로 쓰지 않는다. 같은 상위 해시에서 검증 기준 축소·설계 계약 변경·진행 체크만 변경하는 fixture를 추가한다. 명세 변경 발견 시에만 기존 사용자 승인 절차로 반환한다.

### 2. 섹션 읽기 제한만으로 diff의 완료 설명 누출은 막히지 않는다

- 대상: 역할별 읽기 범위의 1차 입력, 구현 4·5·7단계, 격리 검증.
- 근거: 1차에 실제 diff·소스를 전달하면서 implementation 진행/완료 주장, work 결과, changelog, plan 진행 요약은 배제한다. diff 대상 파일/본문 제한은 없다. 현재 layer1_review는 변경 소스 목록을 git diff 또는 plan 수정 대상으로 추출한다.
- 실패 시나리오: 전체 diff에 plan 진행 요약·implementation·work 결과 포함 → 검증자가 요구사항 판정 전에 성공 주장과 선택된 증거를 읽음. 단일형에서는 승인 섹션과 완료 설명이 같은 파일이므로 파일 단위 제외도 불가능하다.
- 심각도: 높음.
- 보완안: 1차 diff는 실제 제품/Runtime 변경 대상으로 제한하고 작업 기록 파일을 제외한다. plan은 승인 명세·핵심 결정의 지정 섹션만 전달/읽고 단일형 검증 기준도 결과 섹션과 분리한다. 작업 문서 자체가 변경 대상이면 계약 검토에 필요한 범위만 별도 제공한다. 완료 주장에 식별 문구를 넣은 split/단일 fixture로 프롬프트뿐 아니라 실제 읽기·diff 출력에도 문구가 없는지 확인한다. 전체 실행 기록은 2차에서 읽는다.

### 3. 최초 승인 후 연결 미완료의 재개 규칙이 부족하다

- 대상: 공통 helper 연결, approve 후 metadata 갱신.
- 근거: approve와 audit/재개가 같은 helper 결과를 사용하며 하위 기준명세는 승인 뒤 기록한다. 현재 approve는 설계 완료에서 상태/해시를 한 번에 저장해 구현 중으로 전환하고 같은 approve 재실행은 거부한다. 계획에는 갱신 실패 후 보류만 있고 재개 동작은 없다. 최초 approve는 plan 단독 원자 교체이므로 renew-spec의 plan/changelog 거래와 구분해야 한다.
- 실패 시나리오: 승인 전 helper에 승인해시 연결까지 요구하면 최초 승인 불가. 반대로 최초 승인 뒤 한 문서만 갱신되고 중단되면 구현 중이지만 실행 준비 미완료로 남음. approve 재호출이나 상태 되돌리기로 해결하면 기존 승인 경계와 충돌한다.
- 심각도: 중간.
- 보완안: 승인 전 검사(구성·필수 문서·초안 대응)와 실행 전 검사(승인 정본·복구 잔존·필요한 기준 연결)를 구분한다. 승인 후 연결 미완료는 상태/해시를 보존한 채 내용 대조와 빠진 metadata 저장만 재개한다. 최초 승인 직후 중단·첫 하위 문서 저장 후 중단·재개 성공 fixture를 renew-spec 중단 fixture와 별도로 추가한다. 기본 hook 강도는 유지하고 워크플로우 실행 보류로 처리한다.

### 4. work의 실제 사용과 optional/단일형 기준 경계가 검증에서 빠졌다

- 대상: 독립 작업지시서, 문서 구성 식별·기준 연결, 활용 fixture.
- 근거: work는 실제 위임 전에 만들고 상위 plan/기준명세를 요구하지만 활용 완료 기준과 증빙은 주로 구현자·검증자 역할 문서를 다룬다. work 전달→지정 산출물 수령 경로는 구체화하지 않았다. 하위 기준은 reqspec-v1으로 설명하면서 legacy 작업은 단일형으로 유지한다. optional은 실제 존재하는 문서만 목록에 연결하여 삭제 시 필요한 입력이 목록에서도 빠질 여지가 있다.
- 실패 시나리오: 템플릿만 생기고 실제 독립 호출은 전체 plan과 구두 지시를 계속 사용함. 또는 legacy work 기준을 맞추려고 불필요한 명세 전환을 요구함. 등록된 work/design 삭제·기준 불일치가 필수 두 문서 검사에서 누락돼 해당 실행을 계속함.
- 심각도: 중간.
- 보완안: 기존 독립 비평/검증 또는 읽기 전용 탐색 중 한 경로를 work 작성→최소 입력 전달→지정 산출물→메인 통합의 예정 fixture로 명시한다. 담당이 work로 선행 조건·허용 범위·상위 요구사항 연결을 파악하는지 판정한다. optional은 생성 여부만 선택이며, 실행 입력으로 선택된 뒤 누락/불일치하면 그 실행을 보류한다. single reqspec의 work 허용과 legacy의 기존 기준 사용 또는 제한을 명시한다. 자동 위임 도구 구현은 추가하지 않는다.

## 숨은 가정·구조·절차 비용

- 가장 큰 숨은 가정은 같은 상위 해시가 유지되면 하위 내용 대응 확인도 계속 유효하다는 것이다(문제 1).
- 구현 중 조용한 결정 후보는 최초 승인 검사/연결 복구(문제 3), optional 필수성 및 legacy work 기준(문제 4)이다.
- 명세·상태의 plan 정본, 이력의 changelog 정본 자체에는 추가 직접 충돌을 발견하지 못했다. 다만 연결 복구에서 승인 상태를 되돌리거나 별도 승인 권한을 만들면 architecture와 충돌한다.
- 새 major 3종이라는 합의는 재결정 대상으로 삼지 않았다. 보완 확인은 매 세션 전체 문서 재검토가 아니라 계약 내용 변경 및 해당 역할 진입 시에만 수행해야 한다. work 활용 fixture가 실제 최소 입력의 충분성을 보이지 못하면 템플릿 완성만으로 활용 완료를 판정하지 않는다.
