## 요구사항 명세

### 요청 기준

사용자는 plan.md를 최소한으로 항상 유지하고, major/minor와 무관하게 필요한 경우에만 implementation.md/verification.md/ui_design.md를 추가하며, 소프트웨어 설계·실행 계획·진행 기록은 분리 시 implementation.md의 섹션으로 통합하는 구조를 원한다. 또한 문서 타입과 실제 작업의 독립성에 따라 필요할 때 서브에이전트로 실행하는 구조를 원한다. 기본적으로 역할 문서 자체를 담당의 실행 입력으로 사용한다. 다만 작업이 커서 분할되거나 독립 조사가 커지고 자료/결과를 별도 관리할 이익이 있으면 작업 문서와 하위 폴더를 추가할 수 있다.

### 목적

다른 프로젝트에 제공하는 재사용 가이드·템플릿의 개선을 목적으로, 우선 현재 작업에서 요구사항·승인·진행 상태의 공통 정본을 유지하며 구현자와 검증자에게 필요한 입력을 분리한다. 문서 자체에 담당 범위·입력·선행 조건·완료 조건을 담아 필요한 역할만 독립 서브에이전트로 실행할 수 있게 하고, 작은 작업의 문서 부담은 늘리지 않는다.

### 범위·제외 범위

- 범위: 문서별 소유·생성 조건·읽기 범위·상태 정본, 단일/분리 형식 템플릿, 단계별 지침과 최소 문서 검사, 승인·재개·검증·완료의 호환, 테스트·문서·Runtime 동기화.
- 범위: 모든 작업에서 plan.md를 최소한으로 항상 유지한다. major/minor 분류는 문서 수를 강제하지 않으며 implementation.md/verification.md는 필요한 경우만 추가한다. 분리하지 않은 구현·검증 내용은 plan의 해당 섹션에 필요한 만큼 기록한다. 역할 문서별 메인/서브에이전트 실행 판단·최소 입력·산출물 위치를 정의한다.
- 범위: 화면 설계가 필요한 작업은 ui_design.md를 선택 추가한다. implementation.md의 소프트웨어 설계와 구분하고 기존 Figma/화면 이미지 등 디자인 원본을 연결한다.
- 범위: 필요 시 현재 작업 내부의 하위 작업/조사 폴더와 최소 작업 문서를 허용하고 상위 plan 연결·의존성·담당·산출물을 관리한다. 모든 작업에 고정 하위 폴더나 지시서를 강제하지 않는다.
- 범위: 기존 작업의 단일 형식 지원과 통제된 선택적 전환 절차. 전환 검증은 임시 fixture에서 수행한다.
- 제외 범위: 기존 active/hold/done 일괄 재작성, 자동 모델 선택·호출·비용 계산 도구, 병렬 구현 허용, 사용자 소유 채팅 자동 생성, release/deploy.
- 제외 범위: changelog·기존 critique/review 결과 파일 통합, 새 승인 체계나 문서별 사용자 승인, inspect-only TOML 계약의 실행 제어 확장.

### 완료 기준

1. 모든 작업의 plan.md는 최소한의 요구사항·핵심 결정·승인·생명주기·전체 상태를 유지하는 정본이다. major도 추가 역할 문서가 불필요하면 plan만으로 진행할 수 있고 문서 작성량은 실제 필요한 정보에 맞춘다.
2. implementation/verification/ui_design은 필요한 역할 입력을 분리할 이익이 있을 때만 작성하고 사용 여부·목적을 plan에 기록한다. 역할 내용은 생성한 담당 문서 또는 plan의 해당 섹션 한곳에만 둔다. 선택한 문서가 누락된 경우에는 관련 실행을 보류하고 단일형으로 자동 폴백하지 않는다.
3. 추가 문서가 있으면 상세 내용/진행은 해당 문서에 두고 plan은 요약·링크를 유지한다. 없으면 필요한 구현·검증 내용은 plan에 기록한다. 같은 내용을 두 위치에 복제하지 않는다.
4. 역할 문서에는 담당 역할·명세 연결·필요 입력·선행 조건·담당 범위·완료 조건·산출물 위치를 담는다. 문서 타입과 실제 독립성·분리 이익을 보고 메인 또는 서브에이전트 실행을 판단하며 기본적으로 별도 지시서를 만들지 않는다. 규모·독립성·자료 관리 필요가 커져 분리 이익이 있으면 별도 문서/폴더를 만들고 상위 기준·담당 범위·의존성을 연결한다.
5. 요구사항의 단일 정본·reqspec-v1 승인 계산·plan/changelog 승인 저장 복구·현재 승인/완료 경계를 유지한다. 구현/검증 문서 편집만으로 승인 명세 해시를 재계산하지 않는다.
6. 1차 검증은 승인 요구사항·검증 기준·실제 소스로 판단하며 구현자 완료 설명을 읽지 않는다. 2차는 기존 구현 기록과 1차 결과를 대조한다.
7. 문서 분리/선택적 전환에서 기존 명세·승인해시·실패 증거·변경 이력을 보존한다. 문서 기준이 오래되었거나 필수 연결이 누락되면 관련 실행을 보류하고 실제 승인/명세 변경 여부를 판별한다.
8. 단일/분리/누락/기준 불일치/승인 갱신 중단/검증 전달 경로 fixture가 통과하고 source/dist Runtime이 일치한다.
9. fixture에서 구현자는 구현에 필요한 입력만으로 실행 순서·허용 범위를 파악하고, 검증자는 구현 이력 없이 완료 기준별 판정을 할 수 있다. 문서 분리로 읽어야 할 파일만 늘고 핵심 입력이 부족한 구조는 합격으로 간주하지 않는다.

### 사용자 결정

- plan.md는 최소한으로 항상 유지한다. major도 3종 템플릿을 강제하지 않고 필요에 따라 필요한 역할 문서만 작성한다. 문서 타입에 따라 필요한 역할을 독립 서브에이전트로 실행하되 별도 작업지시서 문서/폴더는 기본적으로 만들지 않되, 큰 작업의 분할이나 독립 조사·자료의 관리 효율을 높일 필요가 있으면 생성한다.
- plan.md만 유지하는 구성이 기본이다. 구현 내용을 분리할 필요가 있으면 implementation.md, 검증 기준을 분리할 필요가 있으면 verification.md, 화면 설계가 필요하면 ui_design.md를 추가한다. 소프트웨어 설계와 구현 실행 내용은 분리 시 implementation에 통합한다. 역할 문서 자체를 필요 시 담당 에이전트의 입력으로 사용한다.
- 위임의 독립성·이익과 현재 창 모델 상한은 관련 자동 위임 작업의 결정으로 유지하며 문서 분리가 새 실행 권한을 부여하지 않는다.
- 첫 적용 대상은 현재 task_role_documents 작업이다. 현재 작업의 문서 구성을 전환하는 실행 요청을 반영한다. Runtime 템플릿/도구 구현과 다른 프로젝트 배포를 완료했다고 해석하지 않는다.

### 변경 불가 제약

- plan.md의 요구사항 명세와 프론트매터 상태·승인 기록은 정본이다. 하위 문서에 별도 생명주기/승인 권한을 만들지 않는다.
- changelog.md는 계획·명세 변경 이력의 정본이다. renew-spec의 plan/changelog 저장·복구 대상을 늘리거나 이력을 implementation으로 옮기지 않는다.
- requirements 완료 기준은 plan에만 둔다. 검증 방법·실행 TODO는 명세를 축소·변경하지 못하며 발견된 명세 변화는 기존 승인 절차로 처리한다.
- 문서 분리와 문서 타입 지정은 독립성 인정·에이전트 호출·병렬 수정 승인 자체가 아니다. 공유 source/memory/plan 변경은 기존 단일 수정자 원칙을 따른다.
- Runtime source만 편집하고 dist는 sync-runtime으로 생성한다. 기존 작업·사용자 변경은 자동 변환하거나 되돌리지 않는다.
- 공개 TOML 참조 계약의 경로·상태·승인 semantics는 이번에 확장하지 않는다. 새 내부 문서 구성 표식은 실행 워크플로우용이며 공개 계약과 분리한다.
