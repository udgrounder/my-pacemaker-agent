# 구현 문서: 역할별 작업 문서 도입

**상위 기준:** [plan.md](plan.md)의 요구사항 명세.
**기준 상태:** 승인된 plan 명세 reqspec-v1:379e670bdd19a370에 연결됨. 실제 판정은 실행 증거와 대조한다.
**담당:** 설계/단일 구현 담당. 요구사항·승인·전체 상태의 변경은 메인이 관리한다.
**사용 이유:** 다중 템플릿·단계 지침·기존 독자 사이의 설계/실행 방법을 plan에서 분리해 담당 입력을 명확히 한다.
**읽을 입력:** plan 프론트매터의 승인/상태/문서구성, 요구사항·관련 핵심 결정·선택 문서 목록, 이 문서의 설계 기준/실행 계획, 검증 방법이 필요할 때 verification.md 및 해당 Runtime source. 승인 전 Runtime 구현은 실행하지 않는다.
**수정 범위:** 아래 수정 대상 파일과 승인된 범위. 다른 작업/승인 명세를 임의 수정하지 않는다.

## 설계 기준

### 사전 조사

- 현재 plan_template.md는 요구사항·실행 계획·실행 TODO·검증 결과를 한 파일에 둔다.
- layer1_implement.md는 plan의 수정 대상 파일·구현 단계·실행 TODO를 읽는다.
- layer1_review.md는 1차에 plan+소스, 2차에 changelog+1차 결과를 전달한다. 결과는 review_phase1.md/review_phase2.md/review_summary.md에 남긴다.
- layer1_critique.md는 plan만으로 구현 의존성·반례를 검토한다. 분리 후에는 설계 결과 문서들을 추가로 읽어야 한다.
- plan_hash.py는 reqspec-v1에서 요구사항 섹션만 계산한다. renew-spec은 plan/changelog 쌍과 .plan-renewal.json 복구를 사용한다.
- session_start.py는 plan 프론트매터·상태를 읽고, code_gate.py는 plan의 선택/승인/완료 상태를 검사한다. 상태 정본을 유지하면 기존 경계를 보존할 수 있다.
- tasks/INDEX는 active/hold 항목의 캐시이고 상세 상태의 정본이 아니다.
- 사용자 요청에 따라 현재 작업에서 선택형 역할 문서 구조를 먼저 사용한다. Runtime 지원 구현 전이므로 존재/연결/내용 인계는 직접 확인한다. 다른 기존 작업은 자동 변환하지 않는다.

### 문서 역할과 생성 조건

| 문서 | 생성 조건·시점 | 내용 정본 | 작성/수정 담당 |
|---|---|---|---|
| plan.md | 모든 작업, 설계 시작; 최소한으로 항상 유지 | 요구사항·핵심 선택 이유·승인·생명주기·전체 상태·선택 문서 목록, 미분리 역할의 최소 내용 | 총괄/설계 담당; 상태·명세 갱신은 메인이 직렬 관리 |
| implementation.md | 설계/구현 내용이 커지거나 별도 담당 입력으로 분리할 이익이 있는 경우, 관련 구현 전 | 설계 기준(구조·인터페이스·데이터·처리 흐름·설계 근거), 실행 계획(변경 파일·의존성·TODO), 진행 기록 | 설계 담당 초안, 승인 후 단일 구현 담당 수정; 기준 변경은 메인 확인 |
| verification.md | 검증 기준이 커지거나 별도 검증 담당 입력으로 분리할 이익이 있는 경우, 관련 검증 전 | 요구사항별 검증 방법·정상/실패/경계 사례·필요 증빙·판정 기준 | 설계 담당 초안·독립 비평 점검, 구현 중 기준 수정은 메인 검토 |
| ui_design.md | 화면 구성/상호작용/시각 기준의 별도 설계가 필요한 경우, 해당 구현 전 | 화면 목록·구성·사용자 흐름·상호작용·로딩/빈 화면/오류/권한 등 상태·반응형/접근성 기준·디자인 원본 연결 | 화면 설계 담당; 요구사항 정합성은 메인 확인 |
| changelog.md | 기존 기준대로 의미 있는 변경 시 | 계획·명세 변경 이력·실제 변경 근거 | 현재 변경 담당 기록, 메인 직렬 정리 |
| critique/review 결과 | 기존 독립 단계 수행 시 | 발견·판정·실제 검증 증거 | 각 검토자; 메인은 결과를 읽고 요약 |

- 구현 TODO는 implementation이 있으면 그 문서에, 없으면 plan의 해당 섹션에 둔다. 검증 기준은 verification이 있으면 그 문서에, 없으면 plan에 둔다. 기존 review 결과 파일의 증거 정본은 유지한다. 추가 문서가 있는 단계의 plan 상태는 요약/링크로만 표시한다.
- verification은 검증 계획이며 결과 모음이 아니다. 이미 통과했다는 주장·구현자가 고른 성공 사례·changelog 요약은 넣지 않는다.
- implementation.md 안에서 설계 기준·실행 계획·진행 기록을 구분한다. 설계 내용은 실행 TODO에 반복 복사하지 않고 해당 설계 항목을 참조한다. ui_design.md는 화면/사용자 경험 설계용이다. 화면이 없거나 기존 화면 기준만 참조하면 충분한 작은 수정에는 ui_design을 강제하지 않는다.
- ui_design.md는 Figma·이미지·프로토타입 등 실제 디자인 결과물을 대체하지 않는다. 원본 위치와 버전/확인 시점, 구현에 필요한 화면·컴포넌트·상태·허용 차이와 시각 검증 기준을 연결한다. 디자인 원본과 충돌하면 임의로 한쪽을 선택하지 않고 메인이 유효한 기준을 확인한다.
- 전역 주입 지침/페르소나는 계속 Runtime 자원이고 이 작업 문서와 역할이 다르다. 작업마다 persona 문서를 복제하지 않는다.

### 문서 구성 식별·기준 연결

- 새 최소 계획 형식은 문서구성: roles-v1과 선택 문서 목록으로 식별한다. roles-v1에서도 추가 문서 목록은 비어 있을 수 있다. single-v1/표식 없음은 기존 단일형으로 해석한다. 알 수 없는 값은 추정하지 않고 안내한다.
- implementation/verification/ui_design은 필요하다고 선택한 문서만 plan에 목적·담당·경로를 등록하고 기본적으로 같은 작업 폴더에서 찾고, 큰 하위 작업/조사는 상위 plan에 등록한 작업 내부 상대 경로로 찾는다. 존재 여부만으로 사용을 자동 결정하지 않는다. 미생성 문서는 검사 대상이 아니지만 선택/등록된 문서가 누락되면 해당 실행을 보류한다. 외부 경로나 상위 폴더로의 임의 참조를 실행 입력으로 자동 따라가지 않는다.
- 설계 중에는 미승인 초안으로 기록한다. 설계 완료 전 plan의 최소 내용과 그 시점 실행 입력으로 선택한 문서의 존재·요구사항 대응·반례·독립 비평을 확인한다. 추가 문서가 필요 없다는 사실을 설계 미완료로 취급하지 않는다. approve 전까지 문서 존재나 계산된 해시를 실행 승인으로 해석하지 않는다.
- 승인 뒤 하위 문서에는 상위 plan 경로와 기준명세(reqspec-v1 승인해시)를 기록한다. 문서 기준 일치는 작성자가 해시를 복사했다는 사실만으로 인정하지 않고 내용 대응을 검토한 후 표시한다.
- renew-spec은 기존 plan/changelog 원자 저장·복구를 유지한다. 명세 갱신 후 하위 문서 대응 검토·기준 갱신이 끝나기 전에는 관련 위임/구현/검증을 재개하지 않는다. metadata 갱신 실패가 승인된 명세 자체를 되돌리거나 새 승인 권한을 만들지는 않는다.
- 같은 명세 해시에서도 하위 문서의 실행/설계/검증 기준이 바뀌면 기존 대응 확인을 무효화한다. 새 템플릿은 implementation의 설계 기준·실행 계획과 진행 기록을 명확히 구분한다. verification/ui_design은 기준 본문을 대상으로 한다. 메인이 대응 검토한 명세 식별+기준 본문 checksum을 plan의 문서 목록에 기록하고, helper는 역할 진입 시 현재 내용과 비교해 변경 여부만 알린다. 진행 체크·결과 기록은 기준 checksum에서 제외하며 기준 내용 변경을 단순 진행 변경으로 숨기지 않는다. checksum 재계산 자체를 의미 검토의 증거로 삼지 않는다. 동일한 내용이 확인되면 매 세션 전체 문서를 다시 비평하지 않는다.
- 역할별 문서가 없으면 plan의 해당 섹션에서 기준을 읽고, 있으면 선택한 문서만 읽는다. implementation만 또는 verification만 또는 ui_design만 추가하는 구성도 허용한다. 선택 문서가 누락되거나 오래되면 plan 내용으로 조용히 폴백하지 않는다.
- 새 분리형 명세의 요구사항·완료 기준에는 안정적인 항목 ID를 부여하고 implementation/verification과 필요한 ui_design은 해당 ID를 참조한다. 기존 승인 작업에 ID를 임의 삽입하지 않는다. 기존 작업의 선택적 전환은 기존 명세의 실제 항목/절을 참조하고 명세 원문을 보존한다.

### 역할별 읽기 범위

| 단계 | 입력 | 배제할 것 |
|---|---|---|
| 설계·계획 비평 | plan, 선택된 implementation/verification/ui_design, 필요한 공통 memory | 설계 대화 상속, 무관한 작업 결과 |
| 구현 | plan 요구사항/승인/핵심 결정, implementation 또는 plan 구현 섹션, 필요한 ui_design·소스; 테스트 구현 시 verification 또는 plan 검증 기준 | 무관한 탐색 결과·전체 과거 대화 |
| 1차 독립 검증 | plan 요구사항/핵심 결정, implementation 또는 plan의 설계 기준 섹션, verification 또는 plan의 검증 기준, 필요한 ui_design/공통 memory, 실제 diff·소스 | implementation 진행/완료 주장, changelog, 2차 결과, 구현 대화 |
| 2차 대조 검증 | plan, 1차 결과, implementation 또는 plan 실행 기록, changelog 및 실제 소스 | 완료 주장을 검증 증거로 자동 인정 |
| 문서 타입별 독립 실행 | 해당 역할 문서, 관련 plan 기준·필요한 공통 입력 | 별도 지시서 파일과 전체 문서 묶음을 무조건 전달 |

- 1차는 implementation 전체가 아닌 사전에 준비된 설계 기준 섹션만 참조하고 실행 체크·진행·완료 주장은 배제한다. 1차는 구현 단계의 체크박스가 아니라 승인 요구사항과 설계 계약의 실제 충족을 판정한다. 단계별 실행 완료 대조는 2차에서 수행한다.
- 1차 diff는 실제 제품/Runtime 변경 대상으로 제한하고 task 폴더의 plan 진행 요약·implementation·changelog·review 결과를 제외한다. 작업 문서 자체가 검증 대상인 변경이라면 계약 검토에 필요한 기준 범위만 별도 제공하고 진행/완료 설명은 제외한다. 프롬프트의 파일 목록뿐 아니라 실제 읽기와 diff 출력도 확인한다.
- plan 진행 요약·단일형 plan에 남은 구현 결과를 1차가 보지 않게 프롬프트의 읽을 섹션을 제한한다. 단일형 호환에서도 기존 changelog 미참조 원칙을 약화하지 않는다.
- 입력 격리는 프롬프트·실제 읽기 범위로 확인한다. 권한 수준에서 파일 접근을 강제로 차단한다고 주장하지 않는다.

### 문서 타입별 실행 분배

| 역할 문서/단계 | 기본 담당 | 독립 실행 판단 |
|---|---|---|
| plan.md의 요구사항·승인·총괄 | 메인 | 사용자 의도·승인·상태 관리는 메인이 유지; 기존 독립 계획 비평은 관련 역할 문서를 입력으로 사용 |
| implementation.md의 구현 | 메인 또는 단일 구현 담당 | 승인된 입력과 구현 책임 전체를 독립 인계할 이익이 있을 때만 서브에이전트; 단순 수정·빈번한 협의가 필요하면 메인 |
| verification.md의 검증 | 해당 검증 역할 | 기존 필수 독립 검증은 유지하고 문서+승인 요구사항+실제 소스로 수행; 추가 검증은 독립성과 이익이 있을 때만 분리 |
| ui_design.md의 화면 설계 | 화면 설계 담당 | 사용자 흐름·화면 요구·디자인 원본이 분리 가능한 입력으로 확정되고 이익이 있을 때만 독립 실행; 구현자와 수시 협의가 필요하면 메인이 조정 |

- 역할 문서 자체에 담당·명세 연결·입력·선행 조건·담당/허용 범위·완료 조건·산출물·문제 보고 조건을 포함한다. 작은 호출은 해당 문서의 섹션/항목과 호출 지시로 한정하고 별도 지시서를 기본 생성하지 않는다. 작업이 커지거나 독립 조사·산출물 관리가 복잡해지면 필요한 문서와 하위 폴더를 생성할 수 있다.
- 문서 타입은 역할을 결정할 단서이고 모든 타입을 자동으로 서브에이전트에 맡기는 규칙은 아니다. 필요한 입력만으로 수행 가능하고 분리 이익이 있으면 분리하며, 독립성이 불명확하면 메인이 처리한다. 기존 필수 독립 검증은 해당 실행 정본을 따른다.
- 문서 타입과 실행 방식은 분리한다. implementation을 분리했더라도 작업에 따라 메인 또는 서브에이전트가 담당할 수 있으며, 서브에이전트 실행 자체만으로 추가 문서를 요구하지 않는다. 별도 문서/폴더 생성은 작업 규모와 독립 관리 필요를 따로 판단한다.
- 선택된 implementation/verification/ui_design은 해당 실행의 필수 입력이다. 누락/기준 불일치는 해당 실행만 보류하고 제거/대체는 메인의 영향 확인·이력 기록을 거친다. 파일 누락 때문에 등록을 자동 삭제하지 않는다.
- 단일형/legacy는 기존 plan의 해당 역할 섹션·기존 승인 방식/원문 참조를 입력으로 사용하며 불필요한 형식 전환을 강제하지 않는다.
- 역할 실행 결과는 implementation의 진행 기록이나 기존 critique/review 결과에 남긴다. 문서별 상태는 진행 표시이고 승인/전체 생명주기 정본은 plan이다.
- 실제 모델 선택 자동화는 기존 별도 작업의 범위다. 이번에는 기존 호출 도구에 역할 문서를 전달하는 지침/fixture만 정의하고, 현재 모델 상한·기존 단일 수정자·전체 구현 책임 인계 제약을 유지한다.

### 큰 작업·독립 조사 분리

- 기본은 현재 역할 문서의 섹션과 호출 지시를 사용한다. 작업/조사의 범위가 커지거나 독립 담당·선행 조건·자료·결과를 별도 관리할 이익이 있으면 상위 작업 안에 하위 폴더를 만든다.
- 예: parts/<id>/ 또는 research/<topic>/에 필요한 최소 작업 기준 문서와 조사 자료/결과를 둔다. 이는 예시이며 고정 폴더명이나 문서 세트를 강제하지 않는다.
- 상위 plan은 전체 요구사항·승인·상태의 정본을 유지하고, 하위 작업 목록에 목적·담당·의존성·상대 경로·결과 연결을 기록한다. 하위 문서는 상위 기준을 참조하고 요구사항을 복제하거나 승인 범위를 확대하지 않는다.
- 하위 작업에도 필요한 역할 문서만 사용한다. 기존 역할 문서로 충분하면 추가 지시서를 만들지 않는다. 현재 작은 문서 전환에 하위 폴더를 실제 생성할 필요는 없다.
- 현재 작업 범위 안의 분리 관리와 별도 승인/생명주기를 갖는 신규 작업 항목은 구분한다. 명세 밖 기능·독립 완료 승인이 필요하면 기존 신규 작업 등록 절차를 따른다.
- 폴더 분리는 문서 관리 선택이다. 파일 수정의 순차/병렬 실행 권한과 모델 상한은 기존 규칙을 따르며 폴더 분리만으로 자동 확대하지 않는다.
- 등록한 하위 입력의 누락·오래된 기준은 해당 실행을 보류한다. 작업 내부 상대 경로만 확인하고 경로 이탈/임의 외부 참조를 자동 추적하지 않는다.

### 검사·호환·전환

- 최소 공통 helper인 hooks/task_documents.py에 구성 판별·등록된 작업 내부 경로·존재/기준 연결 검사를 모은다. 범용 문서 파서·새 저장 DB·자동 변환기는 추가하지 않는다.
- plan_hash audit/approve, session_start, 필요한 code_gate 안내가 같은 helper의 결과를 사용한다. 실패 종류는 형식 미확인/필수 문서 없음/기준 연결 오래됨/명세 복구 미완료로 구분한다.
- 설계 중에는 작성 중 문서 누락을 오류 완료로 취급하지 않는다. 관련 실행 진입에는 plan과 실제 선택된 역할 문서만 검사하고, 승인 이후에는 그 입력의 기준 대응을 확인한다. 기본 hook의 경고/선택된 critical 작업의 차단 정책을 임의 확대하지 않는다.
- 승인 전 검사는 구성·필수 문서·미승인 초안의 대응 확인을 요구하고, 아직 없는 승인해시 연결은 요구하지 않는다. 실행 전 검사는 유효한 plan 승인·복구 잔존 여부·선택된 입력의 기준 연결을 확인한다. 최초 approve는 기존 plan 단독 원자 갱신이고 renew-spec은 기존 plan/changelog 거래이므로 실패/복구 fixture를 구분한다.
- approve 이후 하위 기준 metadata 갱신은 순차 후속 작업이다. 실패하면 문서 연결 미완료로 안내하고 실행을 보류한다. approve의 plan/changelog 거래를 다중 문서 거래로 확대하지 않는다.
- 승인 이후 연결 저장 중단을 재개할 때는 기존 plan 상태/승인해시를 보존한 채 필요한 내용 대조와 빠진 metadata 저장만 수행한다. approve 재호출·설계 완료로의 강제 되돌림·불필요한 재승인으로 해결하지 않는다. renew 중단은 기존 .plan-renewal.json 복구를 먼저 끝낸 뒤 하위 연결을 재개한다. 새 사용자 명세 결정이 생긴 경우에만 기존 승인 절차로 반환한다.
- 의미적 독립성·충분한 요구사항 대응은 에이전트가 판단하고, helper는 파일/형식/연결 같은 결정론적 부분만 검사한다.
- 현재 최초 적용 작업의 문서만 전환하고 다른 active/hold/done은 그대로 유지한다. reqspec-v1 작업을 재개하면서 분리가 필요한 경우에만 기존 이력·증거를 보존한 뒤 요구사항 블록/승인해시는 유지하고 명세 밖 상세를 이동한다. 파일이 모두 저장·확인되기 전 구성 표식을 바꾸지 않는다.
- legacy 본문 해시 작업은 단일형 유지가 기본이다. 단순 파일 이동 때문에 해시를 재계산하지 않는다. 최신 요구사항 형식으로의 전환이 필요하면 기존 승인/복구 절차의 별도 검토를 따른다.
- 완료된 done은 전환하지 않는다. 기존 위임 계획과 TOML 계약 작업의 명세/상태도 이번 도입 구현에서 수정하지 않는다.

### 반례

1. 문서가 여러 개지만 요구사항을 각각 복사해 서로 다름 → 1·2·4단계: plan만 명세 정본, 상세 내용의 소유를 분리.
2. 필요하지 않은 verification 부재를 실패로 처리하거나, 선택한 verification이 빠졌는데 plan으로 진행 → 3·5단계: 선택하지 않은 문서는 요구하지 않고 선택 문서 누락은 폴백하지 않음.
3. renew-spec 성공 뒤 하위 문서 기준 갱신이 실패 → 3·4·5단계: 기존 승인 거래 유지, 실행은 연결 미완료로 보류하고 내용 대응 후 기준 갱신.
4. 1차 검증자가 implementation의 완료 주장에 동조 → 4·5·7단계: 요구사항/검증 기준/실제 소스만 전달, 2차에서 실행 기록 대조.
5. 요구사항은 그대로인데 verification에서 완료 기준을 낮춤 → 1·4·5·7단계: 요구사항별 대응 검사, 기준 축소는 명세 변경으로 반환.
6. major라는 이유로 모든 역할 문서를 생성해 문서 비용 증가 → 2·5단계: 모든 작업은 최소 plan 기본, 필요성과 분리 이익이 있는 문서만 추가.
7. legacy 작업 이동으로 기존 승인해시 깨짐 → 3·5단계: legacy 단일 유지, reqspec fixture에서만 명세 외 이동과 해시 불변 확인.
8. 여러 담당자가 plan/changelog를 동시에 수정 → 1·4·5단계: 역할별 문서 소유·메인 직렬 반영, 단일 구현 책임 유지.
9. 역할 문서만 읽고 전체 시스템 제약을 놓침 → 2·4·5단계: 관련 plan 명세·공통 계약을 최소 입력에 명시하고 범위 밖 결정은 메인 반환.
