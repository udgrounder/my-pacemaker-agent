## 비평 결과

### 🚨 실패 시나리오

#### F1. 모델 변경 후 최초 상한이 사라지거나 현재 상한 초과 에이전트가 계속 실행된다

- 심각도: P1.
- 대상·근거: plan.md:37은 모든 호출에 “최초 메인 창 모델의 상한”을 요구한다. 53행은 최초 상한을 임의 생성하지 않는다고 한다. 그런데 57행은 모델 변경 후 “새 상한으로 재판정”하고 실행 중 중단 기준을 “이전 상한보다 높은” 에이전트로 둔다.
- 실패: 최초 A에서 더 높은 B로 메인이 바뀌면 B를 새 상한으로 적용해 최초 A 제약을 위반할 수 있다. 최초 A에서 낮은 C로 바뀌면 A와 동일한 실행 중 에이전트는 이전 A보다 높지 않아 중단 대상에서 빠진다.
- 판정: 최초·현재 상한 우선순위와 실행 중 중단 기준이 모순된다. 113행의 비전이 직접 허용 관계에서는 단순 min 연산도 정의되지 않는다.
- 보완: 최초 허용 집합과 현재 허용 집합의 교집합을 신규 호출·재시도·재위임에 적용할지 명시한다. 실행 중 대상도 현재 유효 허용 집합으로 검사한다. 모델 변경을 탐지하지 못한 호스트의 한계는 별도로 남긴다.

#### F2. 재위임이 모델 목록을 보존해도 총 동시 수·복구 수·수정자 수가 증가한다

- 심각도: P2.
- 대상·근거: plan.md:125는 재위임 생성 담당을 “원칙적으로 메인”이라고 한다. 127행의 1회 복구와 130행의 동시 2개가 전체 트리 기준인지 각 호출 기준인지 없다. 108행에는 별도 정책 재시도 한도도 있다.
- 실패: 자식이 예외적 재위임을 허용됐다고 해석하고 각 자식에 2개·1회 예산을 적용하면 총 호출 수가 증가한다. 구현 담당자가 자식 구현자를 만들면 부모가 멈추지 않은 상태에서 수정자가 겹친다.
- 판정: 최초 상한 전파만으로 예산·단일 수정자 제약은 보존되지 않는다.
- 보완: 기본 자식 직접 생성 금지 여부를 확정한다. 재시도와 동일 모델 재수행을 합산한 총 최대 1회, 트리 전체 활성 수, 구현 소유권 인계와 부모 수정 중단을 명시한다. 설치 정책은 기본 최대치를 낮추기만 하는지도 정의한다.

### ⚠️ 숨은 가정 (파급효과 높은 순)

#### A1. 순수 판단 도구에 넣는 “확인된” 호스트 입력의 출처가 명확하다

- 심각도: P2.
- 대상·근거: plan.md:89–90은 기능 지원·기본 상속·공식 설명을 조사했다. 99–102행은 메인 모델·실제 해석될 모델 확인을 요구한다. 111행의 도구는 호스트 사실을 직접 알아내지 않고 입력 확인 상태를 검사한다.
- 틀렸을 때: 모델 이름 추정이나 요청 모델을 실제 모델로 간주한 값이 확인 입력으로 들어가면 순수 판단 테스트는 통과해도 실제 상한은 입증되지 않는다. 종료 후 미확인 표시는 이미 발생한 호출을 복구하지 않는다.
- 판정: 강제 차단 제외 자체는 결함이 아니다. 불명확 호출의 축소 경로도 계획에 있다. 남은 문제는 어떤 증거가 사전 확인으로 충분하고 어떤 상태가 unknown인지 구현자가 정하게 되어 있다는 점이다.
- 보완: 도구 구현 전에 입력별 허용 증거 출처·확인 시점·역할/호스트 일치·unknown 판정을 정의한다. 문서상 기능 지원, 사전 설정 해석 확인, 실제 호출 메타데이터 확인을 구분한다. 현재 호스트에서 실제 모델이 노출되지 않으면 테스트 성공만으로 확인됐다고 처리하지 않는다.

#### A2. 근거와 확인일이 있는 직접 허용 목록은 사용자의 “하위 모델” 의미를 충족한다

- 심각도: P2.
- 대상·근거: plan.md:38은 이름·가격·출시 순서 추정을 금지한다. 108행은 관계의 근거/확인일을 요구하지만 인정하는 근거 유형·작성 권한은 없다.
- 틀렸을 때: 공식 모델 설명·주관적 품질·실행 성공 중 하나를 근거로 삼아 허용 정책을 활성화하면 사용자 의미와 다를 수 있다. 실행 성공은 가용성 증거이지 상하 관계 증거가 아니다.
- 판정: 관계를 객관 검증한다고 표현할 수 없다. 설치별 명시 정책의 성격을 정해야 한다.
- 보완: 관계는 누가 어떤 승인/출처로 설정하는지 정의한다. 이번 작업은 정책 형식만 제공하는지 실제 설치 정책도 활성화하는지 완료 기준에 적는다. 매 작업마다 사용자에게 모델 선택을 요구할 필요는 없다.

### ❓ 미해소 비가시적 위임

#### D1. “현재 창”과 “최초 창”의 지속 상한 해석이 남아 있다

- 심각도: P1, F1과 동일 원인.
- 대상·근거: plan.md:21·48의 사용자 제약은 현재 창이다. 53·57행은 최초 고정과 새 상한을 함께 선언한다. 70–72행의 Open Questions는 “없음”이다.
- 판정: 사용자 가치 제약의 해석을 구현 기술 세부로 숨겨서는 안 된다.
- 보완: 최초·현재 상한을 모두 보존하는 보수적 해석을 명세와 승인 대상으로 제시하거나, 다른 의미를 원한다면 사용자 결정을 받는다. 매 호출 확인은 필요하지 않다.

#### D2. 하위 모델 운용을 확인하지 못해도 완료하는 범위가 모호하다

- 심각도: P2.
- 대상·근거: plan.md:107은 정책 부재 시 생성하지 않는다. 215행은 실제 호스트 확인을 “가능한 경우”로 둔다. 범위는 JSON schema·CLI·설정 해석 입력·정본·다수 문서·회귀 검사까지 포함한다.
- 실패/영향: 안전 경로가 동일 모델 상속 또는 메인 처리만 남더라도 테스트 성공으로 완료될 수 있다. 사용자가 기대한 하위 모델 효율화는 비활성이고 유지할 체계만 증가한다.
- 판정: 파일 수 자체를 과범위라고 단정할 수는 없다. 현재 설치에서 운용되지 않는 판단 체계를 어디까지 만드는지 완료 의미가 부족하다.
- 보완: 정책 기반 판단 구현 완료와 현재 설치의 하위 모델 운용 확인을 분리한다. 후자가 불가하면 비활성·미확인을 보고한다. 최초 버전에 작업별 선호·retry/concurrency 설정까지 필요한지 줄여 평가한다. wrapper·자동 설치 추가로 해결할 필요는 없다.

### 🔧 구조적 문제

#### S1. 기존 “구현은 쪼개지 않는다”를 단일 동시 수정자와 동일하게 해석했다

- 심각도: P2.
- 대상·근거: architecture.md:213은 “구현은 단일 순차”, “write(구현)는 쪼개지 않는다”고 한다. plan.md:68·123·145·164는 순차 위임을 기존 원칙 유지로 설명한다.
- 판정: 전체 구현 책임자를 한 번 인계하는 것과 구현 하위 작업을 나눠 순차 담당에게 주는 것은 별개다. 기존 문장만으로 후자가 이미 허용됐다고 볼 수 없다.
- 보완: 전체 구현 책임 인계인지 순차 하위 작업 분할인지 명시한다. 분할을 도입하면 기존 규칙의 제한적 변경이라고 적고 architecture·guidebook 정본을 같이 갱신한다. 동시 구현 담당이 하나라는 주장만으로 모순을 닫지 않는다.

#### S2. 안전 확인보다 core 자동 위임 활성화가 먼저 배치된다

- 심각도: P2.
- 대상·근거: plan.md:136–139는 core 자동 허용을 먼저 수정한 뒤 판단 도구·호출 지침을 연결하고 마지막에 호스트 호출을 확인한다.
- 실패: 중간 source를 새 세션이 읽으면 증거 계약과 실패 처리가 완성되기 전에 자동 위임을 적용할 수 있다.
- 판정: 구현 순서가 실행 활성화 순서가 되어서는 안 된다.
- 보완: 정책 정의 → 판단/실패 테스트 → 지침 연결 → 호스트 또는 축소 경로 확인 → core 활성화·동기화 순서를 적거나, 중간 상태에서 새 정책을 사용하지 않는 조건을 둔다.

#### S3. 필수 독립 실행의 모델 확인 불가가 기존 실패 분류에 매핑되지 않았다

- 심각도: P2.
- 대상·근거: plan.md:39·102는 확인 불가 호출 생략, 129행은 기존 절차 우선을 둔다. _agent_execution_priority.md는 도구 없음·격리 불가·호출 실패·산출물 누락과 재시도 규칙만 정의한다.
- 실패: 모델/override 확인 불가를 일시 호출 오류로 취급해 반복하거나 일반 직접 처리 경로로 필수 비평을 대체할 수 있다.
- 판정: 기존 절차 우선 선언만으로 새 실패 원인의 재시도 가능 여부가 결정되지 않는다.
- 보완: 상한·안전 상속·override 확인 불가는 독립 실행 미완료이며 새 확인 자료 없이는 재시도하지 않는다고 명시한다. 비평은 생략 확인, 구현 검증은 자가 검증·미확인으로 매핑한다.
