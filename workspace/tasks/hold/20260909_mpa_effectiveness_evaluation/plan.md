# 작업 계획서: MPA 협업 효과 측정 체계

**파생 출처:** [규칙 정합성과 경량 검증 보완](../../done/20260909_mpa_policy_consistency/plan.md). 선행 작업이 완료되어 설계 준비 상태다. 구현은 별도 승인 후 시작한다.

## 요구사항 명세

### 요청 기준

프로젝트 보완 검토에서 제기된 “규칙 준수와 실제 협업 성과를 별도로 검증해야 한다”는 문제를 다룬다.

### 목적

MPA가 맥락 복구·재작업·품질·절차 비용에 주는 효과를 같은 기준으로 비교할 수 있는 로컬 평가 절차와 집계 도구를 만든다.

사용자가 명시한 “사용자를 필요 이상으로 불편하게 하지 않는다”를 공통 평가 기준으로 삼는다. 단순히 질문 수가 적다는 이유로 좋은 결과로 판정하지 않고, 필요한 판단·품질을 유지하면서 불필요한 개입을 줄였는지 평가한다.

### 범위·제외 범위

- 범위: 대표 시나리오, 결과 기록 스키마, 수동 실행 프로토콜, 로컬 집계 도구, 합성 데이터로 집계 검증, 운영 가이드.
- 제외: 유료 모델/API 자동 호출, 사용자의 실제 프로젝트 데이터 수집, 원격 전송, 장기 실험 수행, 통계적으로 검증된 효과 주장, Runtime에 상시 계측 삽입.

### 완료 기준

1. 문구 수정·설정 수정·버그 수정·다단계 기능·세션 재개·의도 변경의 6가지 시나리오가 있다. 각각 입력, 초기 저장소 상태, 정답/수용 기준, 실패 판정, 중단 조건이 명시된다.
2. MPA 미적용/적용 두 조건은 모델·버전·설정·도구 권한·초기 소스·요청·시간 제한을 맞춘다. 독립 작업 디렉터리/세션을 사용하고 실행 순서를 교차시켜 기억 오염을 줄인다. pilot 권장값은 시나리오별 조건당 3회이며 통계적 확정 근거로 쓰지 않는다.
3. 시간은 작업 시작/종료, 사용자 대기, 실제 실행을 구분한다. 재개 시간은 재개 요청부터 최초로 기준을 충족하는 작업 행동까지다. 정정, 결함, 재작업은 사건 정의와 중복 집계 기준을 갖는다. 토큰 값 미제공은 null로 두며 0으로 간주하지 않는다.
4. 실패·중단 run을 포함한 성공률과 전체 비용을 보고한다. 성공한 쌍만의 시간 비교는 별도 표시한다. 누락/실패를 제거해 효과를 과장하지 않는다.
5. 원시 로컬 기록에서 조건별 요약(표본수·성공률·중앙값·범위·누락수)을 재생성할 수 있다. 목표 개선율은 측정 전에 임의로 성공 기준으로 약속하지 않는다.
6. 합성 데이터의 정상·누락·중복·실패·시간 역전·단위 오류를 검증하고, 가이드에 실행 예시와 실제 측정 전임을 명시한다.
7. 사용자 개입 횟수·동일 의도/승인의 중복 요청·진행을 막는 응답 대기 횟수·수동 기록 요구를 사건별로 집계한다. 당시 이용 가능한 정보와 범위·위험 변화로 개입의 필요성을 분류하고, 판단 불가능한 경우는 미확인으로 남긴다. 사용자 대기 시간은 생활 여건의 영향을 받으므로 필요 없는 질문의 직접 증거로 쓰지 않는다.
8. 계측은 기존 run 기록에서 평가자가 추출한다. 사용자에게 매 턴 설문·수동 타이머·중복 입력을 요구하지 않는다. 추가 기록 비용이 있으면 평가 비용으로 별도 표시한다.

### 사용자 결정

계획서 작성 요청만 확정. 실제 실험 대상·모델 실행 비용 승인은 포함되지 않는다.

추가 확정 원칙: 사용자를 필요 이상으로 불편하게 하지 않는다 (2026-09-09).

### 변경 불가 제약

실제 프로젝트 내용·credential·개인 경로를 자동 수집하지 않는다. Runtime 배포·외부 계정 연결을 하지 않는다. 합성 결과를 실사용 성과로 제시하지 않는다.

### 에이전트 가정

| 가정 | 근거 | 틀렸다면 |
|---|---|---|
| 수동 run 기록과 로컬 집계로 먼저 시작한다 | 비용·호스트 종속성을 낮춰 비교 방법 검증 가능 | 자동 실행 별도 설계 |
| 선행 규칙 보완 후 기준 버전을 고정한다 | 변경 도중 비교하면 조건 혼재 | 버전별 cohort 분리 |

### 결정 대기 항목 (Open Questions)

도구·프로토콜 계획에 필요한 입력 없음. 실제 캠페인의 모델·호스트·시간/비용 한도는 실행 요청 시 확정한다.

## 실행 계획 (Implementation Plan)

### 사전 조사

선행 작업 결과와 기존 가이드의 효과 주장·테스트 범위를 재확인한다. 현재 수치는 단위 테스트 통과뿐이며 생산성 효과는 미측정이다.

### 구현 단계

1. 사례·판정 기준 고정 — 품질을 희생한 속도 개선을 구별하기 위해 `evaluations/scenarios/`에 자급적인 fixture와 기준 작성.
2. 기록 형식·비교 프로토콜 작성 — `evaluations/protocol.md`, `schema.json`에 조건과 지표·누락·실패 처리 정의.
3. 집계 CLI 작성 — `evaluations/summarize.py`에서 로컬 JSON 입력 검증과 Markdown/JSON 보고서 생성. 실행자를 대신해 원시 결과를 추정하지 않음.
4. 합성 데이터 검증·사용 가이드 — `tests/test_evaluation_summary.py`, `evaluations/README.md`로 계산과 재현 절차 확인.

### 예상 조용한 결정

평가자는 가능하면 조건을 가린 결과를 같은 기준으로 채점한다. 조건이 드러나는 한계는 보고한다. 소표본 pilot에서 인과·통계적 유의성을 주장하지 않는다.

### 수정 대상 파일

`evaluations/` (신규 source 전용), `tests/test_evaluation_summary.py` (신규), `guidebook/guidebook.md` (평가 안내 링크). 구체 파일 구조는 재개 시 확정한다.

### 참고 파일 (수정 없음)

선행 plan·verification, `README.md`, `.mpa/runtime/core/principles.md`.

### 반례

- MPA 조건만 더 많은 시간/도구를 사용 → 조건 manifest·총 비용을 함께 보고.
- 토큰 미제공을 0 처리 → null 유지, 비교 가능 표본수 명시.
- 어려운 실패를 제외하고 성공한 결과만 비교 → 실패·중단 포함 전체 집계와 성공 쌍 비교 분리.
- fixture를 모델이 이미 봄 → 독립 세션·실행 순서 교차, 일반화 한계 명시.
